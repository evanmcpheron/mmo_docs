Fixture and readiness

First integrated checkpoint: Phase 30. Stable fixture identifiers: WBP_HUD / WBP_Crafting / WBP_Merchant / normal server command routes.

The First Supplies route is completed once with keyboard/mouse, once with controller, once with large text/reduced motion and once with fishing’s accessible timing mode.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

ABriarwakePlayerController owns local widget lifetime and input focus. Gameplay continues on the server while menus are open; private data is pulled from approved projections.

Local preferences use local configuration, separate from MMO persistence. Account-backed preferences require an explicit privacy/versioning contract if added later.

Frontend, HUD, map/minimap, equipment, inventory/bank, vendor, loot, journal, vocation/crafting, fishing/farm, region, dialogue, social/chat/trade and recovery screens share consistent pending/error states.

Worked execution

  1. Complete a reference purchase/craft/contribution using the normal widgets and record the authoritative command/results.
  2. Close or destroy the widgets, recreate the Pawn in another zone and exercise the same server command contracts through the permitted controller/test harness.
  3. Reopen views: bind one observer, pull the current snapshot and compare rendered state with the durable result.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

The same permissions, costs and receipts apply without a widget. Reopening neither buys nor crafts nor advances a project.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Widget-hidden state cannot bypass station/range/price/skill checks; stale callbacks are ignored.

Concurrent case

Repeated open/close plus parallel requests does not multiply observers or reward callbacks.

Reconnect and server restart

Reconnect with no HUD and then reopen it; all canonical state is still present and private data remains owner-only.
