Fixture and readiness

First integrated checkpoint: Phase 13. Stable fixture identifiers: char-bw-way / merchant.thornmere / item.repair-kit / receipt.purchase.001.

char-bw-wayfinder starts with 100 copper, buys one 20-copper repair kit, sells a 5-copper surplus and commissions an essential fitting for an affordable fixture fee.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

ANpcServiceActor validates local service access. The persistence boundary owns balances, stock, escrow, bank transfers and final trade commits.

Record_Inventory, currency balance, MerchantStockRecord and TradeEscrowRecord update within durable transactions. The service locks records in a deterministic order and validates offer revision/hash.

WBP_Merchant, WBP_Bank and WBP_Trade show current revisions, all offered items/currency and explicit two-sided confirmation. Any offer change invalidates both confirmations.

Worked execution

  1. Earn fixture currency from the First Supplies quest and open the merchant through normal interaction.
  2. Buy the basic repair service/item, sell an eligible surplus and commission a necessary off-vocation basic product.
  3. Use that preparation to finish the story route without a player crafter or alternate character.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

Integer currency is conserved across receipts; essential supplies remain obtainable from NPC services.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Negative quantity, altered client price, insufficient funds or no capacity rejects losslessly.

Concurrent case

Competing purchase/bank/trade commands serialize against the same funds; two clients cannot spend one balance.

Reconnect and server restart

Reconnect after confirmed purchase; original receipt restores exactly one item/debit. Phase 25 extends the same service, not a duplicate wallet.
