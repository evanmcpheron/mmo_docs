Fixture and readiness

First integrated checkpoint: Phase 31. Stable fixture identifiers: load profile BW-30 / Thornmere + Elderwood / synthetic test accounts only.

Matrix: populations 1/2/5/10/30; baseline and 80/150 ms illustrative RTT; 0/1/3% illustrative packet loss; quiet route and shared-node hotspot. Hardware/budgets remain to be measured.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Ownership and user journey

Dedicated zones validate gameplay commands and use server-only credentials. The persistence boundary applies lease fencing, transactions, authorization and audit controls.

Versioned durable records, backups and restricted audit logs are separate from disposable runtime actors. Secrets and bearer tokens never enter the public docs, client package or normal logs.

Operational dashboards show aggregate latency, errors, contention, replication, crashes and progression stalls. Player-facing UI shows maintenance and recovery states without leaking internal credentials.

Worked execution

  1. Record hardware, server build, client process count, storage configuration, warmup, test duration and network impairment settings.
  2. Run the one-human baseline, then 2/5/10/30 clients with simultaneous combat, harvest, vendor, social, project and boundary operations.
  3. Collect frame time, replication traffic, command latency, rejection categories, durable receipts and client UI freshness; reconcile balances and grants.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response
