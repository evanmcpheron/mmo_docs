Account fixture acct-bw-001 has two permitted slots; char-bw-hearth uses discipline.vanguard and vocation.hearthkeeper at zone.thornmere / spawn.square. Resolve FactionId from the approved faction fixture; no real faction ID is authored on the audited main baseline. Slot counts and locations remain test values, not a replacement faction starting-region policy.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Ownership and user journey

ABriarwakeGameMode admits a verified character-session lease. ABriarwakePlayerController routes owned commands. A newly spawned ABriarwakeCharacter is only the current body.

The persistence boundary writes Record_Account, Record_Character and Record_CommandReceipt atomically with the normalized name reservation and unique starter kit. Record_Character owns permanent FactionId/CombatDisciplineId, active VocationId and independent Progression.Combat / Progression.Vocations histories; its Revision versions the complete progression/build projection.

WBP_Login → WBP_CharacterSelect → WBP_CharacterCreate → WBP_HUD. Publish only the permitted public identity/appearance subset. UCharacterStateComponent exposes owner-only committed progression, including inactive vocation histories; raw records, account identity and authentication tokens are never public PlayerState fields.

Worked execution

  1. Open WBP_CharacterCreate; choose an audited appearance, approved faction, available Vanguard (discipline.vanguard) and Hearthkeeper (vocation.hearthkeeper) independently. Confirm that faction and class are permanent.
  2. Submit create.hearth.001 with all required IDs. The authenticated service independently validates every selection, name and slot, then atomically commits identities, initial combat/vocation progression and the unique kit/name/receipt outcomes.
  3. Admit one session lease and spawn at Thornmere square; UI displays the committed vocation and supported layers.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

One CharacterId and kit receipt; permanent faction/Vanguard and active Hearthkeeper with independent retained progression.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Omit CombatDisciplineId, omit VocationId, use unavailable IDs and omit/forge FactionId in separate requests. Each fails before name/item mutation. Attempt a post-creation class patch: PermanentIdentityLocked, with unchanged progression.

Concurrent case

Two requests for the same normalized name produce one reservation; repeat request returns the original CharacterId.

Reconnect and server restart

Logout, restart and reconnect: same permanent identities, appearance, active vocation and all keyed histories; no second kit or threshold rewards.
