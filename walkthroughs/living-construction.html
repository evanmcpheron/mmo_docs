Fixture and readiness

First integrated checkpoint: Phase 23. Stable fixture identifiers: region.elderwood / project.north-road / test target 100 / progress 70.

project.elderwood.north-road has 12 essential units and explicit base-skill/NPC alternatives for all categories. Optional reinforcement uses the frozen population model described separately.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

ARegionProjectionActor and ABriarwakeGameState publish public stage snapshots. Runtime tile overlays and props consume committed stage IDs; they cannot complete projects themselves.

Record_Region, ProjectContributionRecord and Record_CommandReceipt are written by one persistence boundary. A material contribution debits inventory and advances the stage in the same commit.

WBP_RegionBoard displays essential progress, optional enhancements, contribution choices and remaining personal effort. New arrivals receive an authoritative revision before applying deltas.

Worked execution

  1. Run a separate deterministic UI fixture at 70 of 100 credited units, with five distinct vocation contribution categories.
  2. Join a second client; pull the region snapshot and show 70%, open objectives and the current authored road tile stage.
  3. Complete valid remaining objectives, or run the absolute solo-equivalent contract in a fresh realm, then observe road, vendor and quest updates.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

Exactly one completed stage revision; newcomers see authoritative progress; the 70/100 display fixture is not the 12-unit balance proposal.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Old-stage/finished-objective contributions reject without consuming items; duplicate receipt is not a new donation.

Concurrent case

Five vocation types can cooperate, but the transaction does not require five types online. Concurrent final contributions serialize.

Reconnect and server restart

Restart after final commit before presentation delivery; all projections reconstruct the complete stage without granting new rewards.
