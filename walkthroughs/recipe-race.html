Fixture and readiness

First integrated checkpoint: Phase 15. Stable fixture identifiers: recipe.watch-fitting / InventoryRevision 7 / request.craft.001.

recipe.watch-fitting uses 3 IronOre and 1 SalvagePlate to produce 1 WatchFitting. Start with 6 ore and 2 plates; two distinct valid crafts may legitimately succeed, but replaying one request cannot make a third.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

ACraftingStation advertises service definitions; UActionExecutionComponent checks action eligibility. UDurableStateClient submits server-validated operations to the one persistence boundary.

Record_CraftReservation is used only when timed crafting requires durable reserved inputs. Record_Inventory, Record_Character and Record_CommandReceipt change atomically at completion.

WBP_Crafting shows ingredient availability, output preview, applicable specialization and pending state. Closing the panel neither consumes inputs nor cancels a committed result.

Worked execution

  1. Seed three IronOre and one SalvagePlate, no fitting, and a valid forge station in range.
  2. Submit the same craft intent twice, then submit a distinct competing craft request against revision 7.
  3. Disconnect immediately after authoritative success, then reconnect and equip/use the single resulting fitting item where permitted.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

One material debit and one produced instance; duplicate original returns same result; competing stale command is rejected.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Full capacity, stale revision or unsupported recipe fails without partial consumption.

Concurrent case

Atomic inventory locks/revision checks prevent two output items from one input set.

Reconnect and server restart

Query the durable receipt; a lost success message is not a rollback. Supported art fallback changes only presentation.
