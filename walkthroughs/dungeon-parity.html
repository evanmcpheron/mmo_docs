Fixture and readiness

First integrated checkpoint: Phase 28. Stable fixture identifiers: instance.bellroot.001 / checkpoint.entry / milestone.bellroot-cleared.

dungeon.bellroot-vault has one critical milestone unlock.bellroot-road. The same milestone is available at human populations 1, 2 and 5.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

The dedicated instance server owns encounter progress and active participation. Companions follow constrained server AI with explicit assistance tasks and no separate player economy.

InstanceRecord stores resumable checkpoint and eligible reward receipts. Character and region milestones commit through the existing persistence boundary.

WBP_DungeonEntry shows variant, expected roles, available NPC aid and recovery policy. WBP_Party clearly distinguishes NPC helpers from human participants.

Worked execution

  1. Enter alone from the gate; reserve an instance and select the solo mechanism variant plus a bounded helper.
  2. Complete the paired-switch/telegraph mechanic through the authored solo substitution rather than an impossible simultaneous human check.
  3. Repeat with two and five humans in fresh fixtures, using cooperative mechanics and the same essential narrative milestone.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Rejected command

An inactive player cannot receive helper-farmed rewards; spoofed checkpoint or duplicate boss claim rejects.

Concurrent case

Party reconnect and simultaneous exit/reward requests preserve one instance/character ownership and reward receipt.

Reconnect and server restart

Crash the instance after the checkpoint and before final reward; recover the defined checkpoint, not a fabricated clear.
