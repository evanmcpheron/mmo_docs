Fixture and readiness

First integrated checkpoint: Phase 11. Stable fixture identifiers: encounter.road-ambush.001 / spawn generation 2 / loot receipt per eligible character.

dummy.thornmere.01 has 100 health. GA_BasicMelee costs 10 stamina and deals 20 damage in the deterministic fixture; these are test values, not final balance.

All sample quantities and timings are controlled fixtures. Actual authored definitions must match the scenario before running it.

Configure and connect

Open the normal character-selection and Thornmere route. Assign the relevant definitions from DA_GameCatalog and place the station/NPC/site/encounter named by this scenario. Initialize durable records once through the controlled fixture setup; never manufacture rewards in the UI.

Ownership and user journey

The PlayerState-associated AbilitySystemComponent and UCombatAttributeSet own runtime ability/attribute behavior. ABriarwakeCharacter is the current avatar. Server traces and target validation decide hits; PaperZD observes action state.

Record_Character.CombatDisciplineId is permanent after creation. Progression.Combat stores independent TotalXP, DefinitionVersion, PurchasedTalentIds and UnspentTalentPoints. Record_Character.Revision is also the progression/build revision; derive level and rebuild abilities from validated definitions without replaying rewards. Vocation changes preserve this entire combat record and its grants; talent respec remains within the chosen discipline.

WBP_HUD displays health/stamina/mana, cooldowns and action errors; WBP_Talents requests purchases. Keyboard and controller can select the same valid targets.

Worked execution

  1. Start the ambush alone; server validates costs, collision, target range and damage.
  2. A second player joins and receives eligible combat/support participation under the declared encounter policy.
  3. On legitimate server death, finalize one encounter outcome and roll/assign eligible loot under the configured rule.

Command and projection sequence

Player input / UMG
  → owned Controller command (custom project API)
  → authoritative validation: identity, lease, action, range
  → durable boundary: revision + idempotency + domain uniqueness
  → atomic state/receipt commit
  → current snapshot / notification
  → UI observer and cosmetic PaperZD/audio response

Expected successful outcome

Declared participants receive appropriate separate XP/loot receipts; no last-hit monopoly on essential progress.

Inspect the specific record IDs above and compare before/after balances, revisions and receipt identities. An on-screen success toast is not sufficient evidence.

Rejected command

Forged damage amount, duplicate projectile impact or dead-target attack cannot create another death.

Concurrent case

Simultaneous lethal hits race against the same encounter generation; one death event wins.

Reconnect and server restart

Restart after death commit before reward UI: receipts restore rewards, corpse presentation does not reroll.
