Unreal Engine 5 C++ foundation

Native C++ ownership, dedicated servers, setup gates and future verification.

Project baseline and repository boundary

Briarwake is a server-authoritative MMORPG designed for Unreal Engine 5, native C++ and dedicated servers. Game implementation is 0% complete: no gameplay, server, rendering, database, infrastructure or plugin integration is verified. Completed design contracts and documentation checks describe requirements only. The implementation location is unspecified and will be established in a separate task. This documentation builds and validates on its own. Do not create a game project here.

C++ ownership and Unreal mechanisms

Authoritative rules, boundary validation and state commits belong to C++. Blueprints may compose editor-facing assets, presentation and configuration through narrow C++ interfaces. Do not duplicate an authoritative rule in Blueprint. Choose an Unreal mechanism for its actual responsibility rather than mapping every schema to a class.

Mechanism Intended use and limit
Native modules, classes and value types Small cohesive rule and integration owners. Use plain C++ values for calculations where reflection is unnecessary; introduce module boundaries only for demonstrated dependencies.
Actors and Actor Components World entities and composable behavior with explicit lifecycle and replicated-state ownership. Do not create one Actor per catalog row.
Pawns / Characters and Controllers Possession, input intent and movement integration. Evaluate CharacterMovementComponent before building prediction; verify planar/floor rules, equal collision bodies and plugin compatibility.
GameMode, GameState, PlayerState Server session rules, permitted shared session views and permitted player views respectively. Public state must exclude private ledgers, resources and hidden entities. None is a persistence solution.
Subsystems Only a cohesive responsibility matching an engine-managed lifetime. Avoid global mutable state and unrestricted subsystem lookup as dependency injection.
Enhanced Input Candidate for remapping and contextual input in BW-028; emits intent through the controller boundary and grants no authority.
Gameplay Tags Candidate for hierarchical classifications where needed. Preserve canonical identifiers and closed enum encodings; do not replace every existing enum or invent gameplay categories.
Data Assets Candidate editor-facing content route in BW-095. Canonical JSON contracts remain authoritative; validate import/export, stable identity, units and runtime admission without a competing rule definition.

Unreal's Gameplay Framework, Enhanced Input, Gameplay Tags, Data Assets and networked character movement describe candidate facilities. The table states Briarwake engineering choices and verification obligations, not implemented features. No Gameplay Ability System, backend vendor or scaling framework is selected by implication.

Engineering standards

  • Use descriptive Unreal C++ names and standard type prefixes (U, A, F, E, I, T and b for booleans). Follow the selected engine's coding standard and compiler requirements. Keep functions short enough to expose intent, explicitly typed and narrow in responsibility. Comments explain only otherwise non-obvious intent, constraints or edge cases.
  • Apply Clean Code and SOLID where they clarify responsibilities and substitutable behavior. DRY means one authoritative definition of each rule, identifier and validation policy; similar syntax alone does not justify an abstraction. Avoid speculative frameworks and generic managers.
  • Keep includes and public interfaces minimal, declare module dependencies in Build.cs, and keep editor-only modules/assets out of dedicated-server runtime dependencies. Do not let presentation or transport handlers own gameplay rules.
  • Use UCLASS, USTRUCT, UENUM, UPROPERTY and UFUNCTION only where reflection, serialization, editor exposure or networking requires them. Specify allowed edits/calls deliberately. Reflection or replication exposure is not an authorization check.
  • Document object lifetime and ownership. For UObject references, select reflected strong references such as UPROPERTY with TObjectPtr where ownership requires retention, TWeakObjectPtr for non-owning observations, and soft references for deferred asset loading as appropriate. A raw UObject pointer does not itself keep its object alive. Use RAII and appropriate smart ownership for non-UObject resources; do not manage UObjects with ordinary shared ownership.
  • Check references across destruction, unpossession, world teardown, travel and asynchronous callbacks. Cancel or detach work on owner teardown, avoid capturing expired objects, and specify thread access. Replication and persistence lifetimes must not be inferred from an object's memory address.
  • Maintain explicit C++ authority and recipient boundaries. Derive identity from the authenticated connection; validate sequence, size, timing, ownership, visibility, range and current state before committing. Clients submit intent. Never trust client-authored outcomes, inventory, currency or positions.
  • Keep rejection observable with bounded actionable diagnostics and no secrets. Tests must cover invalid, stale, duplicate, conflicting and failure-injection cases. Do not suppress checks, manufacture fallback success or turn authored tests into executed evidence.
  • Measure hot paths and resource budgets with representative workloads before optimizing. Any new abstraction must have a cohesive owner and make the current implementation simpler to understand and test.

Verify details against Epic's C++ coding standard, object pointer guide and UnrealBuildTool. These standards guide future work; this repository contains no placeholder C++ implementation.

Future project setup and reproducible builds

  1. BW-001-T01 selects a compatible UE5 revision and records engine source/distribution identity, compiler, SDK, host and target platform requirements using Epic's version-specific development setup. No particular minor version, installed IDE, OS or hardware is assumed.
  2. BW-001-T02 creates a blank native C++ project when implementation is commissioned, outside this documentation. Pin runtime module dependencies and Game/Editor targets. Verify a clean editor/client launch before gameplay or bulk content.
  3. BW-001-T03 defines a dedicated Server target via Target.cs and verifies a player-free startup. Epic's server tutorial requires a source build and C++ project. Its sample content and Windows commands are examples; establish exact build, cook, stage and launch commands for each chosen platform.
  4. BW-001-T04–T07 verify required configuration rejection, reproducible UBT/UAT build and cooked artifacts, client secret exclusion and automation outcomes. Record actual engine/toolchain revisions, source identity, commands, logs and artifact hashes. Reproducible means declared inputs and repeatable outcomes; bit-for-bit identity requires separate evidence.
  5. BW-100 inventories and validates the already acquired replication plugins on the compatible baseline before BW-004 connectivity and BW-005 movement. Publish a compatibility/capability matrix with unsupported and unresolved entries. Do not purchase alternatives or assume capabilities.
  6. BW-004–BW-013 establish two independent clients, authoritative movement and recipient-safe state; BW-012 proves a minimal action. Transport loss and re-entry are tested early; durable reconnection/checkpoint recovery follows BW-027 and the persistence prerequisites.

Future automation and evidence

Use Unreal's Automation Test Framework for appropriate rule/feature tests and Functional Testing for world-level behavior. Evaluate Gauntlet for unattended server/client sessions when needed. First establish a bounded C++ fixture runner with separate build, startup, timeout and executed assertion outcomes. A missing executable, missing report or unrun fixture is not a pass. Multi-process tests must use a dedicated server and two independent clients; local editor previews and logical recipients do not prove networking.

Keep seeded rule outcomes separate from nondeterministic timing observations; retain raw metrics, revisions and negative controls. Test-only controls are excluded or inaccessible in production artifacts. Documentation commands validate documents, schemas, links, search and generated output only. No Unreal build, plugin test or multiplayer run occurs as part of this documentation reset.

Unresolved technical inputs

Exact supplied plugin identities/versions and licenses; compatible UE5 revision and engine source access; host/client/server platforms and compiler/SDK matrix; plugin/native replication interaction; actual authorization and serialization limits; unit/axis mapping for canonical planar coordinates; identity provider, durable store and hosting; target capacity, latency/recovery budgets; renderer, graphics backend and measured pixel-art settings. Existing gameplay decisions remain in open decisions. No assumption here resolves them silently.
