Phase: 2. First authoritative multiplayer interaction · Completion milestone: Two-client authoritative action

Objective and scope

Expose architectural bottlenecks using the first integrated multiplayer workload before broad content production.

Scope: Movement, direct actions, join/leave bursts and current entity counts on a declared test machine. This produces measurements and follow-up decisions, not a realm-capacity promise.

Acceptance criteria

  1. AC 1

    A repeatable workload drives moving clients and implemented actions, includes burst joins/departures, and records client count, content/rules versions, hardware and measurement duration.

  2. AC 2

    Reports retain tick median/tail percentiles, queue depth, memory, bytes per client, rejection/duplicate counts and recovery behavior rather than connection counts alone. Record the actual client render configuration and frame timings separately so rendering cost is not mistaken for a server or bandwidth limit.

  3. AC 3

    Latency runs include 0/50/100/150/250 ms RTT plus declared jitter, snapshot reordering and 1–5% loss; failures and rejected inputs remain visible.

  4. AC 4

    The report identifies measured constraints and bounded next changes, explicitly distinguishes prototype rates from achieved capacity and records unresolved budgets before further scale claims.

Verification and blockers

Completion evidence required: Required future proof: reproducible workload/configuration, raw measurements and a reviewed bottleneck report tied to the tested build, with reruns for any claimed improvement.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.
