Not Started · Parent epic: BW-097 · 3D pixel-art renderer and camera feasibility proof

Epic acceptance criteria: BW-097-AC-9

Implementation scope

  • Add --case contact to the existing probe with representative cobblestones, wall/roof corners, prop bases, foliage-ground contact and an animated character foot anchor. Provide raw lighting/no-contact, candidate-only, combined and fallback controls, with exact settings and reproducible paths.
  • Evaluate applicable baked, real-time and authored contact/ambient-occlusion approaches using T01 capability evidence. Record why a candidate is inapplicable instead of requiring unavailable renderer features. Measure incremental CPU/GPU frame costs and memory on the pinned hardware with repeatable sampling and an explicit lower-cost alternative.
  • Keep material/contact settings under the existing probe owner and visual-only. No canonical gameplay type applies; do not modify world coordinates, collision or visibility rules. Avoid duplicate darkening when combining baked and dynamic treatment, especially at character feet and thin/overlapping surfaces.

Out of scope

  • A production baking pipeline, a new renderer feature/fork, world-wide AO content or final environment integration (BW-099).

Dependencies

Hard prerequisites: BW-097-T05

Acceptance criteria

  1. AC 1

    The comparison records applicable baked/real-time/authored candidates, actual renderer support, selected treatment, fallback and attributable incremental costs at the approved internal resolutions.

  2. AC 2

    Still and slow/diagonal camera/actor sequences preserve accepted contact/depth separation without dark halos, false outlines, flicker, duplicate darkening or lost silhouettes beyond T03 bounds.

  3. AC 3

    The animated foot-anchor fixture remains continuously grounded without altering source anchor data; fallback retains approved depth/readability cues and has measured lower cost or an explicitly reviewed cost tradeoff.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; every res:// path uses that project root. The rendering launcher/case below is a deliverable of these tickets, not an existing command.
python3 tools/verify_toolchain.py
python3 tools/run_rendering_probe.py --case contact

Setup

  1. Use T01 measured capability path, T03 acceptance/budget sheet and T05 lighting/outlines. This ticket supplies all contact fixtures and candidate/fallback controls; full effect composition is verified in T09.

Actions

  1. Run contact; capture no-contact, each applicable candidate, combined and fallback at identical camera/lighting settings. Inspect prop corners, foliage ground contact and animated feet.
  2. Run stationary, slow and diagonal paths, including moving actors. Record cost samples and compare visual failures/costs against the approved bounds; verify foot-anchor logs before and after.

Expected results

  1. A reviewed candidate/fallback comparison names capability, incremental costs and visual findings; unsupported paths are labeled explicitly.
  2. Contact treatment remains stable/readable without darkening or anchor mutation; unmet bounds remain blocking findings.

Reset

  1. Use the probe Reset control to restore the checked-in case settings, camera, actor path and effect toggles; quit the graphical process normally. No persistent gameplay state is created.
  2. Keep prior captures, failed results and reports intact. Repeat into a fresh launcher-owned artifacts directory; restore only deliberately modified disposable inputs, leaving source assets, canonical registries and existing user files intact.

Completion evidence and blockers

Required evidence: Retain candidate applicability matrix, settings, matched captures/clips, raw incremental timing/memory samples, fallback cost comparison, foot-anchor invariance and approved contact-depth findings.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
