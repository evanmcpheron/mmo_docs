Detailed epics

BW-004 · Dedicated connectivity and bounded command admission Not Started

Objective: Connect authenticated test clients to a dedicated authority and reject invalid requests.

Scope: Connection lifecycle, protocol negotiation, trusted test admission and command identity/size/rate/sequence limits; public account integration belongs to BW-019.

Hard dependencies: BW-001, BW-002

Recommended predecessors: BW-003

Acceptance criteria (AC)

  1. Two separately running clients join a dedicated process using accepted compatible test credentials and receive distinct authorized sessions.
  2. Unauthenticated, expired, incompatible, oversized, out-of-sequence and unauthorized requests are rejected without mutating game state.
  3. Repeated action identities return a consistent outcome without creating another accepted action; conflicting reuse rejects.
  4. Movement, combat/control and reliable state traffic remain distinguishable and connection failure is visible to the client.

Completion evidence required: Two-client connection traces and malformed, replay and admission rejection fixtures.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: A restricted test adapter validates trust boundaries early; choosing an account vendor is unnecessary for this technical proof.

Related documentation: Authority and networking; Verification requirements

BW-005 · Authoritative movement and world geometry Not Started

Objective: Resolve movement from client intent against authoritative geometry and time.

Scope: Continuous planar movement, floor identity, collision, path bounds and server clock; 3D scene placement maps to this geometry, while camera projection, visual elevation and prediction remain separate.

Hard dependencies: BW-001, BW-002

Recommended predecessors: None

Acceptance criteria (AC)

  1. Equal-duration legal input gives the documented base speed, normalized diagonal movement and equal gameplay bodies across races.
  2. Independent aim and motion remain continuous regardless of model facing, eight preview headings, camera projection, visual height or pixel-grid alignment.
  3. Walls, closed boundaries, wrong-floor destinations and impossible movement are rejected or corrected using authoritative geometry.
  4. Movement acknowledgments identify accepted input and state revision; repeated input cannot move a character twice.

Completion evidence required: Headless geometry/movement fixtures with authoritative position and input traces.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Related documentation: Combat rules; Authority and networking; Selected 3D pixel-art direction

BW-006 · Derived attributes and bounded resources Not Started

Objective: Resolve numerical character state without requiring a complete class roster.

Scope: Attribute scaling, racial offsets, combat conversions, resource maxima and regeneration; specialized resource hooks are certified later.

Hard dependencies: BW-001, BW-002

Recommended predecessors: None

Acceptance criteria (AC)

  1. Published allocation/formula fixtures produce the documented derived values with the declared rounding and modifier order.
  2. Resource gains, reservations and regeneration cannot exceed caps or produce negative available balances.
  3. Healer fixtures use Mana plus a signature meter; class/race changes cannot silently alter documented eligibility or base reach.
  4. Invalid resource kinds, caps and unsupported numerical content are rejected rather than given guessed defaults.

Completion evidence required: Executed numerical boundary fixtures and comparison to existing arithmetic examples.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Related documentation: Attributes; Progression; Execution contracts

BW-007 · Entity lifecycle and recipient snapshots Not Started

Objective: Give clients a coherent view of entities they are allowed to observe.

Scope: Spawn/despawn, revisions, initial baselines, owner-private state and visible public value projections; broad interest scheduling is BW-013.

Hard dependencies: BW-004, BW-005

Recommended predecessors: None

Acceptance criteria (AC)

  1. Two clients agree on authoritative movement and entity identity after join, leave and re-entry.
  2. A new observer receives current state rather than depending on an earlier event it never saw.
  3. Stale or duplicate snapshots do not resurrect despawned entities or overwrite newer state.
  4. Owner resources and private recovery state are absent from another client’s public snapshots; unavailable references fail safely.

Completion evidence required: Two-client lifecycle traces including late join and stale snapshot injection.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Begin value projections with movement and identity. Add cast/status/projectile projections with their gameplay rules rather than designing a universal final replicator.

Related documentation: Authority and networking; Public projection definitions

BW-008 · Predicted movement and reconciliation Not Started

Objective: Keep local movement responsive while the server retains the final position.

Scope: Local movement prediction, acknowledged input reconciliation and remote interpolation; no predicted damage or unrestricted historical hit rewind.

Hard dependencies: BW-007

Recommended predecessors: None

Acceptance criteria (AC)

  1. At 0, 50, 100, 150 and 250 ms RTT, correction converges to the server position without applying acknowledged input twice.
  2. Jitter and 1–5% packet loss do not leave permanent remote motion divergence after state delivery resumes.
  3. Collision corrections and ownership changes discard obsolete prediction history and cannot move a character through a wall.
  4. Record correction magnitude/frequency and input response for each scenario, with an explicit review of understandable failure at 250 ms.
  5. Render-camera alignment and visual interpolation do not quantize predicted or authoritative positions; slow tracking during correction and teleport/reset cases remain understandable in the selected low-resolution view.

Completion evidence required: Network-impairment runs with motion traces, correction metrics and reviewed recordings.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Movement semantics must exist first. Prediction is proven before broad human testing, but does not block isolated combat or durable-state work.

Related open decisions: Capacity, security and recovery budgets

Related documentation: Authority and networking; Verification requirements; Selected 3D pixel-art direction; Rendering, camera and input

BW-009 · Target relations and legal spatial intent Not Started

Objective: Resolve eligible targets and aiming from authoritative information.

Scope: Target lock/cycling, friendly selection, line/cone/ground/self modes, reach, line of sight and floor rules; visual controls integrate in BW-028.

Hard dependencies: BW-005, BW-006

Recommended predecessors: None

Acceptance criteria (AC)

  1. Target cycling follows angular difference, distance and stable-ID ordering and excludes illegal hidden/dead/friendly/cross-floor candidates.
  2. Every admitted targeting mode resolves the required intent fields and rejects unused or invalid target data.
  3. Range, relation and geometry failures leave resources and cooldowns unchanged at acceptance.
  4. Ground placement rejects protected, inaccessible and closed-door locations; faction/group relation changes are rechecked when required.

Completion evidence required: Target-policy fixtures over all supported modes, relations and geometry failures.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Related documentation: Combat rules; Execution contracts; Authority and networking

BW-010 · Cast commitment and ability timing Not Started

Objective: Resolve one authoritative ability lifecycle with precise failure semantics.

Scope: Learned/build checks, reservations, GCD, cast/channel/instant timing, release revalidation and cooldown commitment; no full roster.

Hard dependencies: BW-009

Recommended predecessors: None

Acceptance criteria (AC)

  1. Acceptance verifies ability/build/equipment/life/control/target/resource permissions and reserves costs only for legal commands.
  2. Interrupted pre-release casts release reservations, preserve the started GCD and do not consume the ability cooldown under release-commit.
  3. Channels commit at start without refunds on cancellation; accepted instants commit cost and cooldown together.
  4. Movement cancellation, target loss, late input and duplicate commands yield declared outcomes with no extra cast or resource spend.

Completion evidence required: Executed instant/cast/channel fixtures covering valid release, rejection, interrupt and duplicates.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Timing and commitment rules precede expansion of effects and their replicated outcomes; animation never determines authoritative release.

Related documentation: Combat rules; Execution contracts

BW-011 · Damage healing and absorb resolution Not Started

Objective: Resolve effective combat results using documented numerical and accounting rules.

Scope: Primary effects, mitigation, criticals, healing, shields and bounded modifier order; recurring statuses and complex proc graphs follow separately. Bounded damage transfer uses the same effective-result accounting.

Hard dependencies: BW-010

Recommended predecessors: None

Acceptance criteria (AC)

  1. Identical seeded contexts yield the documented modifier order, rounding and effective damage/healing/absorbed amounts.
  2. Overkill and overhealing are recorded without increasing effective output, threat or reward contribution.
  3. Support attribution sums only to the actual support increment under ordered marginal accounting and never adds damage again.
  4. Resource/cooldown commitment and root action identity survive a rejected or duplicate result without extra outcomes.
  5. Redirected damage obeys its cap, receives no second mitigation and cannot redirect recursively; an immune protector leaves damage on the original recipient.

Completion evidence required: Numerical execution fixtures including caps, shields and multi-source support attribution.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Related documentation: Attributes; Combat rules; Execution contracts

BW-013 · Interest privacy and bounded state traffic Not Started

Objective: Keep disclosure correct as relevance and entity counts change.

Scope: Floor/instance/spatial interest, relevant hazards, explicit authorization removal, projection redaction and independent traffic priorities. Initial verification covers the implemented package; later state producers extend this disclosure contract.

Hard dependencies: BW-007, BW-009

Recommended predecessors: None

Acceptance criteria (AC)

  1. Hidden and cross-floor entities are absent from unauthorized snapshots, targeting queries and public correlation identifiers; outlines, shadows, reflections, refractions and other render passes cannot reconstruct or reveal excluded entities.
  2. For each currently implemented cast/status/effect state kind, interest entry restores current state without historical event replay; authorization loss removes or redacts it. Each later state-producing epic must pass these same projection checks before admission.
  3. A hazard that can affect a recipient remains represented while unrelated cosmetic updates may be limited.
  4. A recorded crowded synthetic scene demonstrates finite relevant sets, queue bounds and measured traffic; reliable chat-like traffic does not stall replaceable movement.
  5. Tracking/reveal returns only authorized markers within declared bounds and cannot discover a hidden player or extend visibility through client camera zoom.

Completion evidence required: Packet inspection and visibility-boundary fixtures plus a documented synthetic-load trace.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Privacy is a correctness boundary from the first integration. Final spatial tuning and launch capacity remain measurement-driven later work.

Related documentation: Authority and networking; Interface and accessibility; Selected 3D pixel-art direction; Rendering, camera and input

BW-028 · Action controls and legible combat feedback Not Started

Objective: Expose enough accessible interaction to test actual gameplay decisions early.

Scope: Rebindable movement/target/cast input, action bar, HUD, queue/cancel, telegraphs, status/resource/cast/rejection feedback and presentation hooks; final asset production is separate. Projected world picking, independent UI composition and occluder-aware cues integrate with the active render view; placeholder art can serve the first technical proof.

Hard dependencies: BW-007, BW-010

Recommended predecessors: BW-097

Acceptance criteria (AC)

  1. A player can target, preview/confirm/cancel ground intent, queue one eligible action within the documented window and see rejection reasons.
  2. HUD/action bars show authoritative resources, GCD/cast/cooldown and target state; predicted feedback corrects after rejection.
  3. Friendly-frame targeting has precedence and actionable hazards remain distinguishable without relying only on color.
  4. Keyboard bindings, text/UI scale and reduced visual effects can be exercised independently of world resolution; model pose and camera snapping never decide aim, collision or release.
  5. Pointer ground previews and selection map through actual viewport scale, letterbox offsets, camera projection and snap correction to the intended server floor/position; UI capture and invalid/occluded geometry have deterministic rejection/cancel behavior.

Completion evidence required: Keyboard/controller-if-supported interaction recordings and accessibility checklist with executed correction/rejection cases.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Interaction and feedback belong beside the first technical slice so human tests can reveal control and latency problems; polished art remains later work.

Related open decisions: Render configuration and supported quality envelope

Related documentation: Interface and accessibility; Combat rules; Authority and networking; Selected 3D pixel-art direction; Rendering, camera and input

BW-012 · First authoritative multiplayer action proof Not Started

Objective: Demonstrate the smallest integrated movement-and-action loop before a full game journey.

Scope: Two test clients, one controlled target, authoritative direct action and visible rejection; temporary non-economic state is sufficient.

Hard dependencies: BW-003, BW-011, BW-013, BW-028

Recommended predecessors: BW-008, BW-018

Acceptance criteria (AC)

  1. Two clients move, select an eligible target and observe the same accepted cast and resulting health change from one authoritative action.
  2. A forged hit, position or private-state request fails without changing authoritative state or revealing hidden data.
  3. A late observer receives current health/cast state and packet loss followed by a baseline leaves neither client permanently stale.
  4. The run records action latency, tick/traffic observations and a clear client failure reason; it claims no persistent economy or complete beginner experience.

Completion evidence required: An executed two-client scenario with correlated server/client traces and captured feedback.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: This narrow proof reduces the cost of discovering an incompatible command/simulation/projection boundary. A full offline combat kernel or full database product is not a prerequisite.

Related open decisions: Incremental topology and comparable branch orders

Related documentation: Authority and networking; Verification requirements; Combat rules

BW-083 · Representative early simulation and bandwidth probe Not Started

Objective: Expose architectural bottlenecks using the first integrated multiplayer workload before broad content production.

Scope: Movement, direct actions, join/leave bursts and current entity counts on a declared test machine. This produces measurements and follow-up decisions, not a realm-capacity promise.

Hard dependencies: BW-012

Recommended predecessors: BW-008, BW-018

Acceptance criteria (AC)

  1. A repeatable workload drives moving clients and implemented actions, includes burst joins/departures, and records client count, content/rules versions, hardware and measurement duration.
  2. Reports retain tick median/tail percentiles, queue depth, memory, bytes per client, rejection/duplicate counts and recovery behavior rather than connection counts alone. Record the actual client render configuration and frame timings separately so rendering cost is not mistaken for a server or bandwidth limit.
  3. Latency runs include 0/50/100/150/250 ms RTT plus declared jitter, snapshot reordering and 1–5% loss; failures and rejected inputs remain visible.
  4. The report identifies measured constraints and bounded next changes, explicitly distinguishes prototype rates from achieved capacity and records unresolved budgets before further scale claims.

Completion evidence required: Required future proof: reproducible workload/configuration, raw measurements and a reviewed bottleneck report tied to the tested build, with reruns for any claimed improvement.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: A small integrated probe can invalidate expensive assumptions early; it should not wait for full professions, raids or the complete roster. It does not justify premature seamless worlds or microservices.

Related open decisions: Capacity, security and recovery budgets; Incremental topology and comparable branch orders
