Not Started · Parent epic: BW-004 · Dedicated connectivity and bounded command admission

Epic acceptance criteria: BW-004-AC-2, BW-004-AC-3, BW-004-AC-4

Implementation scope

  • Extend the T03 admission owner with explicitly configured SecurityPolicy per-request byte/array/rate limits and sequence/owner checks. Route only connection-owned requests through native Controller RPCs, resolving identity from T02 on every request before dispatch. Enforce byte bounds before decoding/allocation and validate arrays, unknown fields/tokens, finite values and exact integer ranges using the existing canonical decoder. RPC ownership is necessary but does not replace authorization.
  • Missing required endpoint configuration fails closed; a zero request count disables its family, windows are positive and rate enforcement is independent of GCD. Select explicit test limits in the implementation configuration and test at/beyond each bound; no production tuning values are chosen here. Preserve the original T03 retry outcome under throttling; transport flood rejection cannot replace a prior action result or turn an identical retry into a new action.
  • Use the canonical NetworkTrafficChannel values movement_snapshots, combat_control_events and reliable_state_operations for observable classification. Map each enabled path to actual native RPC/property freshness, recipient and reliability behavior; do not invent independent network channels. Exercise representative test-only traffic without implementing movement, combat, entity replication or economic operations. A reliable response must not imply durable transaction completion.
  • Reuse the T01/T02 connected scenario for the real boundary: two clients, one dedicated authority, a server-owned test-only counted dispatch/effect sink and recipient observations. Add only required controls through the existing harness/process helpers. Run deterministic policy/decoder failures first, affected C++ compilation and a focused connected human QA handoff; missing native peer execution remains unverified. Reuse T03 unit evidence and prior lifecycle results rather than rerunning all suites.

Out of scope

  • Per-domain gameplay legality (BW-005/BW-010 and successors), public entity/privacy replication (BW-007/BW-013), durable transactions (BW-018), production account/session features (BW-019), capacity benchmarks, packet/configuration matrices, packages and new runner frameworks.

Dependencies

Hard prerequisites: BW-001, BW-002, BW-004-T03

Acceptance criteria

  1. AC 1

    Valid in-bound requests route only for their authenticated owner. Unauthenticated/expired sessions, oversized/malformed payloads, excessive arrays/rates, incompatible versions, unauthorized identity/epoch and out-of-sequence input reject before domain dispatch with safe bounded feedback and unchanged state. Tests cover the exact configured bound and the first invalid value, including missing limits and disabled families.

  2. AC 2

    Across the real dedicated/two-client connection, identical accepted/rejected action identities return their consistent prior outcome and count at most one dispatch/effect. Conflicting reuse, reordered input, stale reconnect identity and cross-client requests never create a second action or disclose another owner result. Native policy tests alone do not establish this routing behavior.

  3. AC 3

    The three canonical traffic classes are distinguishable in actual server/client observations with documented native delivery/freshness behavior. Stop/disconnect or a focused dropped/reordered-message case reaches the affected client visibly and permits a clean rejoin; loss cannot promote client data to authority or turn transport acknowledgment into durable success. Existing T01 failure observations may be reused where unchanged.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. Use the T01/T02 runbook and its /Engine/Maps/Entry connection scenario after T04 documents the exact request/traffic controls, configured limits and counted server observation. No connectivity/command suite exists in tools/validate.py today; implementation must document real supported commands.

Setup

  1. Complete T01–T03 and reuse their actual backend, trusted test identities, pinned executables and task-owned ports. Configure explicit SecurityPolicy byte/array/rate windows and bounded retry retention. The request controls and test-only counted dispatch/effect sink are not implemented yet.

Actions

  1. From each client submit one valid request, exact retries before/after its response, conflicting identity reuse and a request naming the other client. Compare redacted response identities and server dispatch/effect counts, then try stale credentials after logout/rejoin.
  2. Exercise delivered malformed, oversized, array, rate/window and sequence controls at the configured boundary and first invalid value; disable one endpoint by removing its limit or setting its request count to zero. Check authoritative state before/after and restore task-local settings.
  3. Observe each of movement_snapshots, combat_control_events and reliable_state_operations on the actual peers. Disconnect/stop the task-owned server or use one documented bounded message-impairment case where needed for delivery behavior; inspect client-visible failure and a clean rejoin. Reuse unchanged T01 lifecycle evidence.

Expected results

  1. Only valid owner requests dispatch; invalid cases leave game/test-effect state unchanged with safe client feedback. Retried identities never add an action/effect, conflicting/foreign attempts cannot replace or read the original result, all three traffic labels map to actual native behavior, and failures remain visible to the client.

Reset

  1. Stop only the task-owned server/clients, release their ports and remove only disposable scenario state beneath ignored artifacts/. Restore any task-local network emulation. Preserve existing assets, configuration, build directories, databases and prior evidence.

Completion evidence and blockers

Required evidence: One concise PR/result summary linking reused T01/T02/T03 evidence, executed boundary tests and affected compilation, actual two-client routing/count/traffic observations, configured limits and source/build/configuration identities. Record client-visible QA or connected execution not performed as Not Run — Manual QA Pending. Do not claim gameplay, Steam, persistence or capacity from test traffic.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
