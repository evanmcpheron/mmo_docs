Interface & accessibility

Mechanics, governing rules, edge cases and acceptance criteria.

Character creation

The screen should closely follow World of Warcraft’s character creation layout and flow: a prominent character preview, clear faction/race/class choices, appearance customization, naming and review before entering the world. The character creation and beginner-area feature flow describes each step and the level 1–10 experience that follows.

Choose faction, race and class as separate controls. A Human can choose either faction; its starting attributes remain identical. Selecting an incompatible faction clears the class selection only after an explanatory prompt. Show an explicit eligibility matrix rather than hiding an unavailable class without explanation. The server validates the final combination again.

Show racial offsets beside class-derived starting values and an optional level-60 preview. Explain that racial modifiers are fixed additions. Do not label races as the “best” for a class based on minor starting differences. Body size never changes the combat capsule, movement speed or selection priority.

Talent and specialization screens

The specialization screen must show the role, sustained resource, signature meter, three starting specialization abilities and two contrasting playstyle examples. Changing from High Priest to Oracle must visibly replace direct-recovery emphasis with prevention; changing talents within Oracle must show a smaller, focused change inside that identity.

Show class points and specialization points separately, including banked points. Every node shows cost, rank, prerequisites, learned-ability requirement, exclusive alternatives and affected abilities. A prospective allocation produces a before/after tooltip diff before confirmation. Highlight changed targeting, movement permissions, resource spending, summon limits and timing—not just damage percentages.

Keep the gameplay talent editor distinct from this documentation site. This ZIP supplies readable node tables and structured data; it does not pretend to contain a working in-game build editor. A game editor must run the same validation rules as the server and treat local validation only as a convenience.

Allow keyboard traversal, zoom independent of text size, search by ability/tag, undo in the uncommitted draft and reset by tree. Use labels and shapes as well as color. Clicking a mutually exclusive choice previews the removal of the other selection and all dependent consequences. Nothing partially applies during preview.

Combat display

Provide eight-direction sprite animation with continuous targeting geometry. An action button shows resource cost, cast duration, current cooldown, range failure, line-of-sight failure and incompatible-state failure. Rejected actions display a brief specific reason rather than a generic error sound.

Keep enemy danger telegraphs above friendly cosmetic effects. Use distinct patterns for hostile cones, persistent hazards, healing areas and selected targets. Player outlines, nameplate density and friendly VFX intensity are adjustable. Boss-critical telegraphs cannot be disabled by the general effect-quality setting.

A ground-targeted ability supports normal confirmation and optional quick-cast. Always offer a held-key preview and cancellation. Friendly frame targeting and self-cast modifiers prevent the need to click overlapping sprites. Target cycling orders candidates by relevance, distance and stable entity ID; repeated presses do not select hidden or ineligible enemies.

Pet classes receive attack, follow, hold and recall commands plus a visible shared capacity indicator. Bard shows maintained song slots and aggregate support strength. Ironbody shows delayed damage as debt separately from health and shields; it must not look like a free absorb.

Profession and market display

A recipe shows the intended character-level band, required skill, actual output, exact cost, material sources, deterministic yield and whether it still gives skill progress. An output that requires customer-owned bound material is clearly a commission, not a tradable ordinary listing.

Display available inventory separately from escrowed, listed and reserved amounts. Show why a stack cannot be used. Before crafting or accepting an order, preview output binding, grade, item budget and enhancements that recrafting would replace. Show the commission fee separately from material value and marketplace fees.

Filter by “useful at my level,” “craftable now,” “gives skill progress,” “available customer order” and “needs one material.” Do not make players inspect hundreds of obsolete recipes to find an appropriate item. Old recipes remain available for trading and collections without falsely appearing to scale to level 60.

Accessibility and input

Support remappable keys, independent UI scaling, readable fonts, reduced screen shake/flashes, non-color status labels, audio/subtitle alternatives and controller navigation where the platform is supported. Do not make the Bard a latency-sensitive rhythm minigame. Reaction windows must consider the target network conditions.

Animations and sound are feedback, not authoritative clocks. Cast progress follows server time with presentation smoothing. Never allow an inaccessible tiny sprite, obscure roof layer or low-contrast marker to be the only signal for a lethal attack.

Readiness tests

Test creation with both Human factions; talent editing entirely by keyboard; expensive craft confirmation; inventory-full delivery; 30-player visual clutter; small-window text reflow; and a healer targeting allies without clicking their world sprites. These are acceptance scenarios, not claims that the Godot UI already exists.

Data

Follow a type name to its canonical members, properties, constraints and review decisions. Definitions are generated from one shared registry.
