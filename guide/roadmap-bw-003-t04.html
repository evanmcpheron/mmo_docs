Complete · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-4

Implementation scope

  • Add --suite metrics to measure the same finite test probe. Collect monotonic elapsed processing duration for each actual probe tick, relevant probe-entity counts and current/peak depth of the queue actually consumed by that probe. Keep scheduling interval, processing duration, wall time and the existing bootstrap heartbeat distinct. Supply idle, active and queued-burst workloads with finite declared entity/client/step/tick bounds.
  • Use at least two logical recipient clients and count the exact UTF-8 serialized probe payload bytes produced per recipient over a declared measurement window. Preserve per-recipient totals and disclose the aggregation policy, direction, units, warm-up and sample/percentile calculation. Label these serialized payload bytes, with logical-client counts and no network transport; they are not wire traffic, RTT, protocol overhead or capacity evidence. Include zero-client and unequal-recipient controls without dividing by zero or inventing traffic.
  • Associate samples with T01 run provenance, T02 world/seed/context, workload identity/configuration, actual engine/build/content/rules identity, OS/CPU architecture and available hardware details. Report raw samples with derived summaries so tick durations, relevant entities, queue changes and byte totals can be independently recomputed; missing measurements are failures or explicitly unsupported observations, not fabricated zero successes.
  • Reuse ServerMetricRecord field meanings and its declared-window invariant when naming comparable measurements, while respecting its durable-service authority and required database fields. This local probe report is not a fabricated canonical ServerMetricRecord or NetworkLoadTestRecord: no database latency, subscriptions, settlement retries or real network load exists to certify. Keep canonical definitions unchanged, document this distinction in tools/README.md, and leave production metric persistence/wire instrumentation to the actual later owners.

Out of scope

  • BW-004 connectivity, real clients/sockets, bandwidth or latency guarantees, production telemetry/storage, database benchmarking and launch player-count targets.
  • Measuring the bootstrap timer as simulation cost, estimating wire bytes from payload bytes, or introducing a second production simulation/event queue solely for instrumentation.

Dependencies

Hard prerequisites: BW-003-T02

Acceptance criteria

  1. AC 1

    An actual bounded run captures raw finite nonnegative probe-tick processing durations, declared relevant probe-entity counts, per-logical-recipient serialized payload byte totals and the real probe queue depth, joined to its workload, context and environment.

  2. AC 2

    The active/burst workload produces attributable payloads for two logical recipients and a nonzero observed queue depth before drain; the idle/reset case returns to its declared empty/idle state. Per-recipient bytes match independent serialization, including an unequal-recipient case.

  3. AC 3

    Declared sample windows, units, counts, warm-up and summary/percentile policy allow raw-to-summary recomputation. Empty/zero-client workloads, malformed/nonfinite input and workload bounds are handled visibly with no divide-by-zero or invented sample.

  4. AC 4

    Reports label payload versus wire measurement, logical versus connected clients and probe versus production ticks/entities. They record no database/network result that was not measured and make no capacity claim.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root.
python3 tools/verify_toolchain.py
python3 tools/extract_content_contracts.py --check
python3 tools/check_runtime_fixtures.py --suite metrics
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use Python 3.10+ and the native macOS ARM64 Godot executable pinned in tools/toolchain.lock.json; the checker resolves that executable rather than assuming godot is on PATH. Keep sibling mmo_docs canonical sources available. No provider, database or network service is required.
  2. Use fixtures/runtime_fixtures/metrics.json, which pins the existing T02 context hash and declares 41 finite cases: idle, active, burst, reset, unequal recipients, zero clients, empty window/subscriptions, partial drain, future arrivals, limits and negative controls. No external traffic generator or manual server scene setup is required.

Actions

  1. Run the launch block and inspect run.json, actual-evidence.json, executed-fixtures.json and logs. Check per-case full workload/context hashes and environment/toolchain identities. One probe owner executes the ordered cases; idle-reset follows queued-burst.
  2. For each measured sample, recompute (finished_usec - started_usec) / 1000 and each payload_utf8 UTF-8 byte length. Sum bytes separately by recipient over measured samples. Sort measured durations and select ceil(p*n)-1 for p=.50/.95/.99; exclude declared idle warmup samples. Check FIFO before-enqueue/before-drain/after-drain depths and pending arrivals.
  3. Confirm queued-burst observes depth 6 before draining to 0, unequal-recipient totals differ, zero-client has an empty total map, and empty-window has no samples with null timing/queue summaries. Partial drain and future arrivals remain explicitly nonempty at their bounded stop.
  4. Run python3 tools/check_runtime_fixtures.py --suite metrics --control import-failure, then startup-failure, missing-report and assertion-failure as separate fresh-output invocations. Each exits nonzero; the first three lack complete executed assertions and assertion-failure records executed failed assertions. Rerun --suite metrics without a control and confirm a fresh passing run.
  5. Review the explicit serialized-payload/logical-client/probe-only policy and unsupported observations. The Python regressions mutate raw durations, queues, identities, bytes, summaries and unsupported fields to verify failure. Do not compare these local values to wire traffic or production capacity.

Expected results

  1. All 41 authored cases pass their expected positive/rejection checks in actual pinned Godot execution. Every raw tick, entity count, real FIFO transition and per-recipient UTF-8 byte total can be attributed and recomputed; malformed/nonfinite/bounded inputs never partially execute.
  2. Expected failure controls fail at their actual stage and clean recovery passes with a new run ID. Existing context/diagnostic behavior remains verified. Network/database/production observations remain explicitly unsupported.

Reset

  1. Let bounded child processes finish; the checker must stop any timed-out child and discard its disposable project. Probe state exists only in that process.
  2. Keep prior evidence directories intact and rerun with a fresh default output directory. Restore any deliberately modified fixture only in its disposable copy; do not edit canonical sources or reuse prior results as a new execution.

Completion evidence and blockers

Required evidence: Retain workload/context/configuration, environment/toolchain identity, raw measured samples, per-recipient payload-byte verification, recomputed summaries, negative controls and the explicit probe/payload-only limitation.

Blockers: None recorded; see dependencies.

  • 41 finite metric workloads/controls record actual processing times, probe entities, independently verified UTF-8 bytes per logical recipient and consumed FIFO depth. Six-command burst/drain/reset, unequal recipients, zero clients/empty windows, invalid/nonfinite/bounds and report-tampering checks pass. Native/exported smoke and client exclusion checks pass.
