Not Started · Parent epic: BW-010 · Cast commitment and ability timing

Epic acceptance criteria: BW-010-AC-1, BW-010-AC-4

Implementation scope

  • Reuse BW-004 command identity/outcome, BW-006 pools/reservations, BW-009 runtime targeting and FContentAdmission resolved definitions. Reuse the GAS fit decision from BW-006; engine timers may schedule checks but do not own commitment.
  • Establish one server cast owner for admitted enabled abilities. Validate learned/build/equipment/life/control/target/resource permissions, reserve once and start GCD only on legal acceptance. Register actual supported handler readiness through the existing admission owner; keep unimplemented behavior disabled.
  • Extend the existing native automation/report path with focused behavior and failure cases; retain exact engine/source/content/rules/configuration identities and actual assertions. Reuse FContentContracts and its canonical extractor/reference closure where these contracts cross a boundary; a schema does not require a separate UObject or new wire protocol. Do not duplicate admission, replay or domain rules in UI/transport.

Out of scope

  • Full roster, new ability framework, public account/build persistence and release/channel effect rules owned by later tickets.

Dependencies

Hard prerequisites: BW-009, BW-004-T03, BW-006-T02

Acceptance criteria

  1. AC 1

    Legal acceptance verifies every documented permission using current server state, creates one cast/root identity and reservation, and starts the documented GCD; rejection changes none of these.

  2. AC 2

    Stale build, late input, wrong ownership and duplicate/conflicting commands cannot accept another cast or spend/reserve again; prior outcome comes from the BW-004 owner.

  3. AC 3

    No free-text/unbound effect becomes enabled and no parallel handler/admission framework is added. Timers and client animation/prediction cannot commit the action.

Manual verification

This outcome is verified by executed headless native automation at the owning rule boundary. Its fixture setup, negative cases and teardown are part of the ticket; documentation checks alone do not verify it.

Completion evidence and blockers

Required evidence: Retain attributable executed positive/negative results for every ticket criterion, the actual build/launch/reset procedure, tested input identities and applicable focused regressions. Use the existing native automation harness with deterministic boundary fixtures; no manual UI proof is required. Report unexecuted prerequisites explicitly; documentation validation and engine API availability cannot satisfy runtime evidence.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
