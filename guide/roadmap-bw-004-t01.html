Implementation scope

  • Inspected 2026-10-23: game origin/main 92817f556aa326c57edec88bf18d97aadee7afc5 (same tree as checkout 21776e507f817245f23d104e5dfc55c28c43d055), docs base bf75815db6907203ce8c51cc9f74f41d8fb7d5a5. tools/toolchain.lock.json pins UE 5.8.3, Xcode 27A266a and Mac ARM64; native Game/Editor/Client/Server targets exist. BW-001 certifies bootstrap, BW-002 contracts/admission and BW-003 a local logical-recipient probe, not connected clients. Config/DefaultEngine.ini uses /Engine/Maps/Entry; the only project map is the camera-reference test map.
  • Use native dedicated networking, GameMode connection lifecycle, owned PlayerControllers and UEngine network/travel failure delegates. Implement one explicit local test route (native IP/direct or NULL) without a server local player or widget dependency. A small opt-in connection scenario on /Engine/Maps/Entry is justified by parent AC1; keep scenario controls separate from gameplay commands. Until T02 admits identity, connections cannot spawn an authorized gameplay character or dispatch gameplay commands.
  • Reuse the supplied UMultiplayerSessionsSubsystem if the selected route needs online sessions; do not add another session subsystem. Source inspection found unchecked local-player dereferences, create continuing after asynchronous destroy, unchecked join/address travel in UMenu and empty StartSession. Adapt only paths needed by the chosen route. Native IOnlineSession exposes hosting-user overloads and completion delegates, but API availability and existing plugin compilation prove neither dedicated nor Steam operation. Record actual backend/plugin activation; native direct connectivity need not repair unused Steam/menu paths.
  • Reuse tools/check_baseline.py process ownership/timeouts and the existing Unreal Automation harness for focused lifecycle rules. Compile affected targets only; document a bounded dedicated/two-client invocation and client-visible status control in the implementation runbook. No new map asset, package, capture framework, all-suite run or automatic editor execution is required.

Out of scope

  • Trusted identity/protocol admission (T02), command replay (T03), bounded gameplay command routing/traffic classes (T04), movement/combat rules, public account providers (BW-019) and Steam certification.
  • Full create/find/join/start/destroy coverage for unused backends, unrelated plugin/menu repair, production reconnect/transfer or economic ownership.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    Two separately running clients reach the same headless dedicated process on the recorded backend, with zero server local players and no menu/widget dependency. This establishes only the transport portion of parent AC1; distinct authorized sessions require T02.

  2. AC 2

    Unreachable server, disconnect, server shutdown and travel failure produce bounded, redacted client-visible failure states; a fresh connection succeeds after cleanup. When online-session APIs are used, the selected create/join/destroy path handles failure, replacement and callback teardown without unchecked travel or local-player access.

  3. AC 3

    The runbook identifies actual map/GameMode/Controller, executable/build revisions, backend and exact launch/status/reset controls. Executed unit/native and dedicated/two-client results are distinguished from authored expectations and unavailable Steam tests.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From GAME_ROOT (the checkout containing Briarwake.uproject), follow the implementation PR/runbook for the exact existing Development server/client executables, ports and launch options. /Engine/Maps/Entry is the current server/default map. The required native connection GameMode/Controller and scenario controls do not exist yet; their actual names, commands and cleanup must be documented before this procedure is executable. Do not use the listen-menu example or camera-reference map as dedicated connection evidence.

Setup

  1. Use the existing pinned Mac ARM64 toolchain and completed BW-001/BW-002 prerequisites. Build affected targets in place; launch one dedicated process and two separate clients using the documented local route and task-owned ports. No Steam account or public account provider is required for this restricted proof.
  2. Use the delivered connection status display/control and native lifecycle diagnostics. The current tools/smoke_server.py checks zero controllers/pawns and exits after three ticks, so it cannot drive this connected scenario; do not pass invented connectivity suite flags to tools/validate.py.

Actions

  1. Connect both clients to the same endpoint. Inspect distinct client process identities, the dedicated process and server local-player count; confirm no authorized gameplay character/command exists before T02.
  2. Disconnect one client, attempt an unreachable endpoint, stop the task-owned server and exercise the delivered travel-failure control. Observe each client status, then restart/reconnect using the same documented procedure. Exercise selected online-session failure/replacement only if that route uses it.

Expected results

  1. Both peers connect to one dedicated process with zero server local players. Failure reaches the affected client with a safe reason; no unchecked address is used and clean rejoin works. Log-only observations do not establish the client-visible failure criterion.

Reset

  1. Stop only the task-owned server/clients, release their ports and remove only disposable scenario state beneath ignored artifacts/. Restore any task-local network emulation. Preserve existing assets, configuration, build directories, databases and prior evidence.

Completion evidence and blockers

Required evidence: One concise implementation PR/result summary with affected compilation, focused lifecycle assertions and actual dedicated/two-client observations, backend and source/build/configuration identities. Missing peer execution or human observation remains Not Run; the existing three-tick smoke is not connection evidence.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
