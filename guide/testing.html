The included validation/run_checks.py uses the Python standard library. It reads the shipped JSON, evaluates the documented invariants, checks all local HTML links/anchors and writes its report. Run it from any directory with python validation/run_checks.py after extraction. Browser checks are recorded separately because they require a browser automation dependency. In this environment, file-URL and loopback navigation were blocked by administrator policy. Generated pages were therefore rendered directly into Chromium with the shipped CSS and JavaScript; search, filtering, disclosures and layouts were tested there. Link destinations were validated structurally. This does not claim successful file-URL navigation inside the restricted test browser.

A successful check means the specific invariant passed, not that the MMORPG is balanced or that an implementation exists. The talent capacity test constructs a valid allocation at every spendable level; it does not prove every possible route is equally viable or that every legal build is fun.

For the first complete player journey, use the beginner-area playtest goals: create a character, follow the required solo path to level 10, choose and practice a specialization, finish the final challenge and follow the departure prompt. Repeat for both factions and each class as it becomes playable.

Build-diversity playtests

Compare at least two builds in each tested specialization under equal level and gear budget. Record action selection, time stationary, resource peaks, casts canceled, target switching, healing distribution and cooldown timing. A build passes the playstyle test only if it changes at least two decision dimensions, while preserving its role's baseline viability.

Use a stationary target, movement encounter, interrupted cast sequence, spread-target encounter and short versus sustained fights. An output-only talent comparison on a stationary dummy cannot establish spatial or support value. Record decision changes separately from numerical strength.

For support attribution, use a deterministic ordered marginal accounting policy. Attribute each eligible modifier's incremental effective damage after caps and mitigation to its source; state the order and do not count the same damage twice. This is an explanatory metric, not proof that removing the support character would produce exactly that lost output in a different team rotation.

Profession relevance test

For every manufacturing profession and every band, a character entering that band must find at least one useful craft without grinding through all later bands. Measure time-to-first-useful-output against the proposed 30-minute target. Measure total material acquisition, not just station channel time.

Test a self-sufficient gatherer/crafter, a dedicated crafter buying supplies, a low-level professional fulfilling a high-level customer's bound-core commission, a returning player and a low-population faction market. Check both trade value and actual personal usefulness.

The same-level consumable must not be replaced immediately by a cheap previous-band item scaled from the consumer's maximum health. Higher-level tools cannot fabricate rare materials or bypass source eligibility. Skill progress, mastery and character XP remain distinct.

Transaction and recovery tests

Run these against the chosen real database and game service, not only an in-memory mock: double buy, simultaneous cancel/buy, disconnect after commit before response, duplicate outbox delivery, crafting-order lease expiry, full inventory, bank withdrawal race, salvage/recraft conflict, server restart with reservations, stale item versions and rollback during a content migration.

The invariant is conservation of authorized item/currency changes with durable, single-owner results. A message may be delivered more than once; idempotent processing must make repeated delivery harmless. Do not describe network delivery itself as “exactly once.”

Network and performance testing

Use realistic scripted movement, combat, pet commands, crafting and market activity—not clients that only connect and stand still. Test median and tail latency, packet loss, reordered snapshots, burst joins and departures, NPC density, maximum legal summon count, many overlapping effects and one unusually crowded market.

Report CPU tick percentiles, backlog, memory, bytes per client, subscriptions, pending transactions, failed content operations and recovery time. A 30 Hz design target is not a promise of players per realm. Start with explicit zone boundaries and measure before implementing seamless transfers.

Test evidence retained

The package includes the machine-readable validation report, progression allocation examples and a browser check record. Keep failed tests and unresolved binding counts visible. No fabricated benchmark, faction win rate, load capacity or measured development schedule is included.
