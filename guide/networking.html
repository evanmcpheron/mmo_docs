Godot & networking

Mechanics, governing rules, edge cases and acceptance criteria.

Practical initial architecture

Use Godot clients and authoritative headless Godot world/instance processes, with a conventional service and relational database for accounts, inventory, bazaar and durable progression. Keep backend responsibilities modular inside a small deployment before creating independent microservices.

Godot supports dedicated headless exports. Its high-level multiplayer APIs provide RPC and transfer-mode building blocks, and MultiplayerSynchronizer supports visibility filtering but does not synchronize arbitrary Resource/Object values. These capabilities do not themselves provide an MMO economy or seamless cross-server ownership. See Sources S2(sources.html#s2), Sources S3(sources.html#s3) and Sources S6(sources.html#s6).

Pin a tested Godot minor version and export-template version during implementation. Do not assume documentation marked “stable” remains unchanged after this reference's access date. No specific player-capacity claim is made here.

Each active character has one session ownership epoch. A stale process cannot continue granting rewards after a transfer. Class/faction/race access is checked from authoritative records, not from the character-selection UI.

Movement and traffic

Prototype simulation at 30 Hz, nearby movement snapshots at 10–20 Hz, lower-priority distant state at 2–5 Hz, and event-driven static objects. These are measurement starting points. Client rendering is independent. Map continuous planar/floor coordinates to 3D scene transforms locally; camera snapping, animation and cosmetic height do not change server position, aim or collision, and require no new network fields.

Send sequenced movement intent. The server simulates movement and acknowledges input sequence in snapshots. The local client predicts and reconciles; remote characters interpolate. Combat requests contain aim/target intent, not a position used to bypass server collision.

Use separate traffic channels for movement snapshots, combat/control events and reliable state operations. Frequent replaceable snapshots need not queue behind chat or an inventory acknowledgment. Reliable transport delivery is not durable transaction completion.

Area of interest and hidden information

Reviewed disclosure policy: Resource pools and reconnect state are owner-only. Public EntitySnapshot and NameplateState expose only currently authorized visible entities. Optional public status details require an explicit server allowlist; otherwise visible_statuses is empty. Authorization loss removes or redacts the projection.

CombatResult remains an internal record. PublicCombatResult carries only recipient-authorized outcome fields and a nullable source entity ID: damage from a hidden source can be shown to the affected owner with a null source. Raw damage/mitigation breakdowns, overkill and resource history are omitted. Hidden-source action/event correlation references are recipient-scoped and cannot be joined to private ledgers. A reconnect snapshot filters public visible entities independently of owner-private restored state.

Track nearby entities using a spatial grid and floor/instance identity. Add explicit interest for relevant projectiles and hazards whose effects can reach the player. Limit update frequency by relevance, not by silently removing a real boss hazard. Bound maximum nameplates, cosmetic effects and redundant pet updates separately from gameplay outcomes.

Do not replicate hidden enemy information merely because the client promises not to render it. Stealth, fog/visibility rules, target markers and pet tracking require server filtering. Camera zoom cannot increase authoritative combat visibility beyond the agreed information envelope.

Clients receive spawn/despawn plus relevant effect snapshots when entering interest. Missing an old buff event cannot leave a newly visible player permanently unbuffed in the UI. Use revisions and periodic authoritative reconciliation for health and status state.

Latency policy

Start with server-current-state validation, client prediction and modest input buffering. Do not add unrestricted rewind compensation to all spells. Directional hazards and movement must remain consistent with what the server can defend fairly. A later bounded historical-hit policy must document its maximum rewind, eligible attack categories and interaction with cover.

Test 0, 50, 100, 150 and 250 ms round-trip latency, jitter and 1–5% packet loss. At 250 ms, the goal is understandable failure and recovery, not a promise of identical competitive performance. Cast rejection needs a clear reason, not silent input loss.

Durable operations

Persist experience/level awards, talents, skill progress, inventory, recipes, currency and trading orders. Avoid a database write for every movement tick or periodic damage tick. Group small character-progress checkpoints, but commit economic ownership changes transactionally and acknowledge only durable results.

Use per-operation idempotency keys, item versions, ownership checks and a transactional outbox. A combat crash cannot cause the same kill reward to mint items twice. Reward identity includes encounter/creature generation and eligible recipient, not just a client request ID.

Zone or instance transfer

Begin with explicit transitions. Suspend new actions; settle or reject pending economic operations; checkpoint character state and cooldowns; issue a one-use transfer token with a new ownership epoch; let the destination claim it; revoke source authority; provide a full destination snapshot. A failed transfer returns to a known authoritative location without duplicating the character or inventory.

Pet capacity, damage debt, active long cooldowns and profession jobs must follow an explicit transfer policy. Never reconstruct a pet from a snapshot while leaving the original authoritative pet running elsewhere.

Disconnect and recovery

Keep an in-combat disconnected character present for a short configured grace period, initially 20 seconds, under simple server defensive behavior rather than invulnerability. Stop issuing new attacks or pet orders. A reconnect claims the existing character through a new session token and receives a snapshot. A second connection cannot operate the same character concurrently.

Clean logout requires out-of-combat state or a logout countdown. Disconnecting cannot clear control, reset a boss, erase stagger debt or cancel an already committed trade. An unclean world-process crash uses a documented recovery point and encounter reset policy; do not claim perfect combat durability without a replay architecture.

Security and observability

Vendor-neutral security contract: A configured trusted authentication adapter issues scoped opaque one-use login/recovery proof. The game service verifies that proof before spawning an economic character and returns revocable opaque session handles; clients do not parse claims or choose signing algorithms. Reauthentication/recovery revokes old credentials and owner epochs. Transfer proof is bound to the exact character, checkpoint, epochs and destination with an explicit server expiry and atomic one-use consumption.

SecurityPolicy requires positive lifetime/retention settings and explicit per-request rate, payload and array limits; missing configuration disables the endpoint. Provider, database and deployment values are selected during future implementation. No credentials, provider connection or deployment is part of this documentation phase.

Boundary representation: Previously symbolic enum members use their exact case-sensitive snake_case IDs; existing serialized values remain unchanged. New movement, party, guild and token boundary objects have explicit versioned discriminators. Unknown tokens and fields are rejected. Instant uses RFC 3339 UTC with Z or +00:00; durations remain seconds. IDs are opaque strings in contract-specific namespaces and never prove authorization. Breaking changes require a new discriminator and migration; compatible additions require a new package version and negotiated capability. Epochs and sequences must never wrap or be reused.

Authenticate before spawning an economic character. Validate payload size, IDs, permission, action rate and sequence. Encrypt account/service traffic with standard transport security. Do not put account secrets or authoritative drop tables into client-facing logs. Add audit trails for admin inventory edits and progression grants.

Monitor tick duration, relevant entity counts, bytes per client, event queue depth, database latency, rejected commands, duplicate requests and settlement retries. Load-test crowded bazaars, world bosses and four-summon classes. A low-resolution 3D presentation does not establish server capacity; measure simulation and client rendering costs separately.
