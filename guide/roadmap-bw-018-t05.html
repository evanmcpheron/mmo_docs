Not Started · Parent epic: BW-018 · Durable ownership and mutation recovery probe

Epic acceptance criteria: BW-018-AC-4

Implementation scope

  • Add one explicit supported SQLite storage-schema migration to the existing T01 owner, using an actual old-layout fixture file produced by the prior implementation and a declared new internal layout. Validate the current schema version before writes and migrate transactionally under exclusive migration ownership. Preserve the stable canonical meaning/field encodings; content_version, rules_version and database schema revision remain distinct. Do not relabel a snapshot or alter canonical definitions to make a migration test pass.
  • Preserve item/owner/container IDs and revisions, wallet balances and append-only ledger history, current process/epoch fences, operation scopes/request identities/terminal receipts and pending/delivered outbox plus test-recipient dedup state. A pre-migration exact key must still return the same result afterward; stale authority must remain fenced and an undelivered notification must remain recoverable without repeating settlement. Include typed/null and exact-integer boundaries used by the probe.
  • Document the migration preflight and rollback/reconciliation procedure for this local probe; unknown/future schemas and incompatible data reject before mutation. A controlled failure inside the migration transaction must roll back to the usable old layout with all economic state intact, rather than restoring currency independently of item ownership. Reopening the migrated file or rerunning the same supported migration is safe and does not apply it twice.
  • Use existing canonical compatibility/value checks and the focused SQLite harness for positive migration and one mid-migration failure; reuse prior concurrency/crash results for unchanged responsibilities. ContentMigrationRecord describes content migration and is not a database-schema success receipt. Keep storage migration metadata internal; production backups, deployment rollback and full gameplay migration remain their own work.

Out of scope

  • Content/talent rebalancing migrations, new canonical wire contracts, production backup/restore, cross-provider migration, all-feature migration coverage and a parent completion audit.

Dependencies

Hard prerequisites: BW-018-T04

Acceptance criteria

  1. AC 1

    An actual old-layout SQLite fixture migrates and reopens under the declared new schema revision with identical stable identities, quantities, balances, receipt results, ledger history, owner fences and pending/delivered notification identities; canonical value compatibility is preserved.

  2. AC 2

    A pre-migration exact retry returns the same terminal receipt, stale-epoch mutation still rejects, and pending outbox recovery retains one economic mutation and one durable recipient effect.

  3. AC 3

    Unknown/future versions, incompatible values and a controlled mid-migration failure leave the old database usable with original economic rows and schema intact. Reopening/repeating a completed migration changes no identities or results; the runbook declares its actual preflight and rollback/reconciliation limits.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From the existing game workspace containing Briarwake.uproject, use the bounded native SQLite probe commands documented by BW-018-T01 after implementation. No SQLite probe command exists at planning time; implementation must record the actual executable, exact suite/phase arguments, pinned build and task-owned database path before handoff. This is data-only work: no map, player controls or visual assets are required.

Setup

  1. Use only a fresh task-owned SQLite database and outputs beneath ignored game artifacts/. Preserve all existing project files, databases and historical evidence; no shared or production data. The selected candidate is local SQLite, explicitly chosen by the owner on 2026-10-23.
  2. Complete T04 and retain its real old-schema fixture with a committed receipt, current epoch and pending notification. Implementation must provide the exact migrate/preflight/failure/reopen commands and rollback/reconciliation procedure.

Actions

  1. Inspect the old file, run the supported migration and reopen. Compare IDs/revisions/ledger totals, replay the original key, attempt a stale-epoch mutation and resume the pending notification.
  2. In a separate fresh old-schema scenario trigger the documented mid-migration failure; verify rollback. Attempt an unsupported future schema, then reopen/reinvoke the completed supported migration.

Expected results

  1. Migration preserves fixture identity and all economic invariants. Retry/delivery remain idempotent, old epochs stay fenced, failed/unsupported migration preserves the old usable state and completed migration does not run twice.

Reset

  1. Close owned connections and let bounded child processes exit. For a new baseline use a fresh task-owned directory; for a recovery/retry case reopen the same scenario database without reseeding it. Preserve prior outputs and unrelated staged work; never reset the checkout or remove database sidecars while a connection is active.

Completion evidence and blockers

Required evidence: Actual old/new file-backed migration, reopen/retry/fencing/pending-outbox and rollback assertions with separate content/rules/database revision identities. Compile affected native code and retain one short result summary; gameplay, operational restore and missing manual replay remain unverified.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
