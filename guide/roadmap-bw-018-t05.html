Complete · Parent epic: BW-018 · Durable ownership and mutation recovery probe

Epic acceptance criteria: BW-018-AC-4

Implementation scope

  • Add one explicit supported SQLite storage-schema migration to the existing T01 owner, using an actual old-layout fixture file produced by the prior implementation and a declared new internal layout. Validate the current schema version before writes and migrate transactionally under exclusive migration ownership. Preserve the stable canonical meaning/field encodings; content_version, rules_version and database schema revision remain distinct. Do not relabel a snapshot or alter canonical definitions to make a migration test pass.
  • Preserve item/owner/container IDs and revisions, wallet balances and append-only ledger history, current process/epoch fences, operation scopes/request identities/terminal receipts and pending/delivered outbox plus test-recipient dedup state. A pre-migration exact key must still return the same result afterward; stale authority must remain fenced and an undelivered notification must remain recoverable without repeating settlement. Include typed/null and exact-integer boundaries used by the probe.
  • Document the migration preflight and rollback/reconciliation procedure for this local probe; unknown/future schemas and incompatible data reject before mutation. A controlled failure inside the migration transaction must roll back to the usable old layout with all economic state intact, rather than restoring currency independently of item ownership. Reopening the migrated file or rerunning the same supported migration is safe and does not apply it twice.
  • Use existing canonical compatibility/value checks and the focused SQLite harness for positive migration and one mid-migration failure; reuse prior concurrency/crash results for unchanged responsibilities. ContentMigrationRecord describes content migration and is not a database-schema success receipt. Keep storage migration metadata internal; production backups, deployment rollback and full gameplay migration remain their own work.

Out of scope

  • Content/talent rebalancing migrations, new canonical wire contracts, production backup/restore, cross-provider migration, all-feature migration coverage and a parent completion audit.

Dependencies

Hard prerequisites: BW-018-T04

Acceptance criteria

  1. AC 1

    An actual old-layout SQLite fixture migrates and reopens under the declared new schema revision with identical stable identities, quantities, balances, receipt results, ledger history, owner fences and pending/delivered notification identities; canonical value compatibility is preserved.

  2. AC 2

    A pre-migration exact retry returns the same terminal receipt, stale-epoch mutation still rejects, and pending outbox recovery retains one economic mutation and one durable recipient effect.

  3. AC 3

    Unknown/future versions, incompatible values and a controlled mid-migration failure leave the old database usable with original economic rows and schema intact. Reopening/repeating a completed migration changes no identities or results; the runbook declares its actual preflight and rollback/reconciliation limits.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Optional replay — supplemental manual QA explicitly waived by the user for this ticket; no human execution is claimed. From the existing game root with native inputs at 21776e507f817245f23d104e5dfc55c28c43d055, run python3 tools/check_content_admission.py --suite migration --timeout 300 --output artifacts/bw-018-t05-replay using a fresh output directory. Exact preflight/migrate/failure/reopen checks, fixture provenance and rollback/reconciliation limits: https://github.com/evanmcpheron/BriarwakeUnreal/blob/21776e507f817245f23d104e5dfc55c28c43d055/docs/sqlite-migration.md. No map, player controls, running editor, database service or MCP action is required.

Setup

  1. Use the existing game and canonical mmo_docs checkouts with pinned macOS ARM64 UE 5.8.3 Editor/source-Server, Xcode build 27A266a and SQLite 3.54.0/unix VFS. The Editor and Server targets compiled/linked at the recorded native source identity. T04 is Complete with retained actual crash/reopen evidence.
  2. The migration suite copies the two immutable 86,016-byte schema-4 files under fixtures/persistence/schema4 into a fresh task-owned native/migration directory below ignored artifacts/. They are verbatim prior-implementation T04 outputs, including a pending zero-amount receipt/max-exact balance and a delivered 25-unit receipt/durable inbox effect. Preserve all originals, historical evidence, unrelated files and active SQLite sidecars.

Actions

  1. Run the exact migration command. The guarded Briarwake.Persistence.Migration.Schema test validates the real schema-4 files, rejects implicit ordinary opens, explicitly migrates 4 to 5 under BEGIN EXCLUSIVE and reopens. Compare every typed row, original receipt, process/epoch, content/rules identity and pending/delivered notification identity; replay the original key and attempt a new reverse transfer with a stale epoch and current asset revisions.
  2. Resume pending delivery, reopen the independent recipient and repeat acceptance against its durable dedup row. Require one effect and unchanged economic/receipt/ledger rows. Reinvoke completed migration and require unchanged database bytes.
  3. The same command denies dropping the renamed original inbox after copying its rows, then verifies whole-transaction rollback, original schema-4 file bytes/rows, usable old reads and successful retry. It also holds a real independent read lock to reject exclusive migration before releasing it, and checks unknown/future versions plus incompatible integer/canonical/inbox/layout/metadata inputs without further mutation.

Expected results

  1. Exit 0 and all 60 migration assertions pass in run.json/native/migration.json. Schema 5 changes probe_inbox to STRICT WITHOUT ROWID; the other six tables and all canonical meanings/encodings remain intact. NULL reservation, 9007199254740991 balance and revisions above 32 bits survive; stale epochs remain fenced, retries retain original results and recovery produces one recipient effect without another settlement.
  2. Unsupported/incompatible inputs remain rejected and unchanged; a controlled migration failure restores the complete usable old layout rather than independently restoring currency. A missing report, failed assertion, partial state, changed identity, duplicate effect or unexpected mutation fails verification. The separate existing storage suite currently has a failed combined lock-contention assertion: observed waits 2.423s and 2.421s exceed its unchanged 2s bound. No storage-suite pass or human test pass is claimed; all ticket-specific migration assertions passed.

Reset

  1. Let owned processes exit and connections close. Use a fresh task-owned directory for another baseline; never reseed a recovery file, relabel user_version, restore wallet rows independently or remove active journals. Preserve original fixtures and historical evidence. There is no supported schema-5-to-4 downgrade or production backup/deployment rollback procedure; retain findings and reconcile the entire file on an indeterminate outcome.

Completion evidence and blockers

Compile affected native code and retain one short result summary; gameplay, operational restore and missing manual replay remain unverified.
