Complete · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-3

Implementation scope

  • Emit diagnostics at the T02 authoritative probe decision/commit owner and correlate them through the existing T01 evidence writer. Use a single origin for run/scenario/action IDs, sequence/tick/time, build/engine/content/rules revisions and the fixture owner epoch. There is no production command/diagnostic owner to extend yet; keep the new owner within this bounded test path.
  • Include explicit rejected, committed and duplicate/retry observations with no fabricated commit on rejection. Correlate a synthetic non-economic queued action to its one committed effect; reuse FixtureAssertion idempotency with null receipt ID where applicable and TestCheck for diagnostic assertions. Do not issue CommandResponse or SessionOwnershipRecord payloads that pretend the production systems exist; preserve their documented authority boundaries.
  • Use an allowlisted shareable diagnostic projection. Add synthetic secret/private-state sentinels and hostile/oversized text in rejected input; ensure serialized reports, native logs, stdout/stderr and shareable samples do not disclose them. Bound field lengths/record volume and report overflow observably. Add a diagnostics suite and missing-correlation/redaction negative controls; preserve raw private execution details only when safe and required, never log arbitrary input blobs.
  • Reuse the context probe and T01 output/evidence owner for this local diagnostic experiment. Production BW-004 command admission and BW-010 cast commitment remain separate consumers of the documented correlation policy; do not promote this test-only probe into a parallel gameplay authority or logging framework.

Out of scope

  • Production log transport, retention dashboards, authentication/session infrastructure, economic audit trails or private gameplay data modeling.
  • Changing canonical command outcomes, rejection enums or world ownership contracts for a diagnostic probe.

Dependencies

Hard prerequisites: BW-003-T02

Acceptance criteria

  1. AC 1

    An accepted probe action has one attributable commit and matching correlation IDs/revisions; a rejected action reports a reason without mutation; a retried synthetic action has one committed effect. Distinct owner epochs/runs cannot silently join each other.

  2. AC 2

    The shareable sample connects every observation to its actual run, action and build/content/rules/owner context. Missing/foreign correlation fields or a forged commit make verification fail.

  3. AC 3

    Synthetic credentials, hidden identifiers and private input sentinels are absent from all retained/shareable output surfaces. Malformed or oversized text and output overflow produce bounded safe diagnostics; a planted leak is detected by the redaction control.

Preserve previous evidence and build directories; do not create project copies, remove caches or resave assets.
  2. Use tools/toolchain.lock.json: UE 5.8.3 installed CL 58210709, pinned patched source commit 396c9f059903aed5fec78ecd3d437a40c6415368 for Server, Xcode 27A266a and macOS ARM64 Development. The runner verifies toolchain, snapshot, source/module identity and fresh output paths before executing UnrealEditor-Cmd with NullRHI and Briarwake.RuntimeFixtures.Diagnostics. No interactive editor/MCP bridge is needed.
  3. FRuntimeFixtureContext remains the only finite test queue/decision/commit owner. FRuntimeFixtureEvidence allocates runner/scenario provenance through the existing writer. FContentRevisions consumes content/rules revisions from fixtures/config/server.valid.json; fixtures/runtime/context.json owns the canonical empty FixtureWorldContext. The snapshot adds FixtureAssertion and its six-definition closure addition without changing the 92 prior definitions or sample bindings.   4. The probe uses transient UWorlds under WITH_EDITOR && WITH_DEV_AUTOMATION_TESTS. Correlation strings have a 128-character ASCII identifier bound; derived action IDs are bounded by those inputs. At most 32 steps, four queued effects, 60 fixture seconds and 12 diagnostic records per reset are supported. The output scanner limits each file to 16 MiB and the complete scan to 64 MiB. These are test-path bounds, not production admission policy.

Actions

  1. Execute the clean suite in a fresh default artifacts directory. Inspect native/fixture-diagnostics.json, automation/index.json, engine.log, combined child stdout/stderr process.log, shareable-sample.json and run.json. Verify the exact 44 native assertions and 41 wrapper mutation checks; run.json binds source, module, inputs and actual environment.
  2. Trace first and next-epoch scenarios. Each queues action 0, retries before and after the one-second commitment, and rejects secret/private input, oversized and hostile text, unknown action references and foreign run/owner-epoch retries. The verifier checks every ordered decision, safe rejection reason, exact correlation projection and one committed effect. Scenario IDs remain distinct even for the overflow execution in the original epoch.
  3. Inspect the 32-rejection overflow case: exactly 12 diagnostic records, 20 visibly dropped records, no committed effect or queued work, and further input rejected without state change. Inspect missing/invalid correlation and canonical idempotency field checks, including required nullable receipt, negative count, wrong type and unknown field.
  4. Run each of the four control commands. Each executes successful native automation, then corrupts only an in-memory copy of its actual output. Missing/foreign context and a forged commit fail verification. The planted synthetic leak fails the scanner in memory and is never written into retained artifacts. Expect nonzero wrapper exit, status Failed, native assertion_result Passed and control_verified true; missing tools or an unrelated failure cannot satisfy a control.
  5. Run a fresh clean recovery and default game FULL. Compare deterministic effects across independent runner nonces; inspect exact child controls, old fixture/prerequisite regressions, normal Game/source-Server builds/packages/startup and binary/package exclusion. All retained output, including wrapper stage logs, must pass the sentinel audit.

Expected results

  1. Clean diagnostic execution and recovery pass with exact run/scenario/action/source/engine/content/rules/world/owner attribution. Rejection produces no effect; retry has exactly one committed non-economic effect with null receipt. Missing or foreign fields, fabricated commits, duplicate effects and mixed scenarios fail verification.
  2. Synthetic credential, hidden-ID and private-input sentinels remain absent from all retained/shareable outputs. Hostile/oversized rejection and diagnostic overflow remain bounded and observable. Negative controls fail for their intended reason and clean recovery passes. No production networking, persistence, economic authority, metrics or capacity certification is implied.

Reset

  1. Allow the runner to destroy/GC its transient UWorld and release test-owned queue, clock, random and diagnostic state. Any timed-out child process is terminated by the existing owned-process wrapper; retain timeout as failed/unverified rather than claiming assertions passed.
  2. Rerun into a new default artifacts directory or a fresh --output under GAME_ROOT/artifacts. Previous output paths are rejected. Controls change only in-memory output copies; never overwrite evidence or modify canonical sources, maps, assets, plugins or normal launch settings to reset a run.
