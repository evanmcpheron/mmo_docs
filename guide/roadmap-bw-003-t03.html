Complete · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-3

Implementation scope

  • Add --suite diagnostics and action-correlated events at the same test probe owner and existing command-reader rejection boundary. Reuse trusted SessionContext, canonical CommandContext identity (session_epoch plus command_sequence), opaque action IDs and nonnegative revisions; add no second gameplay state owner. Name the disposable probe owner/build explicitly so a trace cannot be mistaken for a live character or economic ledger.
  • Record rejected command identity/reason and state before/after, and record a committed probe action only after its owner mutates the probe counter/revision. Link run/scenario identity, actual build/source identity, content/rules versions, test owner identity/epoch and resulting probe revision. Preserve identity across the bounded repeated-input case without turning this test-only behavior into production command admission.
  • Use an explicit diagnostic field allowlist and bounded safe findings; never dump raw commands, configuration, private results or arbitrary exception text. There is no canonical general operational diagnostic envelope: keep this narrowly local, reuse Id/Version/CommandContext and existing finding vocabulary, and do not repurpose CombatLogRecord, CommandResponse acceptance or OperationReceipt to claim combat/durable success.
  • Include valid commit, rejected malformed/stale/control-injected command and repeat cases plus recognizable synthetic credential/token/private-state/hidden-owner sentinels in both successful and failure inputs. Validate serialized logs and the retained shareable sample for redaction while preserving safe action correlation. Reuse content/combat_result_projection.gd for any public combat-result sample; private diagnostic identities must never be copied into recipient-facing projections.

Out of scope

  • Production combat/economy execution, durable receipts/audit storage, full admin/security operations, hosting dashboards and log retention infrastructure.
  • Claiming reader acceptance or a transport ACK is a commit, inventing a new canonical log schema, or exposing private action/owner linkage to a logical recipient.

Dependencies

Hard prerequisites: BW-003-T02

Acceptance criteria

  1. AC 1

    A selected rejected boundary command and committed probe action can each be traced from scenario/run and command identity to the exact build/content/rules and trusted owner epoch/revision. Rejection leaves the probe revision unchanged; a commit event follows the actual mutation and reports its new revision.

  2. AC 2

    Repeated probe input has stable correlation and the expected unique probe-effect count; no rejection, startup failure or missing report can create a fabricated committed action.

  3. AC 3

    Raw and shareable diagnostic output contain none of the synthetic passwords, bearer/recovery tokens, private-result sentinels or unauthorized hidden identifiers, including on malformed-input/failure paths. Safe identity/reason information remains sufficient to attribute the event.

  4. AC 4

    Canonical identifier types, CommandContext ordering fields and existing command encodings remain compatible. Diagnostics remain internal test evidence; any public projection retains the existing recipient entitlement/redaction behavior.

Setup

  1. Use Python 3.10+ and the native macOS ARM64 Godot executable pinned in tools/toolchain.lock.json. The checker resolves/verifies the executable; use --engine /absolute/path/to/Godot for another verified installation. Keep sibling mmo_docs canonical sources available.
  2. The implemented fixtures/runtime_fixtures/diagnostics.json supplies 40 bounded scenarios, two trusted synthetic owners/epochs and recognizable credential/token/private-result/hidden-owner sentinels. The same disposable context probe owns all mutations. Four explicitly constructed public-result samples reuse content/combat_result_projection.gd and the existing boundary corpus.

Actions

  1. Run the launch block. Open the printed fresh output directory and follow mixed-1/mixed-2 in run.json, logs/diagnostics.log, actual-evidence.json and shareable-sample.json. Join run/scenario/source identity, command ordering pair, safe owner alias/epoch and before/after revisions.
  2. Verify committed/rejected/repeated transitions: mixed scenarios have revisions 1,1,1,1,2, and the repeat keeps the first action ID. Stale command epochs differ from the trusted owner epoch; malformed ordering pairs are null and remain attributable by scenario/attempt. Confirm at most eight bounded findings with the full finding count.
  3. Run python3 tools/check_runtime_fixtures.py --suite diagnostics --control import-failure, then repeat with startup-failure, missing-report and assertion-failure. Each must exit nonzero. The first three create no actual-evidence.json or shareable-sample.json; assertion-failure retains a failed report and only actual probe effects. Run a fresh clean command to restore a passing execution.
  4. Check redaction_verified in every run.json; it scans all retained output including nested raw logs against all supplied private sentinels. Secret-bearing execution inputs are hashed and discarded with the temporary project rather than retained as diagnostics.
  5. Compare the constructed public projection samples: hidden source is null with recipient-specific action/event IDs, revoked entitlement and hidden targets yield no event, and public output contains no probe owner/action linkage or private result breakdown.

Expected results

  1. The actual diagnostic suite passes all 40 scenarios and four constructed projection checks. Every commit follows an actual probe mutation, each rejection preserves revision, and a repeated command preserves correlation without another effect.
  2. No synthetic password, bearer/recovery token, private result or unauthorized hidden identifier occurs in retained raw/shareable diagnostics, including unknown private field names and malformed startup input. Existing ability_command_v2/CommandContext encodings and recipient filtering remain compatible. This is internal probe evidence, not combat, durable receipts, connected clients or production capacity.

Reset

  1. Let bounded child processes finish; the checker terminates timed-out children and removes their disposable project. Counter/revision and diagnostics exist only in that process. No database, network or persistent character state needs reset.
  2. Keep previous output directories intact. Rerun with a fresh default directory or an unused --output path. Do not alter canonical sources or authored corpus expectations; negative controls modify only a temporary project.

Completion evidence and blockers

Required evidence: Retain actual correlated rejected/committed/repeated probe traces, source/context hashes, state/revision assertions, redaction checks and a shareable sanitized sample. Record the probe-only boundary and any constructed public projection separately from real gameplay.

Blockers: None recorded; see dependencies.
