In Progress · Parent epic: BW-095 · Versioned content authoring and import workflow

Epic acceptance criteria: BW-095-AC-1, BW-095-AC-2, BW-095-AC-3

Implementation scope

  • Extend the T01 offline export owner to produce byte-reproducible candidate data and a small reviewable fixture index from the same reviewed source, explicit dependency/policy inputs and canonical snapshot. Cover all eight declared families plus world/tutorial relationships delivered by T02–T05. Sort only semantically unordered maps/record sets; preserve ordered operations, phases, tutorial stages and other meaningful arrays. Keep build/run timestamps outside deterministic artifacts and preserve separate content/rules/database revision domains.
  • The manifest is tooling metadata listing source/package identity, schema identity, family/record IDs and canonical fixture IDs/revisions/content digests, not another gameplay authority. ContentPackageManifest is the existing documentation-count record and must not be repurposed as a runtime package or fixture schema. Reuse ContentValidationFixture, FixtureRunEvidence, ContentValidationResult and existing BW-003 evidence ownership; authoring produces unexecuted specifications with null runner/completion fields. Actual admission assertions remain separate results.
  • Validate required binding/presentation references, admitting VisualPresentationDefinition/TelegraphDefinition catalog data only as needed and resolving external render resources through explicit reviewed dependencies. Missing required references reject; legal unbound records may remain stored but disabled. Provide documented client-safe and server-only exports using the same canonical records and explicit ownership/projection rules: server loot/encounter scheduling, credentials, private policy and execution receipts never reach client output. A shared public artifact may be reused; no live network or new wire protocol is needed.
  • Use focused deterministic export/projection tests and actual native admission of the full representative server candidate. Two fresh offline exports from identical inputs must have identical package/manifest bytes and IDs; tampered dependencies, stale schema/versions, forged authored passed evidence and client-private contamination reject. Reuse existing readiness/evidence validators; do not add production handlers, fake receipts or a new fixture framework.

Out of scope

  • Connected client/server deployment, cooked packages, new runtime evidence producers, fixture gameplay execution, full art packaging and production content readiness.

Dependencies

Hard prerequisites: BW-095-T02, BW-095-T03, BW-095-T04, BW-095-T05

Acceptance criteria

  1. AC 1

    Identical reviewed inputs produce byte-identical packages and fixture manifests in two fresh offline outputs, independent of record/map input order where semantically unordered; stable IDs/revisions and meaningful sequence order survive reimport. Every declared family is represented and the full server candidate passes actual native admission.

  2. AC 2

    Client/server outputs follow explicit projection rules with no private loot/scheduling/policy/credential/evidence leakage. Missing or incompatible binding/presentation/schema/dependency references return actionable findings rather than fabricated defaults or partial output.

  3. AC 3

    Exported fixture specifications remain unexecuted with null runner/time. Authoring cannot promote runtime tests, manufacture readiness receipts or activate unbound content; actual admission results are separately attributable to their executed checks.
