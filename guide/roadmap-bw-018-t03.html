Not Started · Parent epic: BW-018 · Durable ownership and mutation recovery probe

Epic acceptance criteria: BW-018-AC-2, BW-018-AC-4

Implementation scope

  • Keep all mutation authorization, optimistic version comparisons, scoped operation-key uniqueness and ownership-epoch fencing inside the same native SQLite transaction owner from T02. Use durable conditional updates/constraints rather than only an in-process mutex or a preflight SELECT. Serialize requests through the database across independent connections; classify a bounded SQLITE_BUSY/lock outcome explicitly and never treat it as an accepted mutation.
  • Scope idempotency to the authenticated actor and operation. Persist a canonical identity of the validated semantic request with the terminal receipt; exact retry returns the original receipt/result without revalidating already-consumed expected versions as a new mutation. Reusing that key with changed item, destination, amount or other operation semantics rejects without altering the original receipt. Identical key text in another actor/operation scope cannot read or reuse a private receipt. Receipt lookup/replay does not itself authorize a new economic write.
  • Persist SessionOwnershipRecord/SessionAuthority compare-and-claim state. Check the caller’s trusted process/epoch against the current row at mutation commit, fencing stale writers after claim/revocation. Only one claimant may advance a given epoch; stale, reused, wrapped or unrepresentable epochs/revisions reject without new asset effects. This storage fence does not implement login, session proofs or zone transfer. Existing FRuntimeFixtureContext foreign-epoch/AcceptedActions checks are test-memory behavior and must not be used as durability evidence.
  • Use a bounded real race with independently opened SQLite connections and a barrier at the conflicting write, not sequential calls labeled concurrent. Cover competing stale-revision mutations, simultaneous identical retries, conflicting key reuse and a claim-versus-stale-writer interleaving. Verify persisted rows/receipt/ledger/outbox counts after both participants finish and after reopen. Add pure/unit cases only for distinct request-identity/range rejection responsibilities, through the actual owner.

Out of scope

  • Steam or network admission, authentication providers, distributed leases, multi-shard consensus, production session lifecycle, respec/combat authority and load/capacity benchmarks.

Dependencies

Hard prerequisites: BW-018-T02

Acceptance criteria

  1. AC 1

    Concurrent conflicting requests with the same expected asset revisions commit at most one mutation; the loser receives explicit stale/lock findings and persisted assets, ledger and outbox remain conserved. A bounded lock wait cannot silently succeed or hang the runner.

  2. AC 2

    Exact sequential, simultaneous and post-reopen retries return the recorded receipt and result with no second debit, item move, revision advance or outbox entry. Changed semantic payload under the same scoped key rejects; another actor/operation scope gains no access to that result.

  3. AC 3

    After a durable ownership claim advances the epoch, a stale process/epoch cannot commit any new asset change, even if it passed earlier validation. A real claim/write race produces a serializable valid outcome with one current authority; epoch/revision exhaustion cannot wrap or reuse a fence.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From the existing game workspace containing Briarwake.uproject, use the bounded native SQLite probe commands documented by BW-018-T01 after implementation. No SQLite probe command exists at planning time; implementation must record the actual executable, exact suite/phase arguments, pinned build and task-owned database path before handoff. This is data-only work: no map, player controls or visual assets are required.

Setup

  1. Use only a fresh task-owned SQLite database and outputs beneath ignored game artifacts/. Preserve all existing project files, databases and historical evidence; no shared or production data. The selected candidate is local SQLite, explicitly chosen by the owner on 2026-10-23.
  2. Complete T02 and use the delivered deterministic race entry point, barrier/timeout and task-owned file. A second real SQLite connection and recorded native VFS are required.

Actions

  1. Run the documented two-participant stale-revision race, identical-key retry race and changed-payload key conflict. Inspect both outcomes and persisted receipt/ledger/outbox counts.
  2. Advance the fixture authority epoch, attempt a mutation with the old context, then run the documented claim-versus-write race. Reopen the same database and inspect the final owner epoch and economic state.

Expected results

  1. Only the serializable valid mutation commits; exact retries reuse its receipt, conflicting or foreign scopes reject, and a superseded epoch cannot grant another asset change. No duplicate items, money or notifications appear; unexecuted race infrastructure remains Not Run.

Reset

  1. Close owned connections and let bounded child processes exit. For a new baseline use a fresh task-owned directory; for a recovery/retry case reopen the same scenario database without reseeding it. Preserve prior outputs and unrelated staged work; never reset the checkout or remove database sidecars while a connection is active.

Completion evidence and blockers

Required evidence: Actual independent-connection races and persisted conservation/receipt/epoch assertions against the selected SQLite file, plus focused request-identity/range checks and affected compilation. Record participants and ordering; a Python fake or sequential-only test is not concurrency evidence.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
