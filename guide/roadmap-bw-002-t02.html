Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-4

Implementation scope

  • Establish the bounded native contract/compatibility owner and fixtures, reusing applicable local FContentContracts/FContentRevisions and extraction drafts after review. Extract only needed definitions and transitive local $ref closure from canonical sources/data-inventory.json into a reproducible game-side snapshot with semantic definition/sample fingerprints; documentation-only planning metadata must not require a gameplay content-version bump. No runtime dependency on the docs checkout.
  • Preserve ability_command_v2, exact opaque IDs and case-sensitive tokens (TargetMode, EffectOperation, ItemGrade and ItemRarity alias), required/optional/nullable distinctions, finite numeric units and UTC Instant representation. Decode only supported schema vocabulary and narrow validated payloads at the serialization boundary; unsupported keywords or incomplete reference closure fail visibly rather than being ignored.
  • Define an internal admission compatibility context with separately named content/rules/database revisions and an explicit server-owned supported-tuple policy. Reuse ServerConfiguration content_version/rules_version rather than introducing competing settings. Do not make a new wire/package canonical schema or database deployment; fixture-only database identities remain explicitly synthetic. Unknown/incompatible domains reject before publication.
  • Add exact registered native automation tests and the bounded content-admission wrapper described in manual setup. Include accepted round trips, independently changed revision domains, stale/modified snapshots and wrong/unknown encodings. Test-only command/result projection examples preserve PublicCombatResult shape without introducing a runtime combat handler.

Out of scope

  • Freezing all 501 contracts, adding a generic schema framework, changing serialized values, real database migrations or network capability negotiation.
  • Treating stored fixture expectations, legacy Godot output or a canonical Fully Defined label as native runtime evidence.

Dependencies

Hard prerequisites: BW-001, BW-002-T01

Acceptance criteria

  1. AC 1

    Canonical selected definitions and their local reference closure reproduce from the registry; a changed semantic definition or compatibility sample is detected, while unrelated roadmap metadata does not change content meaning.

  2. AC 2

    Round trips preserve established IDs/tokens and requiredness/nullability, including absent optional character_id, present-null unused aim fields, ItemRarity as the ItemGrade alias and hidden source null in PublicCombatResult. Unknown fields/discriminators/case variants, nonfinite/fractional invalid numbers and missing required fields reject.

  3. AC 3

    Content, rules and database revisions remain distinct in reports and compatibility decisions. A declared compatible tuple passes; independently incompatible content/rules/database variants fail without mutating accepted state. No fixture database label proves migration support.

  4. AC 4

    The native suite reports exact executed assertions and current source/toolchain/fixture identities. Missing/stale reports, stale binaries and deliberate assertion failure return nonzero, followed by independent clean recovery.

Expected results

  1. Clean canonical round trips and declared compatible cases pass without encoding drift. Every invalid compatibility case is visibly rejected and prior state remains unchanged.
  2. Controls fail distinctly and clean recovery succeeds; no unexecuted case is reported passed.

Reset

  1. Run only against committed synthetic inputs and disposable negative-control copies. Each invocation uses a fresh output directory and rejects an existing output; preserve all prior reports, canonical definitions, user edits and assets.
  2. Bound native child execution, stop only owned process groups on timeout and release candidate/test state after each case. A rejected candidate preserves the previous active selection. Recover by running clean into a new output, without resetting the checkout or changing shared engines.
