Complete · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-4

Implementation scope

  • Add a small reviewed compatibility corpus under fixtures/content_admission/ and a reproducible read-only snapshot/extraction of only the canonical definitions and $ref closure needed by this epic. Record the source registry content_version, source/schema digest and selected definition names; mmo_docs/sources/data-inventory.json remains the sole editable definition owner. Resolve snapshots by explicit local paths, not website availability.
  • Cover the exact ability_command_v2 discriminator, existing ability/content IDs, case-sensitive EffectOperation and TargetMode strings, ItemGrade and its ItemRarity alias, required versus optional versus nullable fields, and shared Id/Version/CurrencyAmount/CombatAmount semantics. Do not serialize GDScript enum ordinals or derive IDs from names.
  • Introduce tools/check_content_admission.py --suite compatibility and a bounded headless fixture entry point under res://tests/content_admission/. Reuse existing tools/verify_toolchain.py and tools/check_configuration.py / tools/check_baseline.py process and unittest patterns; the Python driver launches the same small GDScript boundary functions later used by server admission and never becomes a second implementation of domain validation. No test add-on or generic schema framework is required.
  • Keep build_revision, content_version, rules_version, registry format version and optimistic record/build versions distinct. Supply database revision and its expected compatibility as explicit test context only until a storage owner exists. Use exact declared compatibility for the bounded fixtures; no inferred semantic-version range, new production package envelope or database field is added to ServerConfiguration or ContentPackageManifest.
  • The checker records commands, source/fixture/schema identities, actual assertions, diagnostics and exit status. Authored ContentValidationFixture run_evidence stays unexecuted; only an actual runner records execution. Schema/compatibility checks cannot set ability runtime readiness.

Out of scope

  • Importing all 501 contracts or the full game catalog, a universal validator/code generator, content editors (BW-095), database migrations or a new wire/package format.
  • Engine changes, gameplay execution evidence, and changing canonical IDs, existing serialized keys or prototype readiness markers.

Dependencies

Hard prerequisites: BW-002-T01, BW-001-T01

Acceptance criteria

  1. AC 1

    The compatibility suite round-trips representative supported canonical records without changing identifiers, enum strings, requiredness or nullability; unknown case/ordinal/discriminator values and malformed required fields are rejected with record/field findings.

  2. AC 2

    Independent fixtures vary content, rules and database revisions one at a time: declared compatible tuples pass; missing or incompatible context fails without substituting build_revision, registry format or record versions. Current bootstrap configuration remains valid and unchanged.

  3. AC 3

    The selected snapshot matches its recorded canonical source and closure; stale hashes or an unsupported schema construct fail explicitly. No manually editable duplicate schema is introduced.

  4. AC 4

    An engine/import/startup failure or missing assertion report is reported as not executed/failed, never a passing compatibility or gameplay result.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT (briarwake/). Run python3 tools/verify_toolchain.py; python3 tools/extract_content_contracts.py --check; python3 tools/check_content_admission.py --suite compatibility; python3 -m unittest discover -s tools -p 'test_*.py' -v. For the unchanged bootstrap: python3 tools/run_baseline.py --role server --headless --config fixtures/config/server.valid.json --smoke.

Setup

  1. Use the pinned native macOS ARM64 editor/templates and Python from tools/toolchain.lock.json. No database, account, network service, test add-on or gameplay scene is required.
  2. fixtures/content_admission/README.md documents the twelve-definition read-only local extraction, 140-case corpus and controls. The checker prepares an isolated minimal project using copies of the actual GDScript reader/runner. --output PATH must select a new directory; existing outputs are preserved.
  3. After a reviewed canonical registry update, refresh with python3 tools/extract_content_contracts.py --registry ../mmo_docs/sources/data-inventory.json. Never edit contracts.snapshot.json by hand.

Actions

  1. Run the compatibility suite and inspect run.json and logs/. Confirm all 140 cases ran, accepted records include serialized round trips, expected rejections contain exact record/field findings, and source/schema/fixture/toolchain identities are retained.
  2. Run separate controls using --control import-failure, startup-failure, missing-report, assertion-failure and unsupported-schema. Each must exit 1. Repeat with --engine /nonexistent/bw-test-engine. For stale provenance, alter source_registry_sha256 only in a temporary snapshot copy and use --snapshot PATH; expect nonzero before assertions.
  3. Inspect explicit content/rules/database tuples and the independent build/registry/record versions. Run a fresh clean suite after controls. Authored specification run_evidence must remain unexecuted; no sample prototype/readiness marker changes.

Expected results

  1. A clean suite returns 0 only after all 140 actual GDScript assertions pass; no enum ordinal/case/discriminator, malformed key/nullability, unknown stable reference or incompatible revision is silently accepted.
  2. Unavailable-engine, parse/import/startup and absent-report controls remain Not Executed with no assertion pass; the deliberate false expectation records Executed/Failed. Unsupported schema and stale provenance fail explicitly.
  3. The unchanged external bootstrap configuration still produces the three-heartbeat headless smoke pass. No database field, package envelope, ability enabling or gameplay execution is introduced.

Reset

  1. Allow each bounded process to exit; disposable fixture projects are automatically removed and their process groups reaped. No persistent candidate, world, database or peer state is created.
  2. Retain run.json and logs in the selected evidence location. Remove only owned temporary inputs/output after retention; leave canonical sources, snapshots, corpus and bootstrap configuration unchanged. See validation/tickets/BW-002-T02/ in DOCS_ROOT for actual results, including the retained baseline-test EPERM failure and passing sequential retry.

Completion evidence and blockers

Required evidence: Executed positive/negative compatibility report with source/schema/fixture digests, exact serialized samples, separate version-domain assertions and runner-failure evidence.

Blockers: None recorded; see dependencies.

  • Executed 140 GDScript compatibility cases, all seven runner/provenance/schema failure controls, pinned toolchain, unchanged server bootstrap smoke and 37 game tooling regressions (passing sequential retry after one retained baseline cleanup EPERM). Twelve canonical definitions and exact serialized samples retain IDs/enum strings, nullable/optional fields, amount semantics and separate revision domains.
