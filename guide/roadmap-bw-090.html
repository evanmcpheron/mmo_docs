Phase: 9. Measured capacity and production acceptance · Completion milestone: Production-ready full game

Objective and scope

Establish and verify a defensible supported workload envelope for the intended release configuration.

Scope: Simulation, bandwidth, database/settlement and client presentation measurements under crowded gameplay, plus overload/admission behavior. Capacity is a measured release budget, not a speculative realm population.

Acceptance criteria

  1. AC 1

    The approved test plan states concurrency/density, client hardware/platform/renderer/tier/internal resolution, server tick/bandwidth/tail-latency/backlog/memory budgets, client CPU/GPU frame-time percentiles and video-memory budgets, workload mix and failure/recovery objectives before declaring a pass.

  2. AC 2

    Scripted users move, fight, command the maximum legal summons, create overlapping effects, craft and trade; tests include crowded markets/world encounters, burst arrivals and instance activity. Client workloads include the production water/reflection, foliage, lighting/atmosphere and particle configurations rather than only placeholder scenes.

  3. AC 3

    Runs retain tick percentiles, queues, entity/subscription counts, bytes per client, database latency, pending settlements, memory and recovery measurements for exact release versions. Client results retain CPU/GPU frame percentiles, memory/resource counts and expensive-pass timings per supported quality tier.

  4. AC 4

    Latency/loss/jitter/reordering scenarios and an unavailable/saturated destination preserve authorization, meaningful rejection/recovery and economic conservation.

  5. AC 5

    The supported configuration meets approved budgets or explicitly reduces its admission envelope; identified performance changes have before/after evidence and preserve gameplay-critical hazards.

  6. AC 6

    The integrated client workload also combines dense production geometry, the declared maximum simultaneous local lights, ambient-occlusion/contact-depth treatment and large/overlapping reflective/refractive water surfaces with the actors, legal companion densities and effects already required. Draw-call/overdraw counts and pass timings identify rendering bottlenecks separately from CPU simulation, memory and network costs; every supported hardware/backend/internal-resolution/tier configuration, including fallbacks, meets the preapproved frame-time and memory budgets without losing required gameplay visibility.

Verification and blockers

Completion evidence required: Required future proof: reproducible full-workload load/soak and client-clutter runs, raw percentile/bandwidth/database reports, approved capacity budgets and overload/recovery evidence for the release configuration.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ticket planning

Use BW-090 as the parent epic. Link each future ticket to the AC links above and state the evidence it will produce. Split work into demonstrable behaviors; one criterion may require several tickets. Epic completion still requires every criterion, verified evidence and completed hard prerequisites.

Ordering rationale: Early probes guide architecture; final capacity waits for the workloads that dominate the intended game. Add partitioning or optimization only where measurements justify it.

Related open decisions: Capacity, security and recovery budgets; Incremental topology and comparable branch orders; Render configuration and supported quality envelope
