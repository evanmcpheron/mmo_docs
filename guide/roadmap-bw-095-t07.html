BW-095-T07 · Publish accepted edits while retaining prior valid output on rejection

In Progress · Parent epic: BW-095 · Versioned content authoring and import workflow

Epic acceptance criteria: BW-095-AC-2, BW-095-AC-4

Implementation scope

  • Finish the T01 offline publication boundary using existing native whole-selection admission and staged filesystem output; an authoring command may publish only after the full candidate and all exports/manifests validate. One owner selects the complete accepted output. On validation/export/write/publication failure retain the complete previously accepted package, manifest and client/server projections; never replace individual files from a rejected candidate. Bound staging beneath the caller’s task-owned output and reject unsafe source/output overlap.
  • Demonstrate reviewed A → accepted B → rejected C using the complete representative package: B makes one canonical, compatible content edit with a visible source/output diff and updated identities; C breaks a cross-family reference or progression rule. Preserve every established ID/encoding and canonical schema bundle; deliberate incompatible versions reject through FContentCompatibility rather than redefining contracts. Do not create an independent rollback service or source migration framework.
  • Add only focused publication/last-valid-output tests at the actual new adapter boundary, including validation rejection, a controlled output-write failure and source/output overlap. Existing native atomicity and unchanged admission rules retain their coverage. Publish a short runbook and QA/result summary tying accepted/rejected diffs, revision identities and pending manual replay to the implementation PR; no separate parent completion audit or large evidence archive.

Out of scope

  • Durable gameplay/database transactions, service deployment, live hot reload, automatic gameplay acceptance and completion of downstream feature epics.

Dependencies

Hard prerequisites: BW-095-T06

Acceptance criteria

  1. AC 1

    An accepted canonical edit produces reviewable source and export differences with stable established IDs, traceable changed package/fixture identities and compatibility with sources/data-model.schema.json. The command selects the complete new output only after successful validation.

  2. AC 2

    A rejected edit reports the affected source/record/field and returns nonzero while the entire prior accepted package, manifest and client/server exports remain byte-identical and usable. A controlled write/publication failure and unsafe source/output overlap also preserve prior output and authored inputs.

  3. AC 3

    The documented author/import/validate/export/admit workflow is reproducible from its recorded prerequisites and exact commands. Results distinguish tooling acceptance from unexecuted gameplay/runtime QA; neither source review nor schema success changes runtime evidence.
