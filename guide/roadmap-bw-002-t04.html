Complete · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-2, BW-002-AC-4

Implementation scope

  • Add the missing server-side admission owner, proposed content/content_admission.gd, as a small non-scene boundary with explicit canonical record collections and compatibility context. Parse into an isolated candidate; no active record is exposed by structural validation. Reuse T02 compatibility support and T03 targeting checks rather than copying policy into the loader.
  • Support only the canonical fixture families needed here: AbilityDefinition with optional shared AbilityRuntimeBinding, its targeting/timing/finite operation dependencies, ResourceDefinition/ResourceGainRule and the referenced static catalogs. Resolve the selected $ref and content-reference closure, distinguish instance from definition namespaces, and reject duplicate IDs, unknown references, unsupported families/fields and incompatible content/rules context.
  • Validate documented target-mode/input-kind compatibility, relation, positive cap, finite nonnegative geometry, allowlisted floor/line-of-sight/revalidation policies, explicit resolved resource identity/cost and timing/commit constraints. Preserve shared resource aliases and null-derived maximum semantics; never infer costs from ability prose, profile percent conversions or display labels.
  • Add --suite structure with canonical ContentValidationFixture expectations and ContentValidationResult/ValidationFinding outputs. Include a compatible nonbehavioral static package and one-mutation invalid candidates for references, target/resource fields, timing, duplicates and versions. Required fixtures/catalog dependencies are implementation scope, not assumed production content.

Out of scope

  • Enabling gameplay records at structural validation, importing every catalog family, inventing missing domain types or changing mmo_docs canonical schemas.
  • Content authoring/export tooling (BW-095), actual target geometry simulation, resource spending, build resolution and storage/provider selection.

Dependencies

Hard prerequisites: BW-002-T02, BW-002-T03

Acceptance criteria

  1. AC 1

    A compatible supported fixture stages successfully with unchanged IDs and no active-record mutation. Unknown/duplicate references, invalid target/resource/timing fields and mismatched revisions each produce a stable finding code, record/property path and actionable message.

  2. AC 2

    References are checked in their declared namespaces; malformed unused fields, nonfinite/negative amounts, illegal policy combinations and unknown handlers are not converted into defaults.

  3. AC 3

    A mixed candidate containing a valid record and an invalid record exposes neither as active; prior accepted state, if supplied by a fixture, remains unchanged.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Setup

  1. Use the pinned native macOS ARM64 Godot 4.7.2 executable and Python environment from tools/toolchain.lock.json. All named commands, scripts and fixture catalogs now exist in GAME_ROOT.
  2. fixtures/content_admission/structure.json supplies canonical static collections, explicit compatibility context, trusted policy vocabulary, disabled prototype/binding examples and caller-authored resolved probes. No database, account, peer, scene control or build resolver is needed.

Actions

  1. Run the structure suite and inspect the ContentValidationResult records in the new artifacts/structure-*/run.json report; use --output PATH for another new evidence directory.
  2. Inspect the compatible static/prototype cases, one-mutation invalid cases, 21-mode/four-input matrix, mixed-valid-invalid and same-id-distinct-namespaces controls. Every case repeats with record arrays reversed and compares finding signatures.
  3. Confirm all rejections return no candidate, prior valid candidate snapshots stay unchanged, valid input IDs/null maxima/aliases are preserved, and caller/snapshot mutations cannot affect staged records.
  4. Exercise --control import-failure, startup-failure, missing-report, assertion-failure and unsupported-schema with --suite structure and separate new output directories; all must exit 1. Rerun the clean suite afterward.

Expected results

  1. All 174 authored structure cases pass their expected acceptance/rejection assertions. Findings contain stable codes, record/property paths and actionable messages. Explicit zero/null and separate ID namespaces remain distinct; malformed fields, nonfinite/negative numbers and unsupported policies/references/operations reject.
  2. Only complete supported candidates are returned. Staging owns no active selection and cannot enable behavior; authored readiness flags/fixture run_evidence remain unchanged. Runtime capability/readiness, economic gates and real startup/active-state integration remain T05–T08.
  3. Compatibility/boundary suites and all 43 Python tool tests pass separately. Import/startup/absent-report failures remain unexecuted; an intentionally false expectation is Executed/Failed.

Reset

  1. Let each bounded runner exit; its disposable copied Godot project and in-memory candidate state are removed automatically. Leave canonical snapshots, tracked fixtures and bootstrap configuration unchanged.
  2. Retain run.json and logs from the chosen new evidence directory. Repeating a clean suite needs no persistent-state reset.

Completion evidence and blockers

Required evidence: Executed staging/structural/reference matrix, unchanged-active-state assertions and actual canonical validation results with source/content/rules identities.

Blockers: None recorded; see dependencies.

Compatibility/boundary regressions and 43 Python tool tests pass.
