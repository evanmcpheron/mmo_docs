Complete · Parent epic: BW-001 · Reproducible client and headless project

Epic acceptance criteria: BW-001-AC-1

Implementation scope

  • Inspect the existing project.godot baseline: Godot 4.7, Forward Plus, Jolt and a Windows D3D12 preference are declared, but there are no scenes, scripts, export presets or build tools. Preserve Godot 4.7 as requested; identify its exact release or development build and source revision rather than substituting another minor version.
  • Create tools/toolchain.lock.json with the exact engine and matching export-template versions, acquisition locations and checksums, macOS version/CPU architecture used for verification, required Python version, and any source build instructions. Record no engine patches for the initial stock build, or explicitly pin an existing patch set without adopting a new fork.
  • Record macOS client and macOS dedicated headless server as the verified BW-001 targets. Linux and Windows are future targets, with no compatibility claim until tested. Record the provisional client Forward Plus/backend settings separately from headless simulation, retaining the Windows setting only as an unverified future-platform preference.
  • Add tools/verify_toolchain.py and setup instructions that verify the lock against locally acquired engine/templates, report exact paths and mismatches, and work without a preexisting project import cache. Provide a temporary lock-copy option for negative checks.

Out of scope

  • Selecting a different Godot minor version; renderer feasibility, camera, shaders, art assets or new engine patches (BW-097).
  • Linux/Windows execution, release signing/notarization, hosting, gameplay or automated downloads using credentials.

Dependencies

Hard prerequisites: None

Acceptance criteria

  1. AC 1

    A fresh macOS environment can acquire the exact recorded Godot 4.7 build and matching templates by following the setup instructions; checksum/version verification succeeds and records the native CPU target.

  2. AC 2

    A missing engine, missing templates or modified checksum in a temporary lock copy returns a nonzero exit and identifies the missing/mismatched component with a corrective action.

  3. AC 3

    The lock separates provisional client renderer/backend settings from the headless target and explicitly records the engine patch state; it identifies Linux and Windows as future unverified targets.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: briarwake repository root.
python3 tools/verify_toolchain.py
python3 tools/verify_toolchain.py --engine "/path/to/Godot.app/Contents/MacOS/Godot" --templates "/path/to/templates"
python3 tools/verify_toolchain.py --lock "$BRIARWAKE_NEGATIVE_DIR/toolchain.lock.json"
python3 tools/verify_toolchain.py --engine "$BRIARWAKE_NEGATIVE_DIR/missing-godot"
python3 tools/verify_toolchain.py --templates "$BRIARWAKE_NEGATIVE_DIR/missing-templates"

Setup

  1. Use native ARM64 Python 3.10 or newer on macOS. Follow briarwake/tools/README.md to acquire the stock official Godot 4.7.2-stable editor and matching templates, with download hashes read from tools/toolchain.lock.json. An existing installation may be verified directly; isolated acquired files use the explicit path flags.
  2. Use a clean checkout without copied .godot state. This ticket is command-line tooling: no scene, local player, graphical launch or gameplay fixture is required.
  3. Follow the README Negative checks snippet to create BRIARWAKE_NEGATIVE_DIR and a temporary lock copy with only engine.macos.executable_sha256 changed to 64 zeroes. Keep the canonical lock untouched.
  4. For a missing payload check, create another disposable directory containing only a copy of the matching templates/version.txt, without macos.zip.

Actions

  1. Run the default verification against the installed toolchain, then verify an isolated installation with --engine and --templates. Record the paths, OS/build, Python version, native target, hashes and three engine/template version outputs.
  2. Run against the clean checkout and confirm no .godot directory or project file changes are produced.
  3. Run the altered lock copy, nonexistent engine path and nonexistent templates path. Verify each exit status using the shell immediately after each command.
  4. Pass the directory containing only version.txt with --templates to verify that a missing macos.zip is diagnosed separately.
  5. Inspect the lock target boundaries and unchanged project.godot: client Forward Plus/backend settings remain provisional, the dedicated server is headless with Dummy audio and no graphics dependency, patches is empty, and Linux/Windows are explicitly future unverified targets.

Expected results

  1. Matching installed and isolated toolchains exit 0 and print engine/debug/release version 4.7.2.stable.official.ed1daf0bf, template version 4.7.2.stable and native arm64 target. No project import cache is required or created.
  2. Negative cases exit 1, identify the component/path or expected/actual checksum and provide a corrective action. No failed invocation reports a passing build/runtime/gameplay test.
  3. The lock records the macOS 27.0 (26A428) verification baseline, stock source revision ed1daf0bf001b61586d9930840f2f1394092c079, matching acquisition URLs/checksums and Python minimum. Toolchain verification is separate from subsequent client/server application exports.

Reset

  1. Remove only the disposable negative-check directory and any isolated acquisition/checkout directories created for this test; unset BRIARWAKE_NEGATIVE_DIR. Preserve existing editor/template installations, canonical lock and user files.

Completion evidence and blockers

Required evidence: The committed toolchain lock, acquisition/setup instructions, successful verification output and actual missing/mismatched-component diagnostics.

Blockers: None recorded; see dependencies.
