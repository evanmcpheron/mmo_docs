Epic acceptance criteria: BW-018-AC-1

Implementation scope

  • Owner selection, 2026-10-23: use local SQLite for this bounded probe. At inspected game main 1f705e797fae5507fe477deb85529f047f2ddd63, Briarwake.Build.cs has no database dependency and no durable store exists. The installed UE 5.8.3 SQLiteCore runtime module exposes FSQLiteDatabase/prepared statements and bundles SQLite 3.47.1; it is not enabled or integrated in Briarwake. MultiplayerSessions handles sessions, not persistence. Pin the actual loaded SQLite version, native VFS/locking, journal/synchronous settings, foreign-key enforcement, supported integer ranges and bounded lock/error handling before claiming durability.
  • Address the concrete reuse constraint: SQLiteCore.Build.cs documents that the custom Unreal platform lacks shared-memory/granular locking and permits only one open FSQLiteDatabase per file; TargetRules defaults bCompileCustomSQLitePlatform to true and marks it RequiresUniqueBuildEnvironment. Verify the actual module/VFS used by the probe. Use a native-platform SQLiteCore build with real file locking and sync through the existing source-engine/toolchain when necessary; changing a project flag does not replace an installed precompiled Editor module. Prove two independent connections can access the same task-owned file before later race tests. Do not substitute an in-memory map, Python database implementation or mocked lock for this boundary.
  • Add one explicitly wired, caller-owned native persistence owner in the existing Briarwake module, limited to the fixture records and transactions used by this epic. Reuse FContentContracts/canonical extraction for the required ItemInstance, ItemOwnershipRecord, InventoryContainer, WalletRecord, SessionOwnershipRecord, OperationReceipt, CurrencyLedgerRecord and TransactionalOutboxRecord closure. Keep SQL/storage layout internal; preserve existing identifiers, tokens, nullable fields and exact integer values. Database schema revision comes from real store metadata, separate from content/rules revisions; the existing synthetic FContentRevisions database label does not establish migration support.
  • Provide bounded Editor/development test entry points using the existing Unreal Automation, FContentCompatibilityRun and owned-process helpers. Seed only a small explicit pair of personal fixture owners/containers/wallets and an existing unbound, unreserved whole item for later transfer. Fixture setup is test-only, not a public economic grant. Document exact native build/probe/reopen commands, supported file paths and fresh-output/reset behavior; compile the affected test and Server integration when module/target dependencies change. Reject missing/read-only/incompatible/unsafe stores and SQL failures observably without overwriting an existing file.

Out of scope

  • Production persistence/provider selection, hosted services, live accounts/authentication, an ORM or generic storage abstraction, client database access and full inventory implementation.
  • New art assets/maps, per-tick simulation persistence, packages, broad integration suites or repeating historical FULL workflows. BW-001/BW-002 retained evidence establishes bootstrap/contracts; BW-003 establishes only its local in-memory probe, not SQLite integration.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    The recorded candidate uses the actual selected SQLiteCore/native SQLite runtime with explicit queried durability/locking settings. A native test opens a task-owned file through two independent connections; a fresh process reopens and reads the exact seeded IDs, owner scopes, quantities, balances, record revisions and database schema revision.

  2. AC 2

    The bounded canonical contract closure and native value mapping preserve IDs, required/null semantics and supported exact integers. Unknown fields/tokens, overflow/precision loss, unsupported schema revisions, unsafe paths, read-only/write/open failures and missing settings reject with actionable findings and leave existing data intact.

  3. AC 3

    The delivered runbook names the real executable, exact targeted test/reopen commands, settings and cleanup. Actual storage observations are separated from authored expectations; no successful fixture mutation, database race, crash recovery or production authentication is implied by opening the store.

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From the existing game workspace containing Briarwake.uproject, use the bounded native SQLite probe commands documented by BW-018-T01 after implementation. No SQLite probe command exists at planning time; implementation must record the actual executable, exact suite/phase arguments, pinned build and task-owned database path before handoff. This is data-only work: no map, player controls or visual assets are required.

Setup

  1. Use only a fresh task-owned SQLite database and outputs beneath ignored game artifacts/. Preserve all existing project files, databases and historical evidence; no shared or production data. The selected candidate is local SQLite, explicitly chosen by the owner on 2026-10-23.
  2. The T01 native module/build and probe entry point are missing. Implementation must resolve the custom-VFS locking limitation and record the working native build; API/header presence is not acceptance.

Actions

  1. Using the delivered exact command, create the task-owned baseline, inspect the reported runtime version/VFS/settings and open a second independent connection to that file.
  2. Exit the owned process, reopen the same database in a fresh process and compare canonical records/revisions. Attempt the documented missing/read-only/unsupported-schema inputs without changing user data or permissions.

Expected results

  1. The file-backed baseline and its identities survive reopening, two connections use real SQLite locks, and invalid inputs fail visibly without replacing existing data. Missing native/VFS support is Not Run or failed, never a passing storage result.

Reset

  1. Close owned connections and let bounded child processes exit. For a new baseline use a fresh task-owned directory; for a recovery/retry case reopen the same scenario database without reseeding it. Preserve prior outputs and unrelated staged work; never reset the checkout or remove database sidecars while a connection is active.
