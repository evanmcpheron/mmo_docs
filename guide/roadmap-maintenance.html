Updating statuses and evidence

Edit only sources/development-roadmap.json for planning, status and evidence; preserve stable IDs, AC anchors, dependencies and authoritative contracts. Generated progress/readiness views derive from it.

Use Not Started, In Progress, Blocked or Complete. Implemented work awaiting human acceptance stays In Progress with the exact gap recorded; a PR can be delivered before acceptance. Blocked needs a real prerequisite. Planning alone starts or completes no work.

Complete requires executed passing evidence for every AC and complete dependencies. Evidence records use criteria, artifact, revision, result and summary; result may be Passed, Failed or Not Run. Not Run — Manual QA Pending is never a pass. Preserve accepted history; reopen completion only when current evidence is invalidated.

Before decomposition, read the parent ACs, relevant contracts/dependencies and current implementation owners once. Reuse existing game/Unreal/plugin functionality; API presence does not prove integration. Record only findings that change the ticket plan, without a separate capability-audit framework.

Each ticket defines a small outcome, owner, scope/exclusions, dependencies, exact epic_criteria coverage and appropriate verification. Together tickets cover every parent AC. Prefer deterministic unit tests, affected C++ compilation/native tests and concise human QA; preserve authority, invalid-input rejection, privacy and actual integration requirements.

Follow docs/validation.md for workflow scope, generation, evidence and the protected verification budget. Routine ticket changes use one roadmap generation command and focused gate, no inventory review refresh, browser, Unreal run, ancestor audit or duplicate report tree. Update parent completion only when its own criteria actually qualify.

For human QA provide prerequisites/map/controls, steps, expected/failure behavior and cleanup; record actual execution separately. Codex need not automate it. Quantitative requirements still need suitable objective evidence. No default GIF/frame/capture framework or multi-configuration matrix.

Keep one concise result summary or durable PR link when evidence is needed. Retain historical public acceptance links, not new log/capture archives. Increasing routine scope/budgets requires an explicitly authorized workflow change with defect, cheaper-alternative analysis and recurring cost.

MultiplayerSessions: available session code, incomplete dedicated integration

The supplied plugin is version 1 / VersionName 1.0, Runtime/Default, with content and OnlineSubsystem/OnlineSubsystemSteam dependencies. The descriptor has no engine compatibility declaration; Installed: false is descriptor metadata, not evidence of absence. Its source and menu asset are present. Briarwake.uproject has no explicit Plugins list; the game module has no direct dependency on this plugin. Retained build logs establish its earlier actual compilation/load, not an explicit Steam provider selection in current configuration.

Initialization is lazy: create/find call IsValidSessionInterface to obtain the default subsystem’s session interface; join/destroy require an already-valid interface. The constructor binds delegates without acquiring the backend. Invalid create/find returns without broadcasting failure. There is no explicit subsystem Initialize/Deinitialize implementation. BW-004-T01 must verify initialization order, callback completion and shutdown for its selected route.

Primary source: MultiplayerSessionsSubsystem.cpp and its public contract; Menu.cpp, Menu.h, plugin descriptor/build rules and project Config/DefaultEngine.ini.

Review and validation boundary

No parent criterion, gameplay contract, canonical schema, epic dependency or completed record is removed or relaxed. The new ticket dependency edges make actual consumers explicit without serializing independent movement/attribute work behind connectivity. Repeated AC links partition implementation and integrated evidence; they do not assign two implementations of the same rule. BW-003-T05 consumes completed T01 controls and proves only new aggregate failure modes. Future game work must keep identity, sequence, idempotency, private projections and server-authoritative transitions at their established boundaries.

Routine decomposition uses focused source inspection and applicable retained evidence. Expensive native/peer/Steam/workload tests above are future implementation completion evidence, not prerequisites for generating planning pages. Run documentation generation and the existing focused validation entry point below; it already checks schema shape, graph ordering, complete parent-criterion coverage, links, search and generated freshness. Documentation validation never upgrades the capability classifications or gameplay progress.
