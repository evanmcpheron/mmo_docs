Updating statuses and evidence

Reverify the implementation Git root and current main before execution. The owner selected evanmcpheron/BriarwakeUnreal; BW-001 used a separate BriarwakeNative worktree. BW-001 bootstrap completion is scoped to the retained pinned macOS Development evidence. Planning and historical Godot runs cannot substantiate native gameplay completion.

Edit only sources/development-roadmap.json for planning content, statuses, blockers and evidence. Do not hand-edit the generated pages, dashboard, milestone states, search records or manifest counts. Status must be exactly Not Started, In Progress, Blocked or Complete.

For an existing epic, change status and add verified_evidence records with criteria (one-based AC numbers), artifact (a committed repository-relative file or HTTPS evidence link), revision (the tested game/content revision), result (Passed or Failed) and summary. Preserve prior failure evidence in retained run artifacts; the current completion record must have passing evidence for every criterion. Never copy documentation-validation results into gameplay-completion evidence.

A Blocked epic needs a concrete blockers entry identifying the unresolved decision, missing prerequisite or external limit. Ordinary future prerequisites do not make every unstarted epic Blocked. Reopen an epic when a regression invalidates its current evidence; update dependent completion states rather than leaving a false release gate.

To insert work, allocate a new unused BW ID without renumbering existing epics. Put it at a dependency-valid position, choose its phase, add feature coverage and include it in applicable milestone/integration requirements. Gaps are allowed; IDs must never be reused for a different capability. Do not alter canonical gameplay contracts merely to classify planning documentation.

Each epic is published at guide/roadmap-bw-NNN.html with a stable BW identifier and BW-NNN-AC-N criterion links. Use the epic as the parent for future tickets and link each ticket to its covered criteria and verification evidence. Keep criterion numbering aligned with recorded evidence; introduce actual ticket records only when ticket planning is performed.

Mandatory reuse assessment before every epic decomposition, including Codex split-epic invocations: first read the parent requirements, exact acceptance criteria, linked canonical contracts, prerequisites and existing tickets. Keep sources/development-roadmap.json as the sole planning registry; capability review artifacts are dated evidence, not a second backlog.

Inspect only relevant current game source, callers, owners, configuration, .uproject/.uplugin descriptors, module/target rules, available tests and completed dependency evidence. Record repository/revision and pinned engine/plugin versions. If the game or a plugin is inaccessible, state that limitation; an uninspected integration is never verified. Reuse retained evidence only after checking affected input identities and scope.

Evaluate native Unreal and supplied plugins before proposing custom work. For each relevant capability record exactly one classification: Implemented and verified (source plus applicable executed evidence); Implemented but unverified (source without sufficient behavioral evidence); Provided by Unreal or a plugin (available but not necessarily integrated); Partially implemented (configuration/integration/extension remains); Missing (new implementation needed); Unknown or incompatible (bounded investigation or architectural decision needed). Support the classification with source paths, version/configuration and test artifacts or explicit not-run gaps. Different aspects of one system may need separate classifications.

Map every parent AC to verified existing behavior, reusable engine/plugin functionality, required configuration/integration, missing game-specific behavior and verification/regression evidence before assigning tickets. Record the focused assessment in ticket scope/related_docs or a linked dated review and use exact epic_criteria anchors for traceability. API presence, schemas, compilation, session membership and potential savings are not completed Briarwake behavior.

Create only the smallest cohesive independently verifiable additional outcome. Each ticket names scope/exclusions, existing owners and reusable functionality, genuinely new work, applicable dependencies, objective criteria and completion evidence. Prefer configuration/integration over rebuilding an adequate capability; use a bounded verification requirement when actual behavior is unknown. Extend established owners, not parallel managers, wrappers, protocols, validation suites or generic interfaces without consumers. Evaluate GAS, Iris and Replication Graph only against demonstrated fit, integration cost and measured need; never add them automatically.

Preserve server authority and all security criteria during reuse: derive identity/ownership from trusted connections; validate intent, sequence, size/rate, permissions and idempotency; keep private/server-only state out of unauthorized initial and later projections. RPC routing, replication, session membership, prediction, reliable delivery and movement correction do not establish authorization, exactly-once outcomes, privacy or Briarwake floor/collision legality.

Review dependency order, overlap and test ownership before finalizing: each rule has one implementation owner, each feature supplies its own regressions, and integrated tickets add only cross-boundary evidence. Check that all parent ACs remain covered by the ticket set and retain all existing IDs, parent links, contracts, completed statuses and evidence. Correct unfinished tickets narrowly. Reconcile status from actual execution only; planning never starts or completes an epic.

Keep authoring lightweight: use focused searches and reusable revision-specific evidence, not repository-wide scans or repeated engine builds. Separate expensive future native/connected/Steam/impairment/workload completion checks from ordinary documentation generation. Regenerate once and use the existing aggregate validation for registry shape, dependency ordering, complete AC coverage, links, navigation/search and freshness; do not add a parallel planning validator.

Run the commands below after a status or evidence edit. The first rebuilds all derived progress, readiness and HTML pages from the registry. The inventory review refreshes the generated planning-page fingerprints, navigation, search and page counts. The focused validator checks graph, coverage, evidence and output consistency; the existing full check also includes roadmap validation.

MultiplayerSessions: available session code, incomplete dedicated integration

The supplied plugin is version 1 / VersionName 1.0, Runtime/Default, with content and OnlineSubsystem/OnlineSubsystemSteam dependencies. The descriptor has no engine compatibility declaration; Installed: false is descriptor metadata, not evidence of absence. Its source and menu asset are present. Briarwake.uproject has no explicit Plugins list; the game module has no direct dependency on this plugin. Retained build logs establish its earlier actual compilation/load, not an explicit Steam provider selection in current configuration.

Initialization is lazy: create/find call IsValidSessionInterface to obtain the default subsystem’s session interface; join/destroy require an already-valid interface. The constructor binds delegates without acquiring the backend. Invalid create/find returns without broadcasting failure. There is no explicit subsystem Initialize/Deinitialize implementation. BW-004-T01 must verify initialization order, callback completion and shutdown for its selected route.

Primary source: MultiplayerSessionsSubsystem.cpp and its public contract; Menu.cpp, Menu.h, plugin descriptor/build rules and project Config/DefaultEngine.ini.

Review and validation boundary

No parent criterion, gameplay contract, canonical schema, epic dependency or completed record is removed or relaxed. The new ticket dependency edges make actual consumers explicit without serializing independent movement/attribute work behind connectivity. Repeated AC links partition implementation and integrated evidence; they do not assign two implementations of the same rule. BW-003-T05 consumes completed T01 controls and proves only new aggregate failure modes. Future game work must keep identity, sequence, idempotency, private projections and server-authoritative transitions at their established boundaries.

Routine decomposition uses focused source inspection and applicable retained evidence. Expensive native/peer/Steam/workload tests above are future implementation completion evidence, not prerequisites for generating planning pages. Run documentation generation and the existing FAST/FULL aggregate below; it already checks schema shape, graph ordering, complete parent-criterion coverage, links, search and generated freshness. Documentation validation never upgrades the capability classifications or gameplay progress.
