Not Started · Parent epic: BW-095 · Versioned content authoring and import workflow

Epic acceptance criteria: BW-095-AC-1, BW-095-AC-2

Implementation scope

  • Extend the same extraction and FContentAdmission owners for StatusDefinition and only its required closure. Use the T01 route for representative linked ability/status records; source entity remains runtime StatusInstance state. Validate owner_ability_id, category-specific stacking/refresh/control-group combinations, explicit nullable fields, positive periodic intervals, stack/duration bounds and required persistence flags from the canonical definition and status rules.
  • Current admission does not accept StatusDefinition. Add only its missing static semantic checks at the native boundary; UI/import mapping delegates to those checks. Preserve the documented 30% periodic carry constraint and existing category/control caps without implementing ticks, diminishing-return history, dispels, expiry or transfer execution. Missing behavior/bindings keep activation disabled.
  • Add focused positive/rejection cases to existing content admission tests: a valid periodic and nonperiodic status, missing owner, invalid category-policy pairing, nonpositive interval, invalid stack/cap and missing required field. Exercise real source/export/admit round trips rather than a parallel schema model; retain atomic selection and source-mapped findings.

Out of scope

  • Status gameplay execution, combat/control simulations, full status catalog and production presentation assets.

Dependencies

Hard prerequisites: BW-095-T01

Acceptance criteria

  1. AC 1

    Representative periodic and nonperiodic StatusDefinition records round-trip with stable IDs, explicit null semantics and valid owner ability references through the shared authoring route.

  2. AC 2

    Invalid owner references, category-policy/control-group combinations, required persistence fields, stack/cap values and periodic intervals produce record/field findings and reject the complete candidate without changing prior valid state.

  3. AC 3

    Admitting status catalog data does not create a status handler, passed runtime fixture or executable ability; canonical status encodings and numerical constraints remain unchanged.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From the existing game workspace, use the import/export commands and bounded sample paths documented by BW-095-T01 after implementation. That entry point does not exist at planning time; implementation must record exact runnable commands before handoff. This is offline content tooling: no gameplay map, mouse controls or editor execution is required.

Setup

  1. Use the existing game checkout, pinned UE 5.8.3/toolchain and canonical mmo_docs sources. Use only task-owned sample/output directories beneath ignored game artifacts/; preserve source assets, prior accepted output and historical evidence.
  2. Use the T01 documented CLI and reviewed status sample delivered by this ticket. Current native admission rejects this family; planned examples remain unexecuted.

Actions

  1. Round-trip the periodic and nonperiodic samples. Change only the task-owned owner reference, interval and category-policy fields to the documented invalid variants; repeat import after each edit.

Expected results

  1. Valid IDs/nulls/policies reproduce. Each invalid variant names the status and field, rejects the candidate and preserves prior output; no runtime behavior is enabled.

Reset

  1. Let the bounded command exit; use a fresh task-owned output directory for the next run. Restore only the sample edits made during this procedure; retain the prior valid output and concise actual result. Never reset the checkout, resave unrelated assets or overwrite historical evidence.

Completion evidence and blockers

Required evidence: Focused native status admission and round-trip assertions plus affected compilation. Keep one result summary and pending manual replay; existing admission atomicity and runtime gate coverage is reused.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
