Complete · Parent epic: BW-018 · Durable ownership and mutation recovery probe

Epic acceptance criteria: BW-018-AC-3

Implementation scope

  • Use the existing bounded owned-process execution/report helpers to run only the necessary SQLite crash/reopen scenarios through the actual T02/T03 owner. Test-only checkpoints identify before commit, after durable commit before acknowledgment, before notification delivery and after recipient acceptance before delivered marking. Abruptly terminate only the owned child at the reached checkpoint; an exception rollback or a normal connection close is not process-crash evidence. Reopen the same on-disk database in a fresh process without reseeding.
  • Before-commit failure leaves no partial mutation, receipt or outbox; after-commit acknowledgment loss retains all committed rows and an exact retry returns the original receipt. Resolve any interrupted commit through persisted state/key identity instead of resubmitting a different operation or compensating only currency. Compare conserved item/owner and wallet/ledger values after recovery; retain explicit diagnostics for unavailable storage or integrity failures.
  • Add bounded pending-outbox delivery to a minimal durable test recipient using canonical DurableNotification and stable outbox/receipt identity. Recipient acceptance/deduplication survives its own reopen; mark delivered only after acceptance. Crash between acceptance and producer marking must allow at-least-once redelivery with one recipient effect, without repeating any economic mutation. The recipient is a probe-only durable inbox, not a production broker/notification service; do not claim exactly-once network transport.
  • Record actual TransactionRecoveryTestRecord findings/conservation fields and a short revision/phase/receipt summary using existing evidence ownership. Keep crash switches and fixture seeds behind existing Editor/development guards, unreachable through gameplay commands; child nonzero exit alone or a missing report is not a successful crash test. The surviving verifier must prove the intended checkpoint, fresh database reads and final assertions. No default crash matrix, package run or historical all-suite replay is added.

Out of scope

  • Host power-loss/filesystem hardware guarantees, database corruption repair, distributed message brokers, real player notifications, inventory escrow/full-bag/lease feature scenarios, backup restore and production availability certification.

Dependencies

Hard prerequisites: BW-018-T03

Acceptance criteria

  1. AC 1

    Actual abrupt child termination before commit leaves the prior complete economic state; termination after durable commit before acknowledgment preserves the complete mutation and exact original receipt. Fresh-process retry never duplicates, loses or partially restores its item/currency changes.

  2. AC 2

    Failures before delivery and after durable recipient acceptance but before producer delivered marking recover from the same pending outbox. Redelivery is harmless and produces one durable recipient effect with the original notification identity; no item/wallet/ledger mutation runs again.

  3. AC 3

    Each claimed crash result proves its reached phase and fresh-process database assertions with conserved items/currency and one owner. Unreached checkpoints, failed startup, missing storage and incomplete verification remain Failed/Not Run rather than passing recovery evidence; test-only controls have no gameplay route.

Setup

  1. Use the existing workspace and canonical mmo_docs checkout, pinned macOS ARM64 UE 5.8.3 Editor/source-Server, Xcode build 27A266a and native SQLite 3.54.0/unix VFS. T02/T03 are Complete by the user’s explicit acceptance and their retained actual native evidence.
  2. Use only a fresh task-owned output directory under ignored artifacts/. Schema 4 adds the durable local probe inbox; historical schema-1/2/3 files are rejected and preserved without migration. Producer and recipient use independent connections/separate transactions in the same SQLite file; no production broker or independent storage failure domain is claimed.

Actions

  1. Run the exact recovery command. The existing bounded process helper launches Briarwake.Persistence.Recovery.Crash for before-commit, after-commit, before-delivery and after-acceptance. A guarded checkpoint atomically records the owned PID, run nonce, phase, source identity, acknowledgment state and receipt/outbox identities before waiting at most 10 seconds. The parent sends SIGKILL only to the owned process group after that checkpoint appears.
  2. A distinct process runs Briarwake.Persistence.Recovery.Verify against the same native/recovery/<phase>/recovery.sqlite files without reseeding. Inspect run.json and native/recovery.json for actual abrupt termination, matching phase/identity, fresh-process state assertions and canonical TransactionRecoveryTestRecord observations.
  3. Verify rollback of the entire pre-commit mutation, exact original receipt replay after acknowledgment loss, pending-outbox recovery before delivery and deduplication after recipient acceptance before delivered marking. The verifier reopens both owners and checks original notification identity, exact rows, conserved values, SQLite integrity and rejection of unavailable storage/recipient or changed recipient payload.

Expected results

  1. Exit 0, four reached owned children terminated with -9 and no timeout, then all 46 recovery assertions pass in a fresh verifier. A nonzero exit, failed startup, missing checkpoint/storage or incomplete report alone is never a recovery pass.
  2. Before commit the original complete baseline survives; retry of its original key creates one complete mutation. Other phases retain the complete original mutation/receipt and retry never settles it again. Final item A to B, balances 9007199254740966/125, item/ownership revisions 8 and both container/wallet revisions 4294967298 remain conserved.
  3. After recipient acceptance the original producer outbox is still pending while one durable inbox effect exists. Redelivery and recipient reopen preserve that notification identity and result in exactly one receipt, two balanced ledger rows, one delivered outbox, one inbox effect and one item owner. SQLite 3.54.0/unix/FULL-sync settings remain pinned; no exactly-once transport, power-loss, corruption repair, migration or production availability certification is implied.

Reset

  1. Let owned processes exit and connections close. Retain a concise result and any database needed for follow-up; remove only task-owned outputs no longer needed. Preserve unrelated files, historical evidence and active SQLite sidecars. Never reseed the scenario during recovery.

Completion evidence and blockers

Required evidence: Only the parent-required before/after-commit and event-delivery crash/reopen results, actual receipt/revision/outbox/inbox observations and focused native assertions at a recorded source/runtime/settings identity. Store one concise summary or PR link; do not retain a new large evidence archive.

Blockers: None recorded; see dependencies.
