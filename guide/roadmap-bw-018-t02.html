Not Started · Parent epic: BW-018 · Durable ownership and mutation recovery probe

Epic acceptance criteria: BW-018-AC-1

Implementation scope

  • Extend the T01 native transaction owner with one finite internal fixture transfer: move the existing unbound/unreserved item between the two authorized fixture containers and transfer a declared nonnegative integer amount between fixture wallets. Derive actor/account/character from the trusted server-test context, validate owner/container/item/wallet/epoch preconditions and compute results inside the transaction. This is an internal probe operation, not a new inventory RPC or client-authored economic outcome; unsupported binding/reservation/operation cases reject.
  • Commit item/ownership/container revisions, balanced debit/credit CurrencyLedgerRecord entries, one terminal OperationReceipt and its pending TransactionalOutboxRecord in the same SQLite transaction. Personal ownership remains account plus character with null guild owner; each extant item has positive quantity and one placement, wallets remain nonnegative integer minor units, and internal transfer ledger deltas sum to zero. Reuse canonical DurableContext/DurableNotification shapes; notifications contain committed references, not private rows. No separately writable inventory/wallet copy or trigger-based duplicate authority is introduced.
  • Acknowledge committed success only after SQLite reports successful durable commit under the pinned settings. A write/commit failure never creates fabricated success; an uncertain commit outcome must be resolved by the same operation key on reopen/retry rather than reported as a known rollback. Store the authenticated operation scope and exact validated request identity needed by T03 idempotency; authors cannot supply receipt IDs, balances, passed evidence or compatibility policy.
  • Add focused existing-harness native tests calling the real owner and file-backed store for an accepted transfer, rejection of invalid owner/revision/funds/reservation and a controlled pre-commit SQL failure. Reopen to verify the complete accepted result; retain prior rows on rejection. Test-only phase checkpoints may observe commit/response ordering for later crash controls, but cannot bypass domain validation or appear as gameplay commands.

Out of scope

  • Stack split/merge, equipment, vendors, crafting, guilds, fees, delivery claims, public economic endpoints, full inventory/wallet gameplay and a generic transaction scripting language.

Dependencies

Hard prerequisites: BW-018-T01

Acceptance criteria

  1. AC 1

    One accepted fixture transfer atomically changes the item placement/owner and participating record revisions, writes balanced ledger entries, and stores exactly one canonical receipt plus pending outbox row. Fresh reads/reopen observe the complete result with no duplicate owner, negative balance or lost item.

  2. AC 2

    The committed receipt is returned only after successful durable commit. Pre-commit failure or invalid preconditions leave all asset/ledger/receipt/outbox state unchanged; a failed/unknown commit cannot be acknowledged as committed success.

  3. AC 3

    Server-owned identity and result construction reject foreign owner scope, stale revisions, insufficient funds, reserved/bound unsupported assets, overflow and fabricated result fields. Logs/results identify operation, owner scope and content/database revisions without exposing credentials or another actor’s private rows.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. From the existing game workspace containing Briarwake.uproject, use the bounded native SQLite probe commands documented by BW-018-T01 after implementation. No SQLite probe command exists at planning time; implementation must record the actual executable, exact suite/phase arguments, pinned build and task-owned database path before handoff. This is data-only work: no map, player controls or visual assets are required.

Setup

  1. Use only a fresh task-owned SQLite database and outputs beneath ignored game artifacts/. Preserve all existing project files, databases and historical evidence; no shared or production data. The selected candidate is local SQLite, explicitly chosen by the owner on 2026-10-23.
  2. Complete T01 and use its exact working native commands/settings with a fresh fixture database. The T02 transfer and observation commands must be documented before replay.

Actions

  1. Execute the finite accepted transfer and inspect the receipt, item/container/wallet revisions, paired ledger entries and pending outbox. Exit and reopen the same database.
  2. In separate fresh scenarios submit the documented invalid owner/revision/funds/reservation inputs and trigger the test-only pre-commit write failure. Inspect state and response ordering.

Expected results

  1. Success follows durable commit and reopens as one complete transfer. Invalid/failing attempts preserve prior state, balances never go negative, the ledger conserves transferred currency and no receipt claims a commit that did not complete.

Reset

  1. Close owned connections and let bounded child processes exit. For a new baseline use a fresh task-owned directory; for a recovery/retry case reopen the same scenario database without reseeding it. Preserve prior outputs and unrelated staged work; never reset the checkout or remove database sidecars while a connection is active.

Completion evidence and blockers

Required evidence: Actual file-backed atomic transfer/reopen and rejection assertions, commit-before-ack observation and affected native compilation. Reuse the existing canonical validation/report owners; retain a concise receipt/revision/ledger result, not copied report trees.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
