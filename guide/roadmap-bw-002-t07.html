BW-002-T07 · Reject unlimited guaranteed price and conversion loops

Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-5

Implementation scope

  • Add the no-unlimited-guaranteed-loop analysis to the same admission owner over T06 complete enabled route view. Preserve integer quantities, recipe batch outputs, required inputs and explicit prices; analyze the combined existing-plus-proposed graph, not each recipe or currency edge alone.
  • Enforce crafted output sellback strictly below guaranteed NPC-purchased input cost, accounting for output quantity and the cheapest supported guaranteed conversion path. Reject repeatable guaranteed cycles that generate currency/material value without exhausting required inputs; include salvage/conversion chains and obey their documented binding/access restrictions. Do not reject ordinary player-market arbitrage or assume uncertain rewards are guaranteed.
  • Return actionable findings naming the contributing source route IDs and quantities or a concrete repeatable witness. If supported constraints are insufficient to establish safety, keep those routes disabled and report the unsupported case; do not silently certify it or introduce a permissive heuristic.
  • Add --suite economy-loops: a lossy safe cycle, safe acyclic chain, crafted sellback at/elevated above guaranteed input cost, multi-step profitable conversion, a loop created only by joining prior admitted routes with a new route, explicit free-input profit, multi-input/batch-output cases and a nonrepeatable scarce-input control. Include craft-salvage material loss and no-XP/no-gold constraints from T06.

Out of scope

  • Player-market optimization, numerical production balancing, speculative conversion mechanics, load/capacity measurement and live crafting/vendor services.
  • Approving a route from pairwise price checks alone, rounding floating-point currency into safety, or using a graph pass to bypass later feature/runtime readiness.

Dependencies

Hard prerequisites: BW-002-T06

Acceptance criteria

  1. AC 1

    Positive fixture graphs pass the documented value-loss rules; every guaranteed profit/duplication fixture and equality-at-crafted-sellback fixture fails before route admission with contributing record IDs and a reproducible explanation.

  2. AC 2

    A proposed route that is safe alone but completes a profitable cycle with already admitted routes is rejected. Multi-input recipes, batch quantities and explicit zero costs cannot bypass the gate.

  3. AC 3

    A scarce nonrenewable-input control is not mislabeled an unlimited cycle; unknown completeness/behavior fails closed with an explicit unsupported finding. Reordering the same fixture graph preserves the decision.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root.
python3 tools/verify_toolchain.py
python3 tools/check_content_admission.py --suite economy-loops
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use the pinned native macOS Godot editor and Python environment from tools/toolchain.lock.json. The checker and fixtures named below are implementation deliverables of this ticket or its dependencies, not existing commands today.
  2. Provide all positive/negative graphs in canonical vendor/recipe/item/material/salvage records plus expected findings and exact finite replay steps for each exploit witness. No gold balance or persistent store is needed.

Actions

  1. Run the graph suite and inspect the route/quantity witness for each rejected graph against the expected repeatable gain or strict crafted-price violation.
  2. Run the old-route-plus-addition and permuted-order cases; compare with safe lossy and scarce-input controls.

Expected results

  1. Safe supported graphs pass; unsafe or unsupported graphs leave affected routes disabled with observable reasons. The complete active-plus-candidate graph is evaluated before admission.
  2. No graph fixture executes a production economy or claims balanced content; integer accounting and documented salvage limits are retained.

Reset

  1. Let each bounded checker process exit and discard its in-memory candidate/active registries. Use runner-owned temporary copies for negative mutations; leave tracked canonical snapshots, fixtures and bootstrap configuration unchanged.
  2. Retain the attributable run report and logs in the chosen evidence location. A subsequent clean suite run must reproduce the original outcomes without a database, account, network peer or gameplay scene.

Completion evidence and blockers

Required evidence: Executed positive and negative graph report with exact route/quantity witnesses, combined-graph regression and safe-control evidence.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
