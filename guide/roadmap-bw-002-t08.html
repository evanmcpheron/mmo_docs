Complete · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-1, BW-002-AC-2, BW-002-AC-3, BW-002-AC-4, BW-002-AC-5

Implementation scope

  • Wire the same admission owner into an explicit server content-loading entry point before any requested records become active/feature-accessible. Pass validated ServerConfiguration rules/content context from its existing owner and preserve tools/run_baseline.py, server-ready/bootstrap smoke behavior and the external configuration contract. Add a narrowly scoped optional fixture-package launch input if needed, separate from canonical ServerConfiguration; no client-supplied package selection or new production package schema.
  • Keep static record collections and an explicit requested-enabled selection separate from disabled staged records. Validate compatibility, structure/references, actual capability/readiness and the complete economic graph as applicable, then publish one immutable admitted selection only when every requested record succeeds. A rejected candidate publishes none of its requested records and cannot alter the previous valid selection.
  • Use the existing server bootstrap entry plus tools/check_content_admission.py --suite startup / --suite all for bounded integration checks. Include a valid safe-static package, valid mixed-with-disabled-prototype package, requested unbound ability, mixed valid/invalid records, incompatible versions and missing-value/profitable economic graph candidates. Fixtures requiring gameplay handlers remain disabled; a safe economic graph pass alone does not make an unimplemented vendor/crafting feature executable.
  • Report admitted/disabled IDs, canonical ValidationFinding diagnostics and distinct build/content/rules context without private data; database compatibility stays explicit fixture context until persistence exists. Test A-accepted/B-rejected/A-retained through the real admission API and real server startup rejection before content readiness. Preserve the existing player-free headless bootstrap assertions and baseline regression checks.
  • Document launch/suite commands in GAME_ROOT/tools/README.md and the authority map. Keep fixtures, source and execution reports attributable; no ticket or epic is marked Complete solely from generated plans or schema checks.

Out of scope

  • Live hot reload, production content distribution/signing, catalog authoring, gameplay handlers, persistence integration, authentication, multiplayer sessions and deployment.
  • Weakening BW-001 bootstrap/configuration/credential checks, claiming economic execution from graph admission, or automatically promoting epic progress from individual tickets.

Dependencies

Hard prerequisites: BW-002-T05, BW-002-T07, BW-001-T03, BW-001-T04, BW-001-T07

Acceptance criteria

  1. AC 1

    The actual headless loading path admits the compatible safe-static package and exposes exactly its requested supported records only after all applicable checks pass; disabled prototype records remain unavailable.

  2. AC 2

    Unknown references, invalid target/resource fields, incompatible revisions, unbound/forged-ready behavior and incomplete/unsafe economic candidates fail before activation with actionable findings. A mixed candidate cannot partially activate, regardless of record order.

  3. AC 3

    The A/B sequence retains A byte-for-byte/semantically unchanged after B fails; fresh startup with a requested invalid package returns nonzero before content readiness. Normal bootstrap without a content request retains its previous behavior and does not advertise enabled gameplay.

  4. AC 4

    The all-suite and existing Python tool regressions run with executed assertions and pinned-engine diagnostics; build/startup failures remain distinguishable from executed failures/passes. No game, network capacity or database evidence is inferred from this admission run.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT (briarwake/), with the pinned native macOS arm64 Godot editor.
python3 tools/verify_toolchain.py
python3 tools/check_content_admission.py --suite all
python3 tools/check_content_admission.py --suite startup
python3 -m unittest discover -s tools -p 'test_*.py'
python3 tools/run_baseline.py --role server --headless --config "$PWD/fixtures/config/server.valid.json" --smoke

Setup

  1. Use tools/toolchain.lock.json and tools/README.md#atomic-server-admission-bw-002-t08. The checker creates isolated temporary projects and preserves prior evidence; use --output with a new directory to retain reports.
  2. For a regular CLI case, run python3 tools/content_startup_checks.py --case mixed-disabled-prototypes --output /tmp/briarwake-admission-demo using a new directory. This writes disposable server.json/package.json copies from existing canonical fixtures; it changes no ServerConfiguration contract.
  3. Use res://tests/content_admission/startup_runner.gd through --suite startup for the direct A/B API checks. Local saved-editor-layout import failed in the original checkout during this invocation; the exact committed source passed in an isolated clean worktree. Preserve existing cache/settings and use a clean checkout/worktree if that engine editor-layout error recurs.

Actions

  1. Run the all and startup suites. Inspect all/run.json, per-suite source/input hashes, direct startup-report before/after selection hashes, and separate real server launch logs.
  2. Run python3 tools/run_baseline.py --role server --headless --config /tmp/briarwake-admission-demo/server.json --content-fixture /tmp/briarwake-admission-demo/package.json --smoke. Repeat case generation into new directories with requested-unbound, forged-ready, mixed-valid-invalid, mixed-invalid-first, profitable-graph and safe-graph-missing-handler.
  3. Run the no-content baseline smoke and python3 tools/check_baseline.py --case pass --output with a new absolute nonsymlink output directory. Check clean client/server export, client artifact inspection and exported runtime independently.

Expected results

  1. Only requested supported static records appear in the immutable admitted selection; disabled prototypes/routes are absent. Publication precedes content-ready and server-ready; gameplay_enabled remains false.
  2. Rejected candidates retain A including context/disabled IDs byte-for-byte; fresh invalid startup exits 2 before content-ready/server-ready. Canonical code/path/message findings explain the rejection; no client/player scene loads.
  3. No-content startup emits no admission event and retains the three-heartbeat smoke. Import/startup failures without assertions remain Not Executed; deliberately false assertions are Executed/Failed. Passing admission does not certify gameplay, network capacity, database behavior or production content distribution.

Reset

  1. Let bounded processes exit; each in-memory owner/selection is discarded. The checker removes only its owned temporary project.
  2. Keep attributable reports/logs under the docs evidence directory. Discard disposable manual fixture copies when finished and use new output directories for reruns. Do not modify canonical snapshots or delete user editor state to manufacture a pass.
