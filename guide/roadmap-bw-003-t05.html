Not Started · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-1, BW-003-AC-2, BW-003-AC-3, BW-003-AC-4

Implementation scope

  • Add --suite all orchestration to tools/check_runtime_fixtures.py using the same evidence/context/diagnostics/metrics suites. Produce one attributable manifest linking immutable expectations, actual assertion/run records, deterministic outcome comparisons, action diagnostics, raw measurements and a sanitized shareable sample, with explicit scope labels rather than copied independent result calculations.
  • Exercise the complete bounded probe path twice from fresh isolated projects, including rejected and committed probe actions, seed/context replay, private-sentinel controls and measured two-logical-client/queued workload. Assert same-context rule equality while retaining genuinely varying timing/environment observations. Include a deliberately failing assertion and missing-report run so aggregate success requires actual complete child evidence.
  • Preserve current bootstrap/content admission behavior: run tools/check_content_admission.py --suite all, the existing Python tool regressions and a no-content server smoke using tools/run_baseline.py. Reuse export/client-artifact tooling to verify test probe controls/data are excluded when affected; do not add test nodes to the isolated ServerRoot/Timer baseline scene.
  • Document one runnable command and reset procedure in tools/README.md. Retain an explicit parent-epic review mapping each of the four criteria to actual artifacts and the accepted test-probe/payload-byte scope, checking BW-001/BW-002 evidence applicability, child dependencies and downstream readiness. Update roadmap progress through the existing documentation workflow only after execution; planning/schema validation alone is never evidence of completion.

Out of scope

  • Completing BW-004 connectivity, BW-012 multiplayer action, BW-018 durability, BW-095 content tooling, BW-097 rendering or later game mechanics.
  • Production operations dashboards, benchmark targets, deployment, or treating the finite probe as a gameplay/capacity certification.

Dependencies

Hard prerequisites: BW-003-T03, BW-003-T04

Acceptance criteria

  1. AC 1

    The documented --suite all command executes and joins every required child result with matching run/scenario/source/revision identities. Missing, stale, partial or failed child evidence makes the aggregate fail; specifications remain unexecuted.

  2. AC 2

    Two independent complete runs reproduce deterministic probe outcomes and include attributable rejection/commit traces, successful redaction controls and actual workload/environment-linked measurements for ticks, entities, per-logical-client payload bytes and queue depth.

  3. AC 3

    A deliberate assertion failure and missing-report control fail the aggregate distinctly from import/startup failure. A fresh clean aggregate then passes; no prior evidence directory is overwritten or reused as a successful new run.

  4. AC 4

    Existing content-admission, Python regressions and isolated server smoke pass with no accidental gameplay/test-control enablement. The parent review covers all four BW-003 criteria within the explicitly selected probe scope and records all remaining limitations before any status promotion.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root. The runtime-fixture checker and suite below are implementation deliverables, not existing commands.
python3 tools/verify_toolchain.py
python3 tools/extract_content_contracts.py --check
python3 tools/check_runtime_fixtures.py --suite all
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use Python 3.10+ and the native macOS ARM64 Godot executable pinned in tools/toolchain.lock.json; the checker resolves that executable rather than assuming godot is on PATH. Keep sibling mmo_docs canonical sources available. No provider, database or network service is required.
  2. Complete T01-T04 and use their committed fixtures/runners. Keep existing server.valid.json and content-admission corpora unchanged; choose fresh evidence directories for all runs and controls.

Actions

  1. Run the launch block twice and inspect aggregate manifest links, exact input/source hashes, same-context comparison, diagnostic sample and raw measurement reports.
  2. Run --suite all --control assertion-failure and --suite all --control missing-report in fresh outputs, then a clean --suite all. These aggregate controls are deliverables of this ticket.
  3. Run python3 tools/check_content_admission.py --suite all and python3 tools/run_baseline.py --role server --headless --config "$PWD/fixtures/config/server.valid.json" --smoke; review logs and the applicable client-export isolation checks.
  4. Review the four epic-criterion mappings and prerequisite applicability, then rebuild/check roadmap and inventory views using DOCS_ROOT/README.txt. Keep actual test evidence separate from documentation-validation results.

Expected results

  1. Both fresh aggregate runs pass with complete actual child evidence and reproducible probe outcomes. Deliberate controls fail visibly and never contaminate the later clean run.
  2. Regression/smoke results and parent review accurately identify the completed early diagnostic experiment; gameplay, wire-network and durability work retain their own unfinished statuses.

Reset

  1. Let bounded child processes finish; the checker must stop any timed-out child and discard its disposable project. Probe state exists only in that process.
  2. Keep prior evidence directories intact and rerun with a fresh default output directory. Restore any deliberately modified fixture only in its disposable copy; do not edit canonical sources or reuse prior results as a new execution.

Completion evidence and blockers

Required evidence: Retain two fresh aggregate runs, negative controls, a sanitized diagnostic/measurement sample, Python/admission/bootstrap/isolation regression results and an explicit BW-003 criterion-by-criterion review. Record tested source revision/hashes and scope limitations; reconcile and regenerate every affected current status/readiness view.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
