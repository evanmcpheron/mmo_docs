Complete · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-1

Implementation scope

  • Reuse the completed BW-001/BW-002 owners: tools/check_baseline.py for toolchain/source identity and bounded process handling; FContentContracts/FValidationFinding/FContentRevisions/FContentAdmission for canonical validation, compatible revisions and atomic selection; ContentAdmissionTestSupport and FContentCompatibilityRun for existing native test/report behavior. Add only the missing fixture evidence adapter, native automation cases under Source/Briarwake/Tests and tools/check_runtime_fixtures.py. Keep the existing seven tests and their exact assertion/report checks intact, using Unreal Automation and the existing WITH_EDITOR && WITH_DEV_AUTOMATION_TESTS boundary. Exclude fixture code, inputs and controls from normal Game/Server packages.
  • Select a small immutable positive/negative corpus from fixtures/content_admission/admission.json, preserving its fixture IDs, ContentValidationFixture specifications, package inputs, exact content/rules revisions and expected ValidationFinding values. Execute the real FContentAdmission boundary rather than copying admission rules or claiming that existing admission evidence already implements BW-003. Reuse ContentValidationResult for actual admission findings and expectation matching. Keep authored run_evidence unexecuted; store actual FixtureRunEvidence separately with runner, UTC time and matching revisions. A correctly rejected candidate can yield a passed test with nonempty ContentValidationResult.actual_findings and empty FixtureRunEvidence.findings; reserve failed execution evidence findings for test failures. Attach actual TestCheck assertions and engine/build/source/fixture identities in a test evidence envelope; ValidationReport remains the documentation report and is not a partial runtime envelope.
  • Provide the transient UWorld lifecycle, bounded immutable fixture selection, execution/report adapter and documented native build/launch/reset steps. Reuse tools/extract_content_contracts.py and FContentContracts for canonical TestCheck extraction if needed, preserving existing definitions and fingerprints rather than copying a schema into the runner. Distinguish build/load/startup failure, missing execution/report and executed assertion failure. Implement assertion-failure, missing-report, load-failure, startup-failure and timeout controls; require the expected stage-specific evidence so an unavailable engine cannot satisfy a control. Reject stale/foreign identities, duplicate/missing assertions and reused output directories. Integrate the evidence suite into tools/validate.py without weakening prerequisite gates.

Out of scope

  • Combat/ability execution, player connectivity, persistence, production telemetry and a generic fixture scripting language.
  • Treating authored expectations, a documentation schema check or an old Godot run as current Unreal execution evidence.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    Native execution through FContentAdmission preserves exact existing fixture IDs/encodings and immutable specifications. Actual acceptance/rejection and ContentValidationResult.actual_findings match expectations; a correctly rejected candidate records a passed FixtureRunEvidence with no blocking findings, while a deliberately wrong expectation records an executed failed assertion and failed run evidence with findings.

  2. AC 2

    Unexecuted specifications retain status unexecuted, null runner_id/completed_at and empty execution findings. Separate passed/failed evidence requires an actual runner, valid UTC completion time, matching tested content/rules revisions and canonical finding constraints. Unknown scenario encodings, missing required fields, stale/mismatched identities and duplicate/missing assertion records are rejected. Runtime envelopes do not masquerade as incomplete ValidationReport objects.

  3. AC 3

    Clean execution produces complete attributable records and returns success only after actual assertion/report verification. Each failure control and a child timeout returns nonzero with the correct stage; none fabricates a gameplay pass or changes immutable specifications.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT (workspace containing Briarwake.uproject).
python3 tools/check_baseline.py build
python3 tools/check_runtime_fixtures.py --suite evidence
Final complete native automated route: python3 tools/validate.py

Setup

  1. Use the existing game and mmo_docs checkouts. Initial task bases: game origin/main 32a98048e29a0cacea61a6f02f33ad609bc3d84e; docs origin/main 20a76fcf026fd89f05da30bc63227a40689d2fe7. BW-001/BW-002 remain Complete; their canonical admission owners are unchanged and their original seven-test aggregate still executes separately.
  2. Pinned macOS ARM64 Development, UE 5.8.3 Launcher CL 58210709, Xcode 27.0 build 27A266a; source Server engine commit 396c9f059903aed5fec78ecd3d437a40c6415368 plus the approved lock-file patch. tools/toolchain.lock.json and each run environment record own exact identities.
  3. fixtures/runtime/evidence.json selects compatible, reordered-forward-references and unknown-class from the existing immutable admission corpus. FRuntimeFixtureEvidence reuses FContentContracts, FContentAdmission, ContentAdmissionTestSupport and FContentCompatibilityRun. TestCheck is extracted canonically; no fixture schema or admission rule is copied.
  4. The native Briarwake.RuntimeFixtures.Evidence test creates and destroys a transient UWorld; no project map or interactive MCP connection is needed. Fixture code uses WITH_EDITOR && WITH_DEV_AUTOMATION_TESTS. Actual source/module/input hashes and engine identity are in retained run.json files; authored specifications stay unexecuted.

Actions

  1. Run the evidence launch twice in fresh output directories (or use the clean and recovery stages in python3 tools/validate.py). Inspect automation/index.json and native/fixture-evidence.json: 61 exact checks, 59 canonical TestCheck records, three original specifications and separate actual results/execution evidence. Compare nonce/time and source/module/input/content/rules identities.
  2. Run python3 tools/check_runtime_fixtures.py --suite evidence with --control assertion-failure, missing-report, load-failure, startup-failure and timeout, one at a time. Each uses a new output and must return nonzero with control_verified true. Startup/load stop before admission; assertion failure records actual failed evidence; missing-report retains verified execution in retained-control-native; timeout reaches the native execution marker before owned process-group termination.
  3. Run clean again. Inspect immutable input hashes and world-destroyed. Run python3 -m unittest discover -s tools -p test_runtime_fixtures.py and inspect the native invalid-specification/invalid-evidence checks for missing/unknown fields, wrong revisions, fabricated runner/time, invalid UTC and invalid finding/status combinations.
  4. Use disposable in-memory copies of a real native report to attempt stale/foreign identities, unknown scenario, missing runner/time, mismatched rules and missing/duplicate assertions/fixtures. Reuse an existing --output path and confirm rejection with all prior file hashes unchanged. Invoke each control with --engine artifacts/deliberately-unavailable-engine and confirm preflight failure cannot satisfy the control.

Expected results

  1. Clean execution passes only after native assertions, exact report sets, real runner/time, identity matching and immutable specifications are verified. Expected admission rejection produces actual_findings while passed execution findings stay empty.
  2. An intentionally inverted execution expectation produces failed ContentValidationResult and FixtureRunEvidence with fixture_assertion findings while its authored expectation remains unchanged. Wrapper failure follows actual reports even when Unreal returns process code zero.
  3. Every deliberate failure control returns nonzero at its documented stage; unavailable engines and missing execution never qualify. Malformed/foreign records and reused outputs are rejected; fresh clean recovery succeeds. Normal Game/Server packages contain no fixture code, controls or fixture inputs.

Reset

  1. The native test calls DestroyWorld and verifies garbage collection. Timeout kills and reaps the owned child process group. No maps, assets, caches or canonical specifications are changed as reset.
  2. Keep prior output directories. Rerun with a fresh default directory under GAME_ROOT/artifacts or a new --output beneath that root. Retained evidence under DOCS_ROOT/validation/tickets/BW-003-T01 remains historical; never overwrite it.
