Epic acceptance criteria: BW-003-AC-1

Implementation scope

  • Reuse BW-001 build/revision/smoke ownership and BW-002 content-admission/contract validation ownership once implemented. Current Source/Briarwake contains only the primary module registration/header; no admission or test owner exists to reuse today. Add the smallest native C++ automation tests under the module test boundary and tools/check_runtime_fixtures.py as a bounded process/report wrapper, using Unreal Automation rather than introducing a second test framework. Keep test code and fixture data out of normal packaged client/server behavior.
  • Run a small positive/negative ContentValidationFixture corpus against the real BW-002 admission boundary. Preserve exact fixture/scenario IDs, content/rules revisions, expected ValidationFinding records and immutable source hashes. Store actual FixtureRunEvidence separately from specifications, with named runner, UTC completion time, executed TestCheck assertions and build/engine/source identity in an evidence envelope. Reuse canonical definitions and referenced primitives; do not duplicate their schema policy in the runner or add gameplay handlers.
  • Create the transient UWorld/test lifecycle, committed finite fixture inputs, report reader and documented native command/build steps needed by the evidence suite. A report must distinguish build/load/startup failure, missing execution/report and executed assertion failure. Add assertion-failure, missing-report, load-failure and startup-failure controls plus timeout handling; inspect runner return status and actual assertion records rather than trusting an engine exit code alone.

Out of scope

  • Combat/ability execution, player connectivity, persistence, production telemetry and a generic fixture scripting language.
  • Treating authored expectations, a documentation schema check or an old Godot run as current Unreal execution evidence.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    The evidence suite executes compatible and incompatible content fixtures through BW-002, preserves exact IDs/encodings and records actual findings separately from expectations. A deliberately wrong expected finding fails an executed assertion.

  2. AC 2

    Unexecuted specifications retain status unexecuted with null runner_id/completed_at and empty execution findings; passed/failed records require an actual runner/time and exact tested content/rules revisions. Unknown scenario encodings, missing required fields and stale/mismatched report identities are rejected.

  3. AC 3

    Clean execution produces complete attributable records and returns success only after actual assertion/report verification. Each failure control and a child timeout returns nonzero with the correct stage; none fabricates a gameplay pass or changes immutable specifications.

Expected results

  1. Two clean native runs produce independently attributable evidence; intentional assertion failure is an executed failed test, while build/load/startup/timeout/missing-report paths never claim a pass.
