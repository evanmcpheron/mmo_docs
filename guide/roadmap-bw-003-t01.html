Not Started · Parent epic: BW-003 · Repeatable runtime fixtures and diagnostics

Epic acceptance criteria: BW-003-AC-1

Implementation scope

  • Add tools/check_runtime_fixtures.py --suite evidence and a bounded headless runner under tests/runtime_fixtures/, with checked-in fixtures/runtime_fixtures/ inputs and tools/test_runtime_fixtures.py coverage. Reuse tools/check_content_admission.py process isolation, timeout, source/input hashing and strict complete-report checks, plus tools/check_baseline.py stage/outcome primitives; extend existing helpers only where the same meaning is shared.
  • Run representative existing content-admission acceptance/rejection behavior through its current owner, content/content_admission.gd. Reuse ContentValidationFixture, ContentValidationResult, FixtureScenarioKind, FixtureRunEvidence, ValidationFinding and TestCheck from the existing canonical extraction; extend tools/extract_content_contracts.py only for newly required definitions and their local $ref closure. Do not copy canonical definitions into a second hand-maintained schema.
  • Keep authored specifications immutable and unexecuted. Write separate per-run actual evidence with fixture/scenario identity, scenario/input hashes, runner identity, completion time, exact content/rules revisions, engine/build/source identity, evaluated assertions and actual findings. A tool-local provenance envelope may associate these records; it is not a new gameplay, network or persistence contract.
  • Include disposable import-failure, startup-failure, missing-report and assertion-failure controls, and enforce unique case identities, matching revisions and complete assertion coverage. Preserve the baseline distinction between a failed build/startup, assertions not executed and executed assertion failure; never manufacture canonical failed run evidence with a named runner/time when no fixture ran. Document the command, records and reset procedure in tools/README.md.

Out of scope

  • Gameplay execution, a complete AbilityExecutionFixture runner, content authoring/import tools and retroactively rewriting historical BW-001/BW-002 evidence.
  • Promoting an authored expectation, schema check or child exit code alone to runtime success; changing canonical registry definitions or existing admission/readiness policy.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    An actual named Godot runner evaluates positive and negative content fixtures and emits matching ContentValidationResult plus valid FixtureRunEvidence. A correctly observed expected rejection passes its test; an unexpected result produces failed evidence with actual findings.

  2. AC 2

    Authored run_evidence retains status unexecuted, null runner_id/completed_at and empty findings before and after execution. Actual passed/failed records identify the exact executed fixture, revisions, runner and UTC time separately from expectations.

  3. AC 3

    Unknown scenario tokens, missing/extra canonical fields, invalid evidence nullability, conflicting content/rules revisions, duplicate/missing assertion identities and forged authored pass claims fail visibly without a passing execution result.

  4. AC 4

    Each failure control exits nonzero and preserves its stage/log/provenance record. Import/startup failure and missing reports cannot appear as a completed passing fixture; the deliberate assertion failure proves an assertion actually ran. A subsequent clean run passes independently.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root. The runtime-fixture checker and suite below are implementation deliverables, not existing commands.
python3 tools/verify_toolchain.py
python3 tools/extract_content_contracts.py --check
python3 tools/check_runtime_fixtures.py --suite evidence
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use Python 3.10+ and the native macOS ARM64 Godot executable pinned in tools/toolchain.lock.json; the checker resolves that executable rather than assuming godot is on PATH. Keep sibling mmo_docs canonical sources available. No provider, database or network service is required.
  2. Use the ticket-supplied evidence corpus, bounded runtime runner and disposable failure controls. Reuse safe-static and invalid-content cases from fixtures/content_admission/ without modifying their source expectations.

Actions

  1. Run the launch block and open its reported run.json, immutable authored specifications, per-case actual evidence and captured engine logs.
  2. Run the checker again with --suite evidence --control import-failure, then startup-failure, missing-report and assertion-failure, using a fresh default output directory for each. These options are deliverables of this ticket.
  3. Run a final clean --suite evidence invocation and compare input hashes and canonical evidence fields with the source corpus.

Expected results

  1. The clean run contains actual evaluated assertion results with attributable revisions and runner/time; authored specifications remain unchanged and unexecuted.
  2. Each deliberate failure is observable, nonzero and correctly classified. A build/import/startup problem records assertions not executed; the assertion control records an executed failure. No stale output satisfies a fresh run.

Reset

  1. Let bounded child processes finish; the checker must stop any timed-out child and discard its disposable project. Probe state exists only in that process.
  2. Keep prior evidence directories intact and rerun with a fresh default output directory. Restore any deliberately modified fixture only in its disposable copy; do not edit canonical sources or reuse prior results as a new execution.

Completion evidence and blockers

Required evidence: Retain clean and negative-control reports, actual per-case canonical evidence, source/scenario hashes, logs and Python regression results. Evidence must distinguish observed expected rejection from an execution failure and must not certify gameplay.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
