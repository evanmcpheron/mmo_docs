Epic acceptance criteria: BW-003-AC-1

Implementation scope

  • Reuse the completed BW-001/BW-002 owners: tools/check_baseline.py for toolchain/source identity and bounded process handling; FContentContracts/FValidationFinding/FContentRevisions/FContentAdmission for canonical validation, compatible revisions and atomic selection; ContentAdmissionTestSupport and FContentCompatibilityRun for existing native test/report behavior. Add only the missing fixture evidence adapter, native automation cases under Source/Briarwake/Tests and tools/check_runtime_fixtures.py. Keep the existing seven tests and their exact assertion/report checks intact, using Unreal Automation and the existing WITH_EDITOR && WITH_DEV_AUTOMATION_TESTS boundary. Exclude fixture code, inputs and controls from normal Game/Server packages.
  • Select a small immutable positive/negative corpus from fixtures/content_admission/admission.json, preserving its fixture IDs, ContentValidationFixture specifications, package inputs, exact content/rules revisions and expected ValidationFinding values. Execute the real FContentAdmission boundary rather than copying admission rules or claiming that existing admission evidence already implements BW-003. Reuse ContentValidationResult for actual admission findings and expectation matching. Keep authored run_evidence unexecuted; store actual FixtureRunEvidence separately with runner, UTC time and matching revisions. A correctly rejected candidate can yield a passed test with nonempty ContentValidationResult.actual_findings and empty FixtureRunEvidence.findings; reserve failed execution evidence findings for test failures. Attach actual TestCheck assertions and engine/build/source/fixture identities in a test evidence envelope; ValidationReport remains the documentation report and is not a partial runtime envelope.
  • Provide the transient UWorld lifecycle, bounded immutable fixture selection, execution/report adapter and documented native build/launch/reset steps. Reuse tools/extract_content_contracts.py and FContentContracts for canonical TestCheck extraction if needed, preserving existing definitions and fingerprints rather than copying a schema into the runner. Distinguish build/load/startup failure, missing execution/report and executed assertion failure. Implement assertion-failure, missing-report, load-failure, startup-failure and timeout controls; require the expected stage-specific evidence so an unavailable engine cannot satisfy a control. Reject stale/foreign identities, duplicate/missing assertions and reused output directories. Integrate the evidence suite into tools/validate.py without weakening prerequisite gates.

Out of scope

  • Combat/ability execution, player connectivity, persistence, production telemetry and a generic fixture scripting language.
  • Treating authored expectations, a documentation schema check or an old Godot run as current Unreal execution evidence.

Dependencies

Hard prerequisites: BW-001, BW-002

Acceptance criteria

  1. AC 1

    Native execution through FContentAdmission preserves exact existing fixture IDs/encodings and immutable specifications. Actual acceptance/rejection and ContentValidationResult.actual_findings match expectations; a correctly rejected candidate records a passed FixtureRunEvidence with no blocking findings, while a deliberately wrong expectation records an executed failed assertion and failed run evidence with findings.

  2. AC 2

    Unexecuted specifications retain status unexecuted, null runner_id/completed_at and empty execution findings. Separate passed/failed evidence requires an actual runner, valid UTC completion time, matching tested content/rules revisions and canonical finding constraints. Unknown scenario encodings, missing required fields, stale/mismatched identities and duplicate/missing assertion records are rejected. Runtime envelopes do not masquerade as incomplete ValidationReport objects.

  3. AC 3

    Clean execution produces complete attributable records and returns success only after actual assertion/report verification. Each failure control and a child timeout returns nonzero with the correct stage; none fabricates a gameplay pass or changes immutable specifications.

Actions

  1. Run the launch command twice into fresh outputs; inspect fixture hashes, exact assertion sets, fixture/scenario IDs, runner/time and separate engine/build/content/rules identities. Confirm actual native positive/negative admission results and inspect ContentValidationResult.actual_findings separately from FixtureRunEvidence.findings.   2. Run the same command with --control assertion-failure, then --control missing-report, --control load-failure, --control startup-failure and --control timeout, each in a fresh output. Inspect native logs, wrapper status and which stages actually ran. Run clean again.
  3. Use disposable fixture/report copies to try unknown scenario values, absent required evidence fields, a fabricated passed record without runner/time and mismatched source/content revisions. Inspect rejection and unchanged original specifications.

Expected results

  1. Two clean native runs produce independently attributable evidence; intentional assertion failure is an executed failed test, while build/load/startup/timeout/missing-report paths never claim a pass.
  2. Invalid fixture/report inputs fail visibly, prior outputs remain intact and clean recovery succeeds.

Reset

  1. The runner must stop timed-out child processes and tear down its transient UWorld, fixture clock, seed, queue and test-owned state. Normal client/server launches must remain unaffected.
  2. Retain previous logs/reports; rerun into a new default output directory. Controls modify only disposable inputs. Never overwrite prior evidence or modify canonical sources, user maps or assets to reset a run.
