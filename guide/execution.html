Ability execution contracts

Mechanics, governing rules, edge cases and acceptance criteria.

Scope of the executable rule model

The v2 data separates authored intent, a numerical primary-effect profile, a specialization state contract and a binding/review status. A profile specifies cast time, cooldown, resource-cost policy, effect magnitudes and structured operations. It is not a substitute for coding every named secondary behavior.

The package contains 330 inherited named ability entries and 63 prototype execution profiles. All entries have a selected profile and numerical timing/cost defaults instead of v1's TBD_BALANCE fields. Charge Lance is supplied as an explicit example of a dynamic charge-based contract. Other named secondary behaviors remain flagged for individual binding and tests. They must not be automatically enabled because a table row happens to contain a damage coefficient.

A runtime must reject an entry with unresolved required bindings. Do not execute prose, ask a language model to interpret ability text during gameplay, or let clients choose missing parameters.

  "build_version": 8,
  "content_version": "2.0.0-design",
  "target_entity_id": "entity-example",
  "aim_point": null,
  "aim_direction": null,
  "requested_charge_spend": 4
}

The server derives the character from the authenticated session and compares any supplied ID; it never trusts the field as ownership proof. The client cannot supply damage, target health, cooldown completion, resource balance, random seed or authoritative position. Reject NaN/infinite coordinates, oversized arrays, invalid IDs and stale session epochs.

A repeated (session_epoch, command_sequence) returns the prior acceptance/rejection/result reference. It does not re-execute. Restrict command rate independently of GCD. Queue at most one future eligible action and preserve its sequence.

Profiles are defaults. A specific override must name the changed field and its allowed range. Never combine two full independent profile budgets simply because an ability has both damage and healing flavor.

Cost and cooldown semantics

For mana users, the profile's mana percentage applies to maximum mana. For non-mana users, the prototype conversion is five resource units per percentage point, capped at 30. Ordinary weapon generators have class-specific costs: Energy/Focus users pay their declared generator cost; Rage generators generally pay no Rage and generate only on a valid hit. A specialization state contract governs additional charges or marks; it never creates a second contradictory cost.

The resolved definition replaces this prototype conversion with explicit class-specific fields before runtime certification. Price displays use resolved values, not a generic tooltip guessed from the class name.

Release-commit spells reserve resources at acceptance and spend at release. Channels commit at start. Multi-charge abilities consume one charge and recharge sequentially unless explicitly declared otherwise. Cooldowns belong to stable ability families and survive talent removal or specialization switching.

RESOURCE_RESTORE / EXCHANGE Capped amounts; no nonlethal-cost bypass or fake effective-heal trigger
REVIVE Correct alive/dead relation, encounter charges and combat permission
SET_FORM / PASSIVE Server-owned capability state; no duplicated resource or equipment budget
RESOLVE_PATTERN / RESOLVE_PERFORMANCE Named specialized handler, finite input count and total output budget
RETURN_ANCHOR / REVEAL Authorized destination/information only; not a shortcut around world ownership

Specialized resolvers need finite enumerated states and an implementation, not arbitrary scripts supplied by the client. Prefer a small explicit operation registry and a few class-specific handlers to a universal programming language inside the combat system.

Modifier order

Resolve base profile → specialization substitution → selected exclusive transformation → additive same-family talent ranks → declared multiplicative talent families → equipment-budgeted effects → active source buffs → PvP overrides → clamp caps → target defenses at effect resolution.

Mutually exclusive transforms cannot both apply. Replacements remove the original effect rather than retaining both. Additive modifiers in the same family sum before multiplying; modifiers from independent families multiply only when explicitly allowed. A 6% talent and a 4% talent in one family produce 10%, not 10.24%.

A talent can alter output coefficient, cost, timing, targeting geometry, resource generation, required sequence, movement permission or an explicit triggered operation. It may not edit a hidden arbitrary property on a player node. Validate affected fields against an allowlist.

This is a partial example, not a complete 118-point build. Validate ownership, class/faction, earned point balances, level gates, all prerequisites, exclusive groups, rank bounds, unlocked referenced abilities, active encounter state and expected version before committing anything. Returning an error preserves the old build in full.

Example: Pyromancer consumption

Burning records remaining authored damage, next tick and owner. A detonation selects only that caster's eligible effect on a valid target. In one simulation action, mark the consumed budget, remove or reduce the periodic effect, calculate the finisher and emit the result. The consumed damage cannot tick again, count as a second kill, or trigger its own resource generator. Other Pyromancers' effects are unaffected.

Example: Grovekeeper seed consumption

A seed has stage, expiry, remaining healing budget and owner. Open Bloom consumes the selected seed and converts the declared remaining budget into immediate healing using its specialization coefficient. Cancel the next scheduled tick before resolving consumption. If another heal fills the target first, excess becomes overhealing; it cannot be converted into free resource or automatically jump to another target.

Replication events

Use accepted/rejected command responses; cast started/interrupted/released; entity spawned/despawned; effect applied/updated/removed; resource snapshot; combat result; death/revival; build accepted; durable reward committed. Event payloads contain server tick, stable IDs, version and outcome values, not serialized Godot objects.

Animation is derived from events and gameplay state. A two-frame animation variant cannot cause two server attacks. Clients interpolate presentation and predict local input where safe; they do not reproduce authoritative damage rolls.

Data and runtime gates

The included tests verify schema-like structural requirements, IDs, levels, tree capacity and reference integrity. They do not execute all class-specific handlers. Before an ability is marked runtime-ready, require tests for rejection, normal use, interruption, duplicate request, resource boundary, invalid target, PvP control, respec, death and disconnect. Before a talent is enabled, test it alongside each competing transformation and any affected gear effect.
