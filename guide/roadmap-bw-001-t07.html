Complete · Parent epic: BW-001 · Reproducible client and headless project

Epic acceptance criteria: BW-001-AC-4

Implementation scope

  • Add tools/check_baseline.py as the single automated clean verification entry point. It verifies the lock, builds in an isolated workspace, inspects the client artifact, launches the exported headless smoke mode, and checks ready identity, no client/player scene and bounded heartbeat assertions.
  • Write a machine-readable run record with source/toolchain/fixture revisions, runner environment, artifact hashes, commands/stages, process exit statuses, timeout information and redacted log paths. Keep build outcome, runtime execution state and assertion outcome separate; Not Executed has no passing assertion result.
  • Provide isolated --case pass, build-failure, assertion-failure, startup-failure and timeout controls. Inject failures only in disposable copies: an actual failed import/export, a deliberately false smoke assertion, invalid startup config, and a bounded hung process. Include the fixture controls and cleanup so each case is ready to run.
  • Document a clean macOS automation invocation, prerequisites and where run evidence is retained. Use the same command locally and in any configured automation runner, with no provider/deployment dependency.
  • Include packaged-client launch as a required manual evidence item alongside automation. A headless run cannot claim the GUI was visually verified, and bootstrap smoke evidence cannot substitute for BW-003 gameplay/runtime fixtures.

Out of scope

  • Gameplay fixture framework, seeded world simulation, throughput/capacity benchmarks, database tests or full release/deployment pipelines.
  • Marking BW-001 or any ticket Complete from planning, schema validation, an unexecuted test specification or a started process without executed assertions.

Dependencies

Hard prerequisites: BW-001-T06

Acceptance criteria

  1. AC 1

    A clean macOS pass run records a successful build and client inspection, an actually executed exported-server assertion run with a passing result, and returns zero.

  2. AC 2

    The build-failure case records build Failed and runtime Not Executed with no runtime pass; the assertion-failure case records build Passed, runtime Executed/Failed and nonzero exit.

  3. AC 3

    Startup failure and timeout return nonzero with their stage and reason, terminate owned processes, and cannot be reported as passing executed smoke checks. Assertion execution state reflects whether the assertion runner was actually reached.

  4. AC 4

    Every run retains actual commands, revisions, artifact identities when produced and redacted logs; failed-stage output remains available and a fresh pass after failure is independent of prior output.

  5. AC 5

    Evidence instructions require the packaged macOS client capture and actual headless run before proposing epic completion; Linux/Windows and gameplay checks remain explicitly unverified.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: briarwake (game repository root).
python3 tools/check_baseline.py --case pass --output artifacts/check-pass
python3 tools/check_baseline.py --case build-failure --output artifacts/check-build-failure
python3 tools/check_baseline.py --case assertion-failure --output artifacts/check-assertion-failure
python3 tools/check_baseline.py --case startup-failure --output artifacts/check-startup-failure
python3 tools/check_baseline.py --case timeout --output artifacts/check-timeout
python3 tools/check_baseline.py --case pass --output artifacts/check-pass-after-failures
python3 -m unittest discover -s tools -p 'test_*.py' -v

Setup

  1. Complete T06. Use native macOS ARM64, Python 3.10+, pinned Godot/editor export templates and stock arch/lipo. Follow briarwake/tools/README.md; no provider, deployment, account or network service is required. Use the same command in a macOS automation runner; none is configured in this repository.
  2. Give every run a new output directory. Only committed synthetic configuration fixtures are used. Each build takes an isolated source snapshot with no import cache; current uncommitted inputs are hashed and the source revision is marked dirty. Preserve existing tools, cache, outputs and user edits.

Actions

  1. Execute all five cases, retain actual command exits and inspect run.json, client-inspection.json when produced, build/manifest.json and both logs/ trees. Only pass returns zero; all four failure controls return one.
  2. Verify build-failure retains the invalid-script import diagnostics, build Failed and runtime Not Executed with null assertion_result. Verify assertion-failure builds/inspects successfully, reaches exported assertions and records Executed/Failed; the deliberately false heartbeat assertion fails even though the server itself exits zero.
  3. Verify startup-failure uses server.missing-rules.json and exits before bootstrap assertions. Verify timeout reaches bootstrap/readiness but cannot complete smoke, records the ten-second runtime deadline and nonzero killed exit, and reaps the owned process group. Confirm recorded process IDs and child processes are no longer active.
  4. Run pass again with fresh output after all failures. Compare input/artifact identities, current record timestamps, independent output paths and removed build snapshots. Existing output must be rejected rather than reused.
  5. Read manual_client.launch_command in the final pass run.json. Execute that exact command from /private/tmp using absolute paths. Capture the visible Briarwake client baseline window and Quit control, click Quit and retain exit zero. Record the source manifest, client bundle hash, capture path and post-launch hash in separate manual evidence; automation leaves its own GUI state Not Executed.
  6. Archive every run JSON, manifests, redacted logs, case exits, regression results and packaged-client evidence under mmo_docs/validation/tickets/BW-001-T07/; game applications may remain in local artifacts/ identified by their hashes.

Expected results

  1. A pass proves a clean isolated macOS build, matching client inspection and actual exported-server identity, headless/Dummy drivers, server-only scene, no client/player, ordered bounded heartbeats and completed passing smoke assertions.
  2. Build failure, executed assertion failure, startup failure and timeout remain distinguishable by stage, reason, process exit and assertion execution state. Not Executed has no passing assertion result. Failed-stage output is retained.
  3. Timeout terminates owned processes; failure fixtures never alter the source checkout or installed toolchain. A fresh pass after failure is independent of prior output.
  4. The manual capture identifies the same final pass client build. Both actual headless execution and packaged-client capture are required before proposing epic completion; Linux/Windows, Intel macOS, gameplay/BW-003, multiplayer and capacity remain unverified.

Reset

  1. Quit the owned client and confirm recorded headless process IDs/descendants exited. Archive evidence first; remove only disposable output/workspaces created for these runs. Retain failure evidence and preserve source, installed tools, pre-existing cache and unrelated output.

Completion evidence and blockers

Required evidence: Actual clean pass, build failure, executed assertion failure, startup failure and timeout records/logs, plus final artifact identifiers and a packaged-client launch capture.

Blockers: None recorded; see dependencies.
