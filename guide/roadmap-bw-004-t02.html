Not Started · Parent epic: BW-004 · Dedicated connectivity and bounded command admission

Epic acceptance criteria: BW-004-AC-1, BW-004-AC-2

Implementation scope

  • Owner: a server-owned restricted test admission policy wired explicitly through native GameMode PreLogin/PreLoginAsync, Login/PostLogin and Logout; the T01 route remains transport only. UE 5.8.3 source warns that PreLogin and Login may be separated by significant time and asynchronous admission must complete its callback. Revalidate expiry/ownership at final admission and complete all success/failure paths without blocking the game thread.
  • Use a private configured test adapter with server-registered opaque one-use proofs and server-owned identity, purpose/audience, expiry and revocation state. Bind account/character, process and epoch to the accepted connection, never to URL/payload identity or an OnlineSubsystem ID alone. Issue/validate canonical opaque SessionToken handles; revoke stale handles/epochs on logout or replacement. Test material and adapter controls are not public gameplay endpoints or distributed credentials.
  • Reuse FContentContracts and canonical extraction for the needed SessionAuthority, SessionToken, SecurityPolicy and CommandContext closure. Negotiate existing engine/message compatibility and supported content/rules revisions using FContentCompatibility where appropriate; do not invent a parallel wire protocol or equate content, rules, client build and database revisions. Required positive lifetimes and request limits come from explicit fixture configuration; missing configuration disables admission.
  • Current FContentContracts::DecodeAbilityCommand and FContentCompatibility provide structural/revision checks, not connection authentication. FSqliteProbeStore already implements durable ClaimOwnership/RevokeOwnership and receipts within BW-018; preserve that owner and accepted evidence, without making SQLite or production handoff a dependency of this transient non-economic test session. Keep all gameplay command routes disabled until the T03/T04 boundary is wired.

Out of scope

  • Public credential/provider integration, economic characters, durable exclusive sessions/transfer/recovery (BW-019/BW-018), gameplay legality, command limits beyond admission and a new authentication protocol or persistence abstraction.

Dependencies

Hard prerequisites: BW-001, BW-002, BW-004-T01

Acceptance criteria

  1. AC 1

    Two separate clients with accepted compatible test proofs receive distinct server-bound authorized sessions and opaque handles. Each connection resolves only its server-assigned test identity and epoch; client-supplied IDs, roles, expiry or consumed flags cannot grant authority.

  2. AC 2

    Missing, unknown, expired, reused, wrong-purpose/audience and incompatible proofs/versions reject before an authorized character/session or gameplay mutation is created. Expiry between preliminary and final admission rejects; missing required configuration and asynchronous failures complete with a bounded safe client reason.

  3. AC 3

    Logout/replacement revokes the prior handle and epoch; a stale or foreign handle cannot act as another session. Credentials and provider material stay out of client artifacts, logs, travel diagnostics and other-client responses. Actual connected observations establish parent AC1; pure policy tests alone do not.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Not Run — Manual QA Pending. Reuse the exact T01 dedicated/two-client runbook after T02 documents the private test-proof setup, credential-safe admission control and session-status display. These controls are future implementation; no current command is claimed to authenticate a client.

Setup

  1. Complete T01 and use its same /Engine/Maps/Entry connection scenario, pinned executables and local backend. Configure the trusted test adapter privately with two distinct test identities, explicit lifetimes/limits and compatible revisions; keep proof material out of command lines and logs.

Actions

  1. Admit both clients using separate valid proofs and inspect redacted session/epoch ownership. Attempt a second use, missing/expired proof, wrong purpose/audience and incompatible protocol/content; expire a proof between preliminary and final admission using the delivered bounded control.
  2. Logout/rejoin or replace a test session, then try its old handle and another client identity. Remove a required admission setting for a separate bounded attempt; inspect client rejection and unchanged authoritative state, then restore only task-local configuration.

Expected results

  1. Only accepted compatible proofs create distinct authorized test sessions. Invalid attempts and stale/foreign handles create no authority or gameplay mutations; errors reach the affected client without disclosing credentials or another session. The delivered runbook records actual values and observations.

Reset

  1. Stop only the task-owned server/clients, release their ports and remove only disposable scenario state beneath ignored artifacts/. Restore any task-local network emulation. Preserve existing assets, configuration, build directories, databases and prior evidence.

Completion evidence and blockers

Required evidence: One concise PR/result summary: deterministic admission/expiry/ownership rejection tests, affected compilation and the T01 two-client scenario extended only for credential/negotiation cases. Record server-authorized session identities without token material, client failure observations and exact revisions/settings. No executed test or passing evidence exists from this split.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
