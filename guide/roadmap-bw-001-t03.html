BW-001-T03 · Start a player-free headless server with revision identity

Complete · Parent epic: BW-001 · Reproducible client and headless project

Epic acceptance criteria: BW-001-AC-2

Implementation scope

  • Create res://scenes/server/server_root.tscn with a plain Node root and bounded bootstrap heartbeat. Select this root before loading the client shell when --role server is requested.
  • Extend tools/run_baseline.py with --role server --headless, --config and --smoke. Normal mode stays alive until stopped; smoke mode confirms readiness and a bounded number of heartbeat iterations, then exits. This is a bootstrap heartbeat, not gameplay simulation.
  • Add fixtures/config/server.valid.json using the canonical ServerConfiguration fields and explicit test-only values, including independently identified rules_version and content_version. Carry build revision separately from those two version domains; capture the source commit and mark a dirty development checkout honestly.
  • Emit a machine-readable server-ready record containing build, rules and content revisions, selected role and headless status. Supply an observable bootstrap check of the scene tree and zero local-player count without loading graphics-dependent resources. The export ticket will embed this identity in built artifacts.

Out of scope

  • Multiplayer transport, authentication, economic characters, database access, authoritative game ticks or gameplay fixtures (BW-002/BW-003/BW-004).
  • Production diagnostics/metrics or content admission; bootstrap fixture versions do not certify compatible gameplay content.

Dependencies

Hard prerequisites: BW-001-T02

Acceptance criteria

  1. AC 1

    The normal server command starts with no window or graphics requirement and stays alive without any client connection or local player.

  2. AC 2

    The server-ready record reports nonempty build, rules and content revisions with separate meanings and values traceable to the checkout and supplied fixture.

  3. AC 3

    The smoke command observes the server root, absence of the client scene and zero players, executes its bootstrap assertions and exits zero within a documented timeout.

  4. AC 4

    Changing only a fixture rules/content revision in a temporary copy changes only that reported version domain; build identity remains attributable to the same source.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: /Users/le-evanmcpheron/Documents/Godot/briarwake (the game Git checkout).
python3 tools/run_baseline.py --role server --headless --config fixtures/config/server.valid.json
python3 tools/run_baseline.py --role server --headless --config fixtures/config/server.valid.json --smoke
Main scene: res://scenes/bootstrap.tscn; selected server scene: res://scenes/server/server_root.tscn
Optional pinned engine override: append --engine "/path/to/Godot.app/Contents/MacOS/Godot".

Setup

  1. Complete BW-001-T02. Use the locked official Godot 4.7.2 engine and native macOS ARM64/Python 3.10+ in a normal local session with Godot settings/certificate access. No clients, credentials, network listener or database are required.
  2. Keep the game checkout unchanged during revision comparison. Use fixtures/config/server.valid.json, whose canonical ServerConfiguration keys and bootstrap-test-* values are explicit test fixtures. T03 reads only the JSON object and nonempty rules/content labels; T04 owns complete configuration validation.
  3. For identity comparison, follow the executable Python example in briarwake/tools/README.md, Run the headless server baseline. It makes external temporary copies and changes rules_version and content_version separately without modifying the game checkout.

Actions

  1. Start normal mode, retain stdout/stderr and inspect server-bootstrap-check and server-ready JSON. Observe at least five one-second server-heartbeat iterations, confirming the process is still alive beyond the three-iteration smoke boundary. Stop it with Ctrl+C and verify no owned Godot process remains.
  2. Run smoke mode and retain both scene checks, exactly three timer events, the server-smoke Passed record and Baseline server exited with status 0. The editor import has a 120-second limit; the subsequent runtime has a separate 10-second timeout.
  3. Run the README comparison example. Compare the baseline, changed-rules and changed-content server-ready records. Record game HEAD, dirty status and file hashes with the actual commands/environment.
  4. In a disposable project copy, verify server startup with the client scene/assets absent. Add an extra plain Node to server_root.tscn in that copy and confirm the scene check fails before readiness. Separately pause the Timer in that copy and confirm the smoke launcher times out nonzero with no passing smoke record and no owned runtime left behind. Keep the canonical project unchanged.

Expected results

  1. The normal server uses headless display and Dummy audio, creates no OS window and stays alive without peers. The scene check lists only /root/ServerRoot and /root/ServerRoot/BootstrapHeartbeat. The engine-owned root Window is excluded; the strict two-node allowlist establishes zero local players without inventing a player registry. The client shell is not cached.
  2. Each readiness record reports role server, headless true, full Git HEAD with -dirty for a changed/untracked checkout, and the two exact fixture version labels. Build identity describes source, not a packaged artifact hash; export identity belongs to T05.
  3. Smoke actually executes startup/final scene assertions and three one-second Timer events, then exits 0 within the runtime timeout. This is bootstrap liveness evidence, not a gameplay tick, renderer, multiplayer or capacity test.
  4. Changing rules_version affects only that ready field; changing content_version affects only that ready field. Build revision stays identical. Unexpected scene nodes fail the bootstrap check, while a stalled heartbeat fails via the launcher timeout; neither can produce passing smoke evidence.

Reset

  1. Stop only owned normal-mode processes (Ctrl+C normally returns launcher status 130) and confirm no owned child remains. Temporary comparison files are automatically removed by the README example. Remove only disposable copies created for negative controls after retaining their logs.
  2. Preserve the canonical fixture, game checkout, existing .godot cache and installed toolchain. No gameplay state or network resources need resetting.
