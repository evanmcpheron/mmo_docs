Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-1

Implementation scope

  • Create docs/architecture/authority-boundaries.md in GAME_ROOT. Inspect the current scenes/bootstrap.gd, scenes/server/server_root.gd, scenes/server/server_configuration.gd and tools/run_baseline.py; distinguish these implemented bootstrap owners from future world, session and durable owners.
  • Map movement/collision and combat resources, casts, cooldowns, statuses, summons and debt to the owning world process; map items, currency, applied builds and progression to their canonical durable records; map interpolation, animation, rendering and audio to client presentation. Record command entry, authoritative mutation, recipient projection and teardown/recovery responsibility for each.
  • Name the one-session-epoch invariant, durable acknowledgement boundary, transfer/reconnect fencing, and build-change preservation of resources/cooldowns/debt. Describe required future lifecycle behavior without implementing those systems or claiming a database exists.
  • Link the canonical contracts and identify the narrow admission/serialization owners to be added by this epic. Keep bootstrap build_revision and configuration rules_version/content_version ownership intact; document database revision as a distinct future storage compatibility domain, not an invented ServerConfiguration field.

Out of scope

  • Gameplay simulation, authentication/RPCs, session claiming, persistence provider/schema selection, transfer/reconnect implementation and deployment.
  • Editing protected AGENTS.md or docs/ai/**, or redefining canonical contracts in mmo_docs.

Dependencies

Hard prerequisites: None

Acceptance criteria

  1. AC 1

    The map names exactly one authoritative owner and lifecycle for every domain in BW-002-AC-1, including creation, mutation, build changes, disconnect/reconnect, transfer, death and recovery where applicable.

  2. AC 2

    Each implemented owner links to the actual game file; each missing owner is explicitly future work. No client presentation or transport adapter is authorized to commit gameplay or economic outcomes.

  3. AC 3

    A review traces client intent through world validation, durable mutation where needed and filtered presentation; it records epoch fencing and preserved cooldown/resource/debt and economic ownership invariants without introducing competing mutable state.

Manual verification

Documentation-only responsibility review. From GAME_ROOT (briarwake/), read docs/architecture/authority-boundaries.md beside the linked current scripts and canonical contracts; inspect each domain/lifecycle row and verify local links. There is no scene or runtime behavior to exercise in this ticket.

Completion evidence and blockers

Required evidence: Reviewed responsibility/lifecycle map, link-check output and a review record identifying implemented versus future owners; no gameplay execution claim.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
