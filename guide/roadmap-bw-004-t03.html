BW-004-T03 · Make command retries reuse one authoritative outcome

Implementation ticket for BW-004.

Not Started · Parent epic: BW-004 · Dedicated connectivity and bounded command admission

Epic acceptance criteria: BW-004-AC-2, BW-004-AC-3

Implementation scope

  • Owner: one server command-admission policy consuming T02 connection-derived identity/epoch and canonical CommandContext/CommandResponse. Keep transport handlers thin and leave effects with explicitly wired domain owners; T04 exposes this policy through bounded owned RPC routing. No externally callable gameplay route is enabled by this ticket alone.
  • Reuse FContentContracts::DecodeAbilityCommand and canonical value comparison for validated requests. Within the authenticated owner scope, an identical (session_epoch, command_sequence) resolves to the same accepted/rejected action/result identity; conflicting semantic payload reuse rejects without replacing it. Exact retries are checked as retries rather than automatically rejected as old sequences.
  • Bound retained outcomes, sequence ranges and in-flight work explicitly; epochs/sequences cannot wrap or be reused. Eviction, timeout and reconnect cannot authorize re-execution of an old identity. Preserve the prior rejection and any later completion reference, with documented behavior when a retained response expires. Do not add pending enum tokens to the canonical accepted/rejected CommandOutcome.
  • Use deterministic native tests of this actual policy with a test-only counted dispatch/effect boundary, not the Editor-only FRuntimeFixtureContext AcceptedActions set as production authority. BW-003 only proves a local logical-recipient probe. BW-018 operation-key receipts and durable economic retry remain separate responsibilities; do not copy their storage ledger into session command admission.

Out of scope

  • RPC transport/size/rate integration (T04), durable receipts, database recovery, movement/cast/combat outcomes and a second generic replay framework.

Dependencies

Hard prerequisites: BW-001, BW-002, BW-004-T02

Acceptance criteria

  1. AC 1

    Identical retries while an accepted action is unresolved and after completion reuse its action identity and consistent response/result reference; a rejected command repeats its recorded rejection. Tests count at most one dispatch and one test effect. Conflicting reuse rejects while leaving the original outcome intact.

  2. AC 2

    Reordered unknown sequences, stale epochs, foreign session identities and sequence overflow cannot dispatch another action or disclose another owner result. Retention bounds, expiry and reconnect do not permit an old command to execute again.

  3. AC 3

    Focused native tests execute the actual policy for accepted/rejected/conflicting retries, unresolved/completed results and the distinct retention/owner failure boundaries. Transport acknowledgments or an in-memory fixture assertion are not described as durable exactly-once gameplay.

Manual verification

This ticket adds a server policy exercised at its actual native boundary with deterministic trusted-session inputs and a counted test-only dispatch/effect sink. Run focused Unreal Automation with affected compilation using the existing harness; document the actual test name/command in the implementation PR. T04 verifies connected RPC wiring, so this ticket does not duplicate two-client scenarios or claim transport evidence.

Completion evidence and blockers

Required evidence: One concise PR/result summary with executed deterministic native policy assertions and affected compilation, tested revision and explicit retention/sequence settings. T04 supplies connected routing evidence; no browser/editor/manual UI execution is required for this policy ticket.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
