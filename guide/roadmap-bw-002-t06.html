Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-5

Implementation scope

  • Extend the same staged admission path for VendorOfferDefinition, VendorPricingConfiguration, RecipeDefinition/RecipeIngredient, MaterialDefinition, ItemDefinition and SalvageRule with only their required canonical reference closure. Resolve item versus material namespaces explicitly; do not invent a mapping from display names.
  • Build a process-local view of the complete declared enabled vendor/crafting/conversion route set, including already admitted routes and the proposed additions. Include input/output quantities, explicit integer minor-unit NPC prices/sellback, eligible common-material salvage returns, and binding/access constraints relevant to guaranteed repeatability. This derived graph is not a second editable economy schema.
  • Reject unknown or missing required prices/quantities/relationships and unsupported route behavior with route/field findings before graph certification. A missing value is not zero; an explicit zero price remains a real value to analyze. Enforce SalvageRule limits: destroy original, at most 25% eligible original common materials, no rare/bound cores, gold or skill XP. Starter assistance cannot become tradable/exportable input.
  • Add --suite economy-data with fully authored synthetic canonical records and missing-value/bad-reference/bad-salvage cases. Fixture values exist only to prove admission and are not proposed production balance. Partial/unknown graph inputs keep affected routes disabled; later T07 proves the loop rule.

Out of scope

  • Production price/recipe catalogs, live vendors/crafting/salvage, profession advancement handlers, wallets/transactions, player market prices or a general economic simulation.
  • Treating a complete graph as a loop pass, inventing undocumented conversion mechanics or enabling routes whose operational dependencies do not exist.

Dependencies

Hard prerequisites: BW-002-T04

Acceptance criteria

  1. AC 1

    The valid fixture produces a complete derived route view with every reference, quantity, price and salvage limit attributable to its canonical source record.

  2. AC 2

    A missing sellback/purchase input, unknown material/item relation, malformed quantity or unsupported route produces an explicit finding and cannot expose the route as admitted. Explicit zero-priced inputs remain distinguishable from missing values.

  3. AC 3

    Excess common-material return, rare/bound-core return and starter-assistance export examples fail their documented constraints. Prior admitted route state is unchanged on every rejection.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root.
python3 tools/verify_toolchain.py
python3 tools/check_content_admission.py --suite economy-data
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use the pinned native macOS Godot editor and Python environment from tools/toolchain.lock.json. The checker and fixtures named below are implementation deliverables of this ticket or its dependencies, not existing commands today.
  2. Author the small complete vendor/recipe/material/item/salvage fixture closure, a preexisting-route context and disposable negative copies. Include required repair-pricing fields when using VendorPricingConfiguration even though repair execution is outside this epic.

Actions

  1. Run the economic-data suite; inspect the full combined route set, units and provenance, then each missing-value/reference/salvage diagnostic.
  2. Compare a missing price with an explicit zero price and verify neither receives an inferred market value or silent fallback.

Expected results

  1. Only complete supported inputs reach graph analysis; incomplete/invalid routes remain disabled with actionable findings.
  2. Safe data completeness does not claim loop freedom, operational gameplay readiness, production prices or a currency transaction.

Reset

  1. Let each bounded checker process exit and discard its in-memory candidate/active registries. Use runner-owned temporary copies for negative mutations; leave tracked canonical snapshots, fixtures and bootstrap configuration unchanged.
  2. Retain the attributable run report and logs in the chosen evidence location. A subsequent clean suite run must reproduce the original outcomes without a database, account, network peer or gameplay scene.

Completion evidence and blockers

Required evidence: Executed complete/incomplete economic-input and salvage-constraint results, canonical fixture provenance and unchanged-active-route assertions.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
