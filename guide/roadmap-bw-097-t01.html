Epic acceptance criteria: BW-097-AC-1

Implementation scope

  • Create the standalone res://tests/rendering/rendering_probe.tscn, its explicitly wired scene script and minimal checked-in geometry/material fixtures under fixtures/rendering/. No Camera3D, SubViewport or rendering test scene currently exists; scenes/client/client_shell.tscn remains the baseline shell and is not the prototype owner.
  • Add tools/run_rendering_probe.py --case capabilities, resolving the verified native engine through tools/verify_toolchain.py and tools/toolchain.lock.json. Start with the existing stock Godot 4.7.2-stable macOS ARM64 Forward Plus path; record the actual graphics backend/device rather than inferring it from the Windows D3D12 preference. Do not change the engine pin or production renderer merely to run a candidate.
  • Provide camera, opaque normal/depth diagnostic geometry, screen-copy swatches, source-versus-decoded buffer views, case selector, capture and Reset controls. Demonstrate orthographic depth reconstruction, normal space, texel sampling and screen-copy timing on each candidate; store a pass/resource availability matrix with exact source, engine/template/export identities, backend, OS, hardware and settings. A source-only capability result is provisional until T10 packages the same scene.
  • Reuse existing process isolation, output ownership and provenance helpers only where their meaning matches. Reuse FixtureRunEvidence, ValidationFinding and TestCheck for actual automated probe checks through the existing canonical extractor/validator and local $ref closure; keep graphical captures and human review in an attributable tool-local envelope. No canonical renderer schema applies to probe settings, captures or capability rows. Mark authored expectations unexecuted; headless diagnostics cannot certify visible output.
  • Include unknown-case, invalid-settings, missing-report and deliberate-check-failure controls in the launcher and meaningful regressions in the existing tools/test_*.py harness. Document installation-free launch, desktop requirements, artifact ownership, controls and reset in tools/README.md.

Out of scope

  • An engine fork, toolchain upgrade, production client routing, platform certification beyond tested hardware, gameplay/network/persistence systems, or adapting the content-admission fixture runner into a generic graphics framework.
  • Assuming depth/normal availability or historical Unity/Godot shader behavior without a capture from the pinned path.

Dependencies

Hard prerequisites: BW-001, BW-003

Acceptance criteria

  1. AC 1

    A fresh source checkout launches the standalone graphical case with the pinned executable and records actual engine/backend/device/settings identity. Unsupported candidates have an explicit diagnostic and no successful capability claim.

  2. AC 2

    Diagnostic captures demonstrate the sampled depth, normal and screen-copy contents and their timing for known surfaces; projection/normal-space mismatches and unavailable resources are recorded as actionable findings. The capability matrix distinguishes demonstrated, unsupported and untested paths.

  3. AC 3

    Actual automated checks preserve FixtureRunEvidence required fields, UTC completion, exact content/rules labels, status/nullability and empty findings for passed records. Forged authored pass claims, invalid records and missing reports are rejected; human visual approval is recorded separately.

  4. AC 4

    Unknown-case/invalid-settings/missing-report/deliberate-check-failure controls fail visibly, retain attributable diagnostics and cannot reuse stale output as success. A fresh clean launch succeeds independently.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; every res:// path uses that project root. The rendering launcher/case below is a deliverable of these tickets, not an existing command.
python3 tools/verify_toolchain.py
python3 tools/run_rendering_probe.py --case capabilities

Setup

  1. Use a desktop macOS ARM64 session and the installed engine/templates pinned in tools/toolchain.lock.json; keep sibling mmo_docs available for canonical extraction. The prototype requires working graphics. Other platforms remain untested until explicitly exercised.
  2. This ticket supplies all probe geometry, shaders, swatches, controls and launcher inputs. Run the existing Python tool regressions after implementing the launcher.

Actions

  1. Run the launch block; inspect the window identity panel and capture the raw/decoded depth, normal and screen-copy diagnostics. Switch between known planes, slopes and color swatches, then reset.
  2. Use the documented launcher negative controls for unknown case, invalid settings, missing report and deliberate check failure in fresh disposable runs. Rerun capabilities cleanly and inspect logs, canonical evidence and the capability matrix.

Expected results

  1. The visible diagnostic surfaces agree with the known fixture; each buffer/pass claim names the actual tested path. Untested or unsupported paths and startup/import failures remain explicit.
  2. Negative controls return nonzero with the correct failed/not-executed distinction; clean automated records validate canonically. No screenshot alone is labeled an automated visual pass.

Reset

  1. Use the probe Reset control to restore the checked-in case settings, camera, actor path and effect toggles; quit the graphical process normally. No persistent gameplay state is created.
  2. Keep prior captures, failed results and reports intact. Repeat into a fresh launcher-owned artifacts directory; restore only deliberately modified disposable inputs, leaving source assets, canonical registries and existing user files intact.

Completion evidence and blockers

Required evidence: Retain source/settings hashes, toolchain/backend/hardware manifest, capability/pass matrix, annotated diagnostic captures, canonical automated evidence, failure-control reports and launcher regression results.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
