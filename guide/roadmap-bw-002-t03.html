Complete · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-1, BW-002-AC-4

Implementation scope

  • Add only the typed ability-command reader and pure recipient-filtered combat-result projection needed for boundary fixtures, with explicit trusted session/visibility context. Keep these at the intent/projection boundary identified in T01, reusable by later transport; do not add a network endpoint or combat executor.
  • Preserve ability_command_v2 and its three always-present targeting keys. Validate entity/point/direction/none against resolved AbilityTargetingPolicy, finite nonzero direction, optional checked character_id and current-session coordinate scope. Reject client-authored outcome fields rather than ignoring them. Reject client activation of passive definitions even when all three targeting inputs are null. Runtime visibility/range/collision and actual session authentication remain future authoritative checks, not facts proven by shape validation.
  • Project internal CombatResult to the canonical shared PublicCombatResult inside CombatResultEvent using explicit recipient entitlement. Hidden source IDs become null; hidden-source correlation IDs are recipient-scoped and cannot reveal private action/ledger identity. Exclude raw/mitigation/debt/resource internals. Use EntitySnapshot as the related public-state allowlist without implementing a full snapshot producer.
  • Add --suite boundaries fixtures and Python-driver behavioral regression coverage. Include canonical CommandResponse accepted/rejected examples without claiming command execution, replay storage or durable success. No second mutable CharacterState or private result store is created.

Out of scope

  • Authentication, actual RPC transport, movement/combat simulation, idempotency/replay storage, interest management and full EntitySnapshot production.
  • Inferring a target/facing fallback, client-selected authority, or serializing a Godot Object/Resource or raw internal CombatResult to observers.

Dependencies

Hard prerequisites: BW-002-T02

Acceptance criteria

  1. AC 1

    Resolved policies for all 21 documented TargetMode branches obey their allowed input kinds; passive definitions cannot be activated by client commands. Ambiguous summon/pet bindings, missing/extra aim inputs, zero/nonfinite direction, mismatched optional character_id and injected outcome fields are rejected.

  2. AC 2

    Authorized owner/observer fixtures receive only the canonical public result fields. A hidden source produces null source identity and safe correlation; an unauthorized target/recipient receives no result. Private identifiers and numeric breakdowns are absent from serialized output.

  3. AC 3

    The same boundary functions are invoked by fixtures and are available for future authoritative callers; no shape-check result is presented as permission to execute gameplay or as a durable acknowledgement.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root.
python3 tools/verify_toolchain.py
python3 tools/extract_content_contracts.py --check
python3 tools/check_content_admission.py --suite boundaries
python3 tools/check_content_admission.py --suite compatibility
python3 -m unittest discover -s tools -p 'test_*.py'
python3 tools/run_baseline.py --role server --headless --config "$PWD/fixtures/config/server.valid.json" --smoke

Setup

  1. Use the pinned native macOS Godot 4.7.2 editor and Python 3.10+ from tools/toolchain.lock.json, with sibling mmo_docs canonical sources available. No dependencies or network peers are needed.
  2. Use fixtures/content_admission/boundaries.json and contracts.snapshot.json unchanged. The corpus contains trusted synthetic SessionContext/RecipientContext inputs, all 21 resolved TargetMode branches, command overrides and recognizable private-result sentinels. The fixed HMAC fixture key is synthetic; production session wiring/key lifecycle is future work.
  3. Each checker invocation creates a fresh artifacts/<suite>-<timestamp>/ directory, or use --output with a new absolute directory. run.json retains exact source/input SHA-256 hashes, Git revision, engine identity, per-case assertions and logs.

Actions

  1. Run the launch commands. Inspect the 121 command cases, 14 recipient projection cases and 2 CommandResponse shape examples in the boundaries run report. Verify the passive-none case rejects activation, every allowed summon/pet alternative is explicit, and malformed/injected/ambiguous cases produce the expected field findings.
  2. Compare owner-hidden-source, observer-visible, observer-hidden-source, hidden-another-recipient, hidden-new-key, entitlement-revoked and observer-target-hidden outputs. Hidden sources must be null; action/event references must match independent HMAC expectations and differ by recipient/key. Search serialized public output for private source/action/event IDs and raw/mitigation/debt/resource fields.
  3. Run disposable failure controls by adding --control import-failure, startup-failure, missing-report, assertion-failure or unsupported-schema to the boundary command, using a new output directory each time. All exit 1; an executed false expectation is Executed/Failed while import/startup/missing-report paths cannot be passing assertions. Rerun boundaries cleanly afterwards.

Expected results

  1. All 137 clean boundary cases pass in the pinned engine; compatibility and Python regression checks pass without engine errors or warnings. Negative expectations are actual rejections, with no returned intent/event and unchanged input state.
  2. Typed intents use the trusted actor/current session epoch and zone/instance/floor. Direction is normalized; coordinates remain intent. Public events have only canonical CombatResultEvent/PublicCombatResult fields; unauthorized recipients or hidden observer targets receive no event.
  3. The direct fixture runner invokes content/ability_command_reader.gd and content/combat_result_projection.gd, available to later authoritative callers. CommandResponse examples are schema-compatible examples only. No authentication, RPC, gameplay execution, replay storage, durable success, full EntitySnapshot producer or content readiness is claimed.

Reset

  1. Allow each bounded checker/engine process to exit; disposable harness projects are removed automatically. No database, account, world state or network session exists to reset.
  2. Preserve run.json and logs before removing only runner-owned artifact directories. Leave tracked fixtures, canonical definitions and bootstrap configuration unchanged; a subsequent clean run must reproduce the results.
