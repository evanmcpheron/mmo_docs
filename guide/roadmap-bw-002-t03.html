Complete · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-2

Implementation scope

  • Implement or complete FContentAdmission as the single candidate-validation and active-selection owner, reusing T02 contracts. Keep candidate parsing/staging separate from publication; resolve references against the complete candidate/explicit admitted dependencies, never whichever record happened to load first. Bound file/payload/collection/nesting inputs and surface actionable canonical ValidationFinding records.
  • Add a finite compatible synthetic static package and negative ContentValidationFixture inputs for unknown/duplicate/wrong-namespace IDs, missing referenced definitions, invalid targeting mode/input-kind branches, unknown floor/line-of-sight/revalidation policies, invalid resource references/caps/aliases/gain rules and incompatible binding revisions. Reuse the canonical 21-mode matrix, resource definitions and referenced primitive semantics; do not copy divergent policy tables into the Python wrapper.
  • Validate supported static records and requested activation separately: a legacy ability may remain cataloged without runtime_binding, but a request to enable unsupported executable behavior must fail through the T04 readiness gate. Economic activation stays disabled until T05/T06. Missing unimplemented families/policies are explicit unsupported findings, not fabricated runtime handlers.
  • Create all finite fixture records and native assertions needed by --suite admission. Exercise first admission, replacement and rejection after a valid selection; the entire active selection and revisions remain unchanged on failure. Return ContentValidationResult with actual findings separately from expected findings.

Out of scope

  • Ability execution, player commands, live world geometry/range checks, production resource simulation, vendor/crafting handlers or authoring all shipped content.
  • Accepting a package merely because JSON shape validation passed, ignoring unknown policy IDs or silently enabling a valid subset of a rejected activation request.

Dependencies

Hard prerequisites: BW-002-T02

Acceptance criteria

  1. AC 1

    A complete compatible supported static fixture is admitted with its exact selected IDs and versions. Reordered record families/forward references have the same result.

  2. AC 2

    Unknown/duplicate/cross-namespace references, malformed targeting/resource fields and incompatible versions produce code/path/message findings before any candidate records become active. Required semantic checks cannot be bypassed by structurally valid input.

  3. AC 3

    After valid package A, each invalid package B leaves A and its revisions unchanged; a fully valid replacement C publishes once. Input specifications/expected findings remain immutable and actual findings are separately inspectable.

  4. AC 4

    Catalog-only unbound legacy definitions stay disabled; explicit unsupported activation is rejected. The test runner evaluates real native admission results rather than reimplementing admission rules.

Expected results

  1. Both clean admission runs pass 1,284 actual checks; all invalid candidates reject before publication, leave the full prior selection/revisions unchanged, and produce inspectable canonical findings. No valid subset is published after a rejected request.
  2. Actual assertion failure is Executed/Failed. Missing/stale reports fail verification, stale binaries stay Not Executed, and fresh recovery passes. Current compatibility/baseline/build/Python/docs checks pass without claiming gameplay handlers, economic safety, production readiness or new packaged-runtime evidence.

Reset

  1. Each wrapper run creates a fresh output and rejects an existing directory. Preserve prior reports. Allow bounded owned child processes to exit; the wrappers terminate only their process groups on timeout.
  2. Fixture owners are local to each case; no live world/database/assets are changed. Tests remove only their owned temporary admission file, and stale-binary removes only its unique marker. Never reset, clean, stash, overwrite user work, create another checkout or modify shared engines to recover.
