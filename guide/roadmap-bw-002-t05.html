Epic acceptance criteria: BW-002-AC-5

Implementation scope

  • Owner decisions recorded on 2026-10-21 select a one-to-one MaterialDefinition economic_policy mapping to ItemDefinition(kind=material), immutable actual-consumption lineage with per-unit rounding, and explicit classifications/route declarations under 2.3.0-design. Preserve existing namespaces, IDs and enum encodings; equal strings or names never establish identity.
  • Review all economy/item/profession mechanics, contracts, catalog examples and consumers. Extend durable ItemLineageRecord with CraftMaterialProvenance: original recipe/content and independent rules revisions, net consumed material facts after mastery, total output units and equal rational per-unit shares. Preserve the original basis through trade/split/merge/recraft; rare/earned/bound inputs return zero. Missing proof disables salvage.
  • Update only the relevant canonical definitions/shared references, ordinary mechanics, compatibility notes, resolved review issue and finite scoped sample bindings. Keep unconfigured prototype routes disabled without guessed mappings, classifications or prices. Refresh the game snapshot content version only; its selected native closure/fingerprints remain unchanged. Publish linked docs/game PRs and regenerate schema/inventory/roadmap outputs.
  • If required choices remain unanswered, record the exact unresolved decision and keep affected routes disabled; neither T05 nor AC5 becomes Complete. A Fully Defined label on existing structures does not prove this cross-contract graph input is available.

Out of scope

  • Choosing production price tables, weakening the no-unlimited-guaranteed-loop gate, inferring identity from equal strings/display names, implementing graph admission or a database.
  • Changing unrelated contracts, protected engineering standards or marking design documentation as an executed economic test.

Dependencies

Hard prerequisites: BW-002-T01

Acceptance criteria

  1. AC 1

    Owner-reviewed definitions explain how every price/conversion/salvage node resolves across existing ID namespaces and how original common-material provenance is established for quantities and alternative recipes; no implicit identity equivalence remains.

  2. AC 2

    Guaranteed/repeatable routes, explicit required values, eligible common returns, zero rare/bound returns and zero salvage gold/XP are represented or explicitly constrained so the later gate can reject incomplete input. Missing decisions cannot silently default to safe or zero.

  3. AC 3

    Canonical changes retain stable identifiers/serialized values or carry an explicitly approved version/migration boundary, with linked decisions, regenerated definitions and passing docs/schema/sample checks. Runtime status remains unverified until T06/T07 execute.
