Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-2, BW-002-AC-3

Implementation scope

  • Extend the same admission owner with a closed capability/readiness check using canonical AbilityRuntimeBinding and ResolvedAbilityDefinition semantics. A known operation token is not proof that its handler exists; capabilities come from actual server-owned implementations, never candidate-authored claims.
  • Require complete rules-matching bindings, finite supported operation parameters/policies, presentation references, supported talent field paths/operation indices and cleanup rules before behavior eligibility. Missing or unsupported named secondary behavior produces explicit record findings; do not parse effect/review_note prose or execute arbitrary expressions/scripts.
  • Keep bindings_resolved, data_tests_passed and runtime_tests_passed independent and attributable to the exact binding/build/content/rules tuple. Unexecuted fixture specifications, forged candidate flags, copied evidence from another revision and schema success cannot establish readiness. Trusted evidence ownership follows T01; this ticket does not invent a cryptographic evidence service.
  • Add --suite readiness using existing prototype records as negative controls, missing binding/handler/presentation/talent-policy examples, stale/unexecuted evidence and caller-supplied true flags. Current Briarwake has no combat handlers: preserve this fact and keep ability execution disabled. A safe nonbehavioral resource fixture can still pass its applicable admission checks.

Out of scope

  • Implementing damage, class mechanics, arbitrary scripts, all talent transforms, presentation assets or gameplay fixtures merely to manufacture a ready ability.
  • Promoting shipped prototype readiness labels, importing documentation validation as gameplay execution evidence, or weakening unsupported-behavior rejection.

Dependencies

Hard prerequisites: BW-002-T04

Acceptance criteria

  1. AC 1

    An ability with a valid numerical profile and descriptive effect but no binding stays disabled with a specific finding; adding a binding with an absent handler, unknown parameter/path/policy or presentation reference also cannot enable it.

  2. AC 2

    Authored all-true readiness flags, unexecuted/failed evidence or evidence for another binding/build/content/rules tuple do not bypass server-owned readiness. Structural/data tests never count as runtime execution.

  3. AC 3

    Safe supported static content remains admissible while unsupported behavior is rejected or explicitly retained disabled according to the declared candidate selection; findings identify every requested unsupported record. No free-text interpretation or client-supplied handler capability is used.

Manual verification

Run from the Briarwake implementation repository. The commands, scenes and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: GAME_ROOT, the briarwake/ repository root; all res:// paths use that project root.
python3 tools/verify_toolchain.py
python3 tools/check_content_admission.py --suite readiness
python3 -m unittest discover -s tools -p 'test_*.py'

Setup

  1. Use the pinned native macOS Godot editor and Python environment from tools/toolchain.lock.json. The checker and fixtures named below are implementation deliverables of this ticket or its dependencies, not existing commands today.
  2. Provide prototype, unknown-handler, missing-presentation, unsupported-talent-path, missing-cleanup, wrong-rules and stale/unexecuted/forged-readiness fixtures. All gameplay execution specifications remain unexecuted until a real later feature runner executes them.

Actions

  1. Run the readiness suite and compare each requested enabled ability with the final eligible/disabled list and findings.
  2. Alter only a disposable fixture effect sentence or candidate readiness flags; confirm this cannot change the missing server capability or evidence result.

Expected results

  1. Every unsupported or unverified requested behavior is rejected before activation, with explicit findings; safe static positive controls still pass.
  2. No ability becomes executable, no canonical readiness label changes, and actual admission-test evidence is kept separate from absent gameplay evidence.

Reset

  1. Let each bounded checker process exit and discard its in-memory candidate/active registries. Use runner-owned temporary copies for negative mutations; leave tracked canonical snapshots, fixtures and bootstrap configuration unchanged.
  2. Retain the attributable run report and logs in the chosen evidence location. A subsequent clean suite run must reproduce the original outcomes without a database, account, network peer or gameplay scene.

Completion evidence and blockers

Required evidence: Executed unsupported-binding/readiness rejection matrix, disabled-record assertions, safe static positive control and exact evidence/capability provenance.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
