Not Started · Parent epic: BW-002 · Authority boundaries and content admission

Epic acceptance criteria: BW-002-AC-5

Implementation scope

  • Owner-selected prerequisite on 2026-10-21: resolve the missing economic contracts before implementing the complete graph gate. Review RecipeIngredient.material_id -> MaterialDefinition versus VendorOfferDefinition.item_definition_id and sellback_by_item -> ItemDefinition, and how SalvageRule proves original eligible common inputs when multiple recipes produce one item. Current schemas declare these namespaces separately and have no explicit identity bridge or original-material provenance contract.
  • Inspect all economy/item/profession mechanics, associated canonical definitions, catalog examples and consumers. Present precise alternatives for the material/item relationship, provenance across recipe quantities/alternate recipes, common versus rare/bound exclusions and repeatability/guaranteed-route inputs. Obtain explicit owner decisions before changing contract meanings; this ticket does not preselect new fields, IDs, schema names, price values or a graph algorithm.
  • After decisions, update only the relevant canonical registry definitions/shared references and associated ordinary mechanics, version/compatibility notes, review issues and finite sample bindings. Preserve stable IDs/encodings; document any explicit migration boundary. Regenerate schema/inventory/roadmap views and run all docs checks. Publish a docs PR and a linked game PR only if game-side snapshots/consumers actually change.
  • If required choices remain unanswered, record the exact unresolved decision and keep affected routes disabled; neither T05 nor AC5 becomes Complete. A Fully Defined label on existing structures does not prove this cross-contract graph input is available.

Out of scope

  • Choosing production price tables, weakening the no-unlimited-guaranteed-loop gate, inferring identity from equal strings/display names, implementing graph admission or a database.
  • Changing unrelated contracts, protected engineering standards or marking design documentation as an executed economic test.

Dependencies

Hard prerequisites: BW-002-T01

Acceptance criteria

  1. AC 1

    Owner-reviewed definitions explain how every price/conversion/salvage node resolves across existing ID namespaces and how original common-material provenance is established for quantities and alternative recipes; no implicit identity equivalence remains.

  2. AC 2

    Guaranteed/repeatable routes, explicit required values, eligible common returns, zero rare/bound returns and zero salvage gold/XP are represented or explicitly constrained so the later gate can reject incomplete input. Missing decisions cannot silently default to safe or zero.

  3. AC 3

    Canonical changes retain stable identifiers/serialized values or carry an explicitly approved version/migration boundary, with linked decisions, regenerated definitions and passing docs/schema/sample checks. Runtime status remains unverified until T06/T07 execute.

Manual verification

Contract-resolution work only; no game launch/map is introduced. In DOCS_ROOT inspect decided definitions and finite positive/negative sample bindings, then execute every rebuild/check from README.txt. If a game-side snapshot changes, verify its canonical extraction from GAME_ROOT using the actual T02 command. Graph behavior remains planned and unverified until T06.

Completion evidence and blockers

Required evidence: Owner decision record and scoped canonical changes/compatibility notes, linked PRs where needed and passing generated-output/inventory/roadmap/regression/full validation. No runtime pass is required or implied for this contract-only ticket.

Blockers: None recorded; see dependencies.

Recorded evidence: None. Planning does not establish an executed pass.
