Briarwake Development Roadmap

Dependency-ordered capabilities, verification gates and Git-tracked progress from a blank project to the documented full game.

Development roadmap overview

A capability and evidence map for building Briarwake from a blank Godot project to the complete documented MMORPG. Use it to identify the next useful work, the prerequisites of each playable milestone, and what remains before release.

Planning baseline, not implementation evidence.

At the initial roadmap review on 2026-10-17, this repository contained design documents, canonical contracts and documentation validation, with no implemented Godot game or verified game-repository completion evidence. Every epic was initialized as Not Started. Later progress must come from the recorded epic evidence; a complete schema, passing arithmetic check or authored fixture is not completed gameplay.

Each epic is one coherent, demonstrable capability with a permanent BW identifier, scope, hard prerequisites, acceptance criteria and required evidence. Phases group integration objectives derived from the dependency graph; they do not require every independent branch to wait for the previous phase.

Hard dependencies must be Complete before the dependent epic can be completed or meaningfully verified. Recommended predecessors improve risk reduction or integration efficiency without becoming technical gates. Direct dependencies are preferred; prerequisite closure supplies inherited requirements.

The displayed sequence is a reasoned engineering recommendation, not an immutable technical fact. Numerical IDs do not imply priority. Reorder an epic only after checking its dependencies and integration gates; keep its ID and anchor stable.

An epic reaches Complete only when every acceptance criterion has passing, revision-specific runtime/content/operational evidence and its hard prerequisites are Complete. Criteria define observable behavior rather than internal methods. Failure scenarios are part of completion. Status does not advance automatically when a document or fixture specification is written.

Milestone requirements include their transitive hard prerequisites. Explicit integration/certification epics test connected behavior on compatible builds. Phase completion means every member epic is Complete; it does not replace those integrated proofs.

Documented requirement
An explicit gameplay or integrity rule in the feature reference; preserve it regardless of the recommended schedule.
Technical constraint
A real limitation such as recipient-safe value replication or one active owner; a tool capability is not evidence that the game meets it.
Hard dependency
A capability needed to complete or meaningfully verify another epic, represented by an explicit ID edge.
Recommended ordering
A judgment about risk, testability, integration or maintenance; independent work may move earlier.
Assumption
An unverified working expectation, recorded with a resolution gate rather than treated as a fact.
Open decision
A future implementation/configuration/content choice that current evidence cannot responsibly settle.

Analysis method. First inventory capabilities across feature prose, 501 canonical structures, class/specification catalogs, professions, content-readiness flags and existing audits. Separate simulation, durable ownership, recipient views and content-production responsibilities. Establish prerequisites from observable behavior and failure cases, then identify parallel branches and small experiments that expose costly assumptions. Compare alternatives on rework, security, testability, operational recovery and unnecessary complexity. Only then topologically order the capabilities and group them into the phases below. A final reverse review traces every documented family to the full-game gate and challenges unnecessary edges.

Research basis. Governing design decisions; Authority and networking; Execution contracts; Statuses and summons; Creation and beginner journey; Profession requirements; Economy; Interface and accessibility; Supporting gameplay; Validation and evidence; Readiness and remaining work; Canonical definitions and resolved history; Ability inventory; Talent inventory; Representative recipes. The canonical registry and shipped catalogs were reviewed together with all class and profession pages. Existing implementation-order recommendations were evaluated as hypotheses.

Detailed epic roadmap

Every epic delivers one demonstrable capability. All members are required for their phase to be Complete. A phase milestone can additionally require earlier prerequisites or an explicit integration epic; individual passes do not imply integration. Epics in the same phase remain independently actionable when their own dependencies permit it. Disclosures are expanded for reading and printing.

BW-001 · Reproducible client and headless project Not Started

Objective: Establish a blank Godot implementation that can be built and exercised independently of presentation.

Scope: Pinned engine/export revision, client and dedicated headless builds, versioned configuration and repeatable foundational checks; no gameplay content.

Hard dependencies: None

Recommended predecessors: None

Acceptance criteria (AC)

  1. A clean checkout produces a launchable client and a headless server using the recorded engine and export-template revisions.
  2. The server starts without graphics or a local player and reports its build, rules and content revisions.
  3. Missing required configuration fails with an actionable diagnostic; credentials are absent from distributed client artifacts.
  4. A clean automated run distinguishes build failure from an executed passing or failing runtime check.

Completion evidence required: Clean-build logs, artifact identifiers and an actual headless smoke-test run.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites and linked open decisions.

Ordering rationale: An executable baseline is required for runtime evidence; engine version is selected here rather than inferred from changing stable documentation.

Related documentation: Authority and networking; Verification requirements

BW-002 · Authority boundaries and content admission Not Started

Objective: Make documented state ownership and enabled-content compatibility enforceable boundaries.

Scope: Stable IDs, version domains, command/result contracts, public/private projections and package admission; evolve only the contracts needed by enabled features, without freezing every future message.

Hard dependencies: None

Recommended predecessors: None

Acceptance criteria (AC)

  1. The boundary review names an owner and lifecycle for movement, combat, durable assets, builds and client presentation, preserving documented invariants.
  2. Admission accepts a compatible package and rejects unknown references, invalid targeting/resource fields and incompatible versions before enabling its records.
  3. Unbound named behavior cannot be enabled by interpreting free-text intent; unsupported records produce explicit findings.
  4. Compatibility fixtures preserve existing identifiers and serialized values and separate content, rules and database revisions.

Completion evidence required: Reviewed responsibility map plus positive and negative content/compatibility validation results.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites and linked open decisions.

Ordering rationale: Broad ownership and identity contracts constrain later systems. Full future payloads need not be frozen before gameplay proves their needs.

Completion evidence required: Actual fixture run records and a redacted diagnostic/measurement sample.

Recorded evidence: None. Required evidence above describes future verification.

BW-018 · Durable ownership and mutation recovery probe Not Started

Objective: Prove economic consistency before building asset-dependent features.

Scope: Versioned ownership, atomic changes, idempotency receipts, durable acknowledgment and recoverable event delivery in a minimal store; provider selection remains explicit.

Hard dependencies: BW-001, BW-002

Recommended predecessors: BW-003

Acceptance criteria (AC)

  1. A committed fixture mutation has one owner, revision and durable receipt; acknowledgment never precedes durable completion.
  2. Concurrent stale requests and conflicting operation-key reuse reject; exact retries return the recorded result.
  3. Injected failure before/after commit and during event delivery neither loses a committed mutation nor applies it twice.
  4. A stale ownership epoch cannot mutate assets; a schema-version migration preserves fixture identity and declared invariants.

Completion evidence required: Actual transactional concurrency/crash/replay results against the selected persistence candidate, with receipt and revision traces.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites and linked open decisions.

Ordering rationale: A narrow early persistence probe tests the highest duplication/recovery risks in parallel with movement and combat. Persisting every simulation tick would add complexity without a documented need.

BW-008 · Predicted movement and reconciliation Not Started

Objective: Keep local movement responsive while the server retains the final position.

Scope: Local movement prediction, acknowledged input reconciliation and remote interpolation; no predicted damage or unrestricted historical hit rewind.

Hard dependencies: BW-007

Recommended predecessors: None

Acceptance criteria (AC)

  3. Collision corrections and ownership changes discard obsolete prediction history and cannot move a character through a wall.
  4. Record correction magnitude/frequency and input response for each scenario, with an explicit review of understandable failure at 250 ms.

Completion evidence required: Network-impairment runs with motion traces, correction metrics and reviewed recordings.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites and linked open decisions.

Ordering rationale: Movement semantics must exist first. Prediction is proven before broad human testing, but does not block isolated combat or durable-state work.

Architectural sequencing decisions

These are engineering judgments constrained by documented behavior. Alternatives remain reasonable where evidence is comparable; a changed measurement may justify reordering without changing IDs.

Authority and the first network proof

Chosen sequence: Establish server-owned intent/outcome boundaries, then validate two clients with movement and one direct action before the complete combat roster or persistent journey.

Alternatives and tradeoff: A client-owned local prototype gives fast visual feedback but cannot test the required concurrent authority. A complete offline combat kernel first is viable, but defers Godot lifecycle/protocol/latency risks. Headless combat fixtures can still develop in parallel with the transport.

Basis: Server authority is documented. The size and placement of the first integrated proof are recommendations intended to discover boundary errors at low content cost.

BW-002, BW-004, BW-005, BW-012 · Authority and networking; Supporting gameplay; Validation and evidence

Replication grows with executable semantics

Chosen sequence: Begin with movement/lifecycle revisions and owner/public projections; add casts, statuses, projectiles and recovery state as their rules become executable. Enforce disclosure from the first snapshot.

Alternatives and tradeoff: A universal final replication layer before gameplay exists guesses state semantics. Broadcasting all state and hiding it in the client leaks information. Rich spatial tuning can wait for measurements, while privacy and hazard relevance cannot.

Basis: Godot provides building blocks, including visibility filtering and value constraints, rather than an MMO authorization policy. Recipient-specific disclosure and correct current-state reconstruction are documented invariants.

BW-007, BW-013, BW-014, BW-015, BW-027 · Authority and networking; Execution contracts

Prediction before broad usability judgments

Chosen sequence: Add prediction/reconciliation after authoritative movement and acknowledgments, before interpreting broader movement/combat playtests.

Alternatives and tradeoff: Prediction is unnecessary for numerical headless tests or a tightly scoped authority proof. Deferring it until a large content roster risks tuning hazards around zero-latency assumptions. Unlimited historical rewind is neither needed nor part of the baseline.

Basis: The target network impairment scenarios are documented; an acceptable correction budget and supported platform envelope must be measured and approved.

BW-008, BW-012, BW-083, BW-090 · Authority and networking; Validation and evidence

Small durability proof early; live assets later

Chosen sequence: Test durable ownership, version conflicts, receipts and crash boundaries early in parallel with simulation; require them before real inventory, rewards and exchanges.

Alternatives and tradeoff: Persisting every tick increases cost without the promised exact combat replay. Waiting until all combat is complete postpones the most consequential conservation/concurrency risks. A purely in-memory economy cannot certify restart safety.

Basis: Economic acknowledgments must be durable; conservative combat checkpoints/reset are explicitly sufficient. A small conventional relational deployment is the documented starting recommendation, not a hard requirement for independent microservices.

BW-018, BW-019, BW-021, BW-025, BW-027 · Authority and networking; Economy; Validation and evidence

Stable boundary contracts, incremental binding

Alternatives and tradeoff: Freezing every future final payload delays gameplay learning on unauthored content. Inventing disconnected local models now creates integration debt. Existing complete contracts constrain behavior without claiming their handlers exist.

Edit only sources/development-roadmap.json for planning content, statuses, blockers and evidence. Do not hand-edit the generated page, dashboard, milestone states, search records or manifest counts. Status must be exactly Not Started, In Progress, Blocked or Complete.

For an existing epic, change status and add verified_evidence records with criteria (one-based AC numbers), artifact (a committed repository-relative file or HTTPS evidence link), revision (the tested game/content revision), result (Passed or Failed) and summary. Preserve prior failure evidence in retained run artifacts; the current completion record must have passing evidence for every criterion. Never copy documentation-validation results into gameplay-completion evidence.

A Blocked epic needs a concrete blockers entry identifying the unresolved decision, missing prerequisite or external limit. Ordinary future prerequisites do not make every unstarted epic Blocked. Reopen an epic when a regression invalidates its current evidence; update dependent completion states rather than leaving a false release gate.

To insert work, allocate a new unused BW ID without renumbering existing epics. Put it at a dependency-valid position, choose its phase, add feature coverage and include it in applicable milestone/integration requirements. Gaps are allowed; IDs must never be reused for a different capability. Do not alter canonical gameplay contracts merely to classify planning documentation.
