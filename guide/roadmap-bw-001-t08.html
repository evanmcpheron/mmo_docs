Complete · Parent epic: BW-001 · Reproducible client and headless project

Epic acceptance criteria: BW-001-AC-1, BW-001-AC-2, BW-001-AC-3, BW-001-AC-4

Implementation scope

  • Version and verify the minimal Unreal C++ project in the owner-selected BriarwakeUnreal repository, including Game/Editor/Server targets, engine/toolchain identities and reproducible build/cook/stage commands. Preserve the supplied engineering documentation and MultiplayerSessions plugin source/assets.
  • Reuse native FServerConfiguration as the owner of the canonical ServerConfiguration startup shape. Reject missing or malformed configuration before server readiness, with no credentials embedded in distributed clients.
  • Execute the packaged client and a bounded dedicated-server smoke with executable/engine/source/rules/content identities, no rendering or local player, and three checked world ticks. Retain artifact identities and real process results.
  • Use fresh isolated C++ project snapshots to distinguish build failure, executed assertion failure, timeout and independent passing recovery. Inspect loose and decoded Pak contents with harmless contamination controls. Bootstrap operational records do not implement gameplay FixtureRunEvidence or ValidationReport.

Out of scope

  • Gameplay, replication-policy implementation, connected multiplayer, production credentials, provider deployment and Steam account/session certification.
  • Promoting written test plans, source checks, stale binaries or historical Godot executions into Unreal completion evidence.

Dependencies

Hard prerequisites: None

Acceptance criteria

  1. AC 1

    On a documented clean machine, the developer can install the required engine and native C++ toolchain, create a fresh C++ Unreal project in an explicitly chosen separate repository, pin the tested engine revision, and produce launchable client and dedicated-server targets using recorded build, cook and package steps.

  2. AC 2

    The compiled dedicated server starts without rendering or a local player and reports its executable, engine, rules and content revisions; the client can be launched separately.

  3. AC 3

    Missing required configuration fails with an actionable diagnostic; credentials are absent from distributed client artifacts.

  4. AC 4

    A clean automated run distinguishes build failure from an executed passing or failing runtime check.

Manual verification

Run from the Briarwake implementation repository. The commands, test worlds and fixtures below are deliverables of this ticket and its prerequisites; these are unexecuted test instructions.

Launch command or scene

Working directory: the BriarwakeUnreal game repository root containing Briarwake.uproject (the task uses a separate BriarwakeNative worktree).
python3 tools/check_baseline.py toolchain
python3 tools/check_baseline.py build --target BriarwakeEditor
python3 tools/check_baseline.py build --target Briarwake
python3 tools/check_baseline.py package --output artifacts/client-package
python3 tools/check_baseline.py build --target BriarwakeServer --engine /Users/Shared/UnrealEngine-5.8.3-source --timeout 7200
python3 tools/check_baseline.py package --target BriarwakeServer --engine /Users/Shared/UnrealEngine-5.8.3-source --output artifacts/server-package --timeout 1200
python3 tools/verify_baseline.py --case pass --output artifacts/clean-verification
python3 -m unittest discover -s tools -p 'test_*.py' -v

Setup

  1. Use the pinned native macOS ARM64 UE 5.8.3/Xcode environment and the recorded source engine for the dedicated Server target. Follow the game README for installation, existing engine patch identity and side-by-side build-tool preparation. Do not modify a shared engine or install a second engine merely to repeat a check.
  2. Use new artifact output paths; existing paths are deliberately rejected. Preserve user checkouts, imported plugin assets, pre-existing builds, credentials and unrelated files. Only committed synthetic configuration is used.

Actions

  1. Run the documented build and package commands. Preserve run.json, commands, actual exits, source hashes and engine/toolchain identities from each output directory.
  2. Launch the exact packaged client identified by its artifact inventory from outside the game source tree. Capture the visible window, close it normally and record its exit and unchanged artifact identity.
  3. Run tools/smoke_server.py with --executable pointing to the exact packaged Server launcher, --case pass and a new --output directory. Repeat with missing-config and invalid-config; those must reject before accepted configuration/readiness. A timeout run must return nonzero and stop its owned process group.
  4. Run tools/inspect_client.py with --bundle pointing to the exact client package, --self-test and a new --report. Inspect loose files and every extracted Pak member; ensure the deliberate loose and compressed-Pak contamination is detected without recording synthetic values.
  5. Run tools/verify_baseline.py with pass, build-failure, assertion-failure and timeout into separate new outputs, then a fresh pass. Read the actual build, runtime execution and assertion fields; a missing/unexecuted report must have no assertion pass.

Expected results

  1. The native client and dedicated server build/package commands succeed for the recorded supported matrix. The exact packaged client visibly opens and closes; this is a baseline window, with no gameplay claim.
  2. The actual Server smoke completes three passing dedicated-world checks with rendering disabled and zero local players, controllers and pawns. Missing/invalid configuration and timeout return nonzero.
  3. Client inspection reports zero findings for the distributed client, actively detects the harmless negative controls after decompression, and removes owned temporary contamination fixtures.
  4. The clean pass and recovery execute the two exact native automation tests. Build failure never runs them; assertion failure remains Executed/Failed; timeout cannot become a passing assertion result.

Reset

  1. Close the owned client and confirm recorded test/server process groups exited. Keep all reports, logs and captures. Only disposable snapshots and inspection controls created by the scripts are removed automatically; choose new output paths for reruns.

Completion evidence and blockers

Required evidence: Versioned native project/repository, pinned engine and toolchain identities, clean C++ client/server build and package logs, exact artifact hashes, actual client launch and headless-server smoke, configuration rejection, credential inspection and distinct automated failure controls.

Blockers: None recorded; see dependencies.

  • Historical AC4 execution at the initial native revision: fresh C++ snapshot builds and two registered Unreal tests distinguish a pass, real compilation failure with runtime Not Executed, executed assertion failure, bounded timeout with no assertion pass, and independent recovery.
