Phase objective and completion

Establish reproducible runtime evidence, a versioned content-production route and durable ownership independently of combat.

0/5 complete · 0%

Phase status: Not Started. Complete only when all 5 epics below are Complete with verified evidence.

The durable retry/crash probe is executed against a real candidate store. The author/import route also produces a reproducible reviewed package and rejects invalid content.

Integrated completion milestone: Executable ownership proof. Its full prerequisites and integration evidence must also pass; individual components do not prove their integration.

Hard dependencies are required for completion. Recommended predecessors are scheduling preferences. Other phases are not global start barriers. How to read this roadmap.

Detailed epics

BW-001 · Reproducible client and headless project Not Started

Objective: Establish a blank Godot implementation that can be built and exercised independently of presentation.

Scope: Pinned engine/export revision, client and dedicated headless builds, versioned configuration and repeatable foundational checks; no gameplay content.

Hard dependencies: None

Recommended predecessors: None

Acceptance criteria (AC)

  1. A clean checkout produces a launchable client and a headless server using the recorded engine and export-template revisions.
  2. The server starts without graphics or a local player and reports its build, rules and content revisions.
  3. Missing required configuration fails with an actionable diagnostic; credentials are absent from distributed client artifacts.
  4. A clean automated run distinguishes build failure from an executed passing or failing runtime check.

Completion evidence required: Clean-build logs, artifact identifiers and an actual headless smoke-test run.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: An executable baseline is required for runtime evidence; engine version is selected here rather than inferred from changing stable documentation.

Related open decisions: Engine, platform and deployment candidates

Related documentation: Authority and networking; Verification requirements

BW-002 · Authority boundaries and content admission Not Started

Objective: Make documented state ownership and enabled-content compatibility enforceable boundaries.

Scope: Stable IDs, version domains, command/result contracts, public/private projections and package admission; evolve only the contracts needed by enabled features, without freezing every future message.

Hard dependencies: None

Recommended predecessors: None

Acceptance criteria (AC)

  1. The boundary review names an owner and lifecycle for movement, combat, durable assets, builds and client presentation, preserving documented invariants.
  2. Admission accepts a compatible package and rejects unknown references, invalid targeting/resource fields and incompatible versions before enabling its records.
  3. Unbound named behavior cannot be enabled by interpreting free-text intent; unsupported records produce explicit findings.
  4. Compatibility fixtures preserve existing identifiers and serialized values and separate content, rules and database revisions.
  5. Before enabling vendor/crafting/conversion routes, the complete enabled price and conversion graph passes the documented no-unlimited-guaranteed-loop gate; missing required values keep affected routes disabled. Positive and negative fixture graphs demonstrate this admission rule.

Completion evidence required: Reviewed responsibility map plus positive and negative content/compatibility validation results.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Broad ownership and identity contracts constrain later systems. Full future payloads need not be frozen before gameplay proves their needs.

Related documentation: Design constraints; Execution contracts; Canonical definitions; Economic content admission

BW-003 · Repeatable runtime fixtures and diagnostics Not Started

Objective: Produce attributable runtime evidence from the first experiments.

Scope: Pinned fixture world/time/content context, bounded test control, action-correlated diagnostics and baseline tick/traffic/queue measurements; no claim of launch capacity.

Hard dependencies: BW-001, BW-002

Recommended predecessors: None

Acceptance criteria (AC)

  1. Executed fixtures record scenario revisions, runner, result and assertions separately from unexecuted specifications.
  2. The same seeded fixture context reproduces observable rule outcomes; test-only control cannot be invoked through gameplay commands.
  3. Diagnostics connect rejected commands and committed actions to build/content/owner revisions without exposing secrets.
  4. A test run captures tick duration, relevant entities, bytes per client and queue depth, including its workload and environment.

Completion evidence required: Actual fixture run records and a redacted diagnostic/measurement sample.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Minimal observability precedes meaningful multiplayer tests; production dashboards and retention policy can wait.

Related documentation: Verification requirements; Supporting gameplay; Authority and networking

BW-095 · Versioned content authoring and import workflow Not Started

Objective: Make documented content producible and reviewable through the same contracts used by runtime admission.

Scope: Versioned editors or importers for abilities, statuses, talents, items, recipes, NPC kits, loot tables and encounter triggers, with world/tutorial relationships. A bounded import/export route is sufficient; full content authoring and gameplay handlers remain with feature epics.

Hard dependencies: BW-001, BW-002, BW-003

Recommended predecessors: None

Acceptance criteria (AC)

  1. Representative records from each declared authoring family round-trip from reviewed source through validation/export to package admission with stable IDs, versions and traceable findings; later enabled families extend the same route.
  2. Invalid references, target/resource fields, caps, exclusive choices, progression relationships and required binding/presentation references produce actionable record-level findings and cannot partially publish an enabled package.
  3. The same reviewed source produces a reproducible package and fixture manifest for client/server use; unbound records remain disabled and authoring or schema validation never promotes runtime-test evidence to passed.
  4. An accepted content edit and a rejected edit demonstrate reviewable differences, retained prior valid output and compatibility with the canonical schema bundle; no parallel authoritative contract is introduced.

Completion evidence required: Executed author/import/validate/export/admit examples, invalid-content diagnostics, reproducible package identifiers and a reviewable fixture manifest; this proves tooling, not completed gameplay content.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Admission and content migration do not provide a production workflow. Establish a small author/import path before starter and catalog production; fixture-based simulation may still proceed independently.

Related documentation: Required content tools; Readiness boundaries; Canonical data contracts

BW-018 · Durable ownership and mutation recovery probe Not Started

Objective: Prove economic consistency before building asset-dependent features.

Scope: Versioned ownership, atomic changes, idempotency receipts, durable acknowledgment and recoverable event delivery in a minimal store; provider selection remains explicit.

Hard dependencies: BW-001, BW-002

Recommended predecessors: BW-003

Acceptance criteria (AC)

  1. A committed fixture mutation has one owner, revision and durable receipt; acknowledgment never precedes durable completion.
  2. Concurrent stale requests and conflicting operation-key reuse reject; exact retries return the recorded result.
  3. Injected failure before/after commit and during event delivery neither loses a committed mutation nor applies it twice.
  4. A stale ownership epoch cannot mutate assets; a schema-version migration preserves fixture identity and declared invariants.

Completion evidence required: Actual transactional concurrency/crash/replay results against the selected persistence candidate, with receipt and revision traces.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: A narrow early persistence probe tests the highest duplication/recovery risks in parallel with movement and combat. Persisting every simulation tick would add complexity without a documented need.

Related open decisions: Engine, platform and deployment candidates

Related documentation: Authority and networking; Itemization; Supporting gameplay
