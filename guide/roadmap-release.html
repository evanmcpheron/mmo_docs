Detailed epics

BW-090 · Measured full-game operational capacity Not Started

Objective: Establish and verify a defensible supported workload envelope for the intended release configuration.

Scope: Simulation, bandwidth, database/settlement and client presentation measurements under crowded gameplay, plus overload/admission behavior. Capacity is a measured release budget, not a speculative realm population.

Hard dependencies: BW-074, BW-083, BW-089, BW-008

Recommended predecessors: BW-088

Acceptance criteria (AC)

  1. The approved test plan states concurrency/density, client hardware/platform/renderer/tier/internal resolution, server tick/bandwidth/tail-latency/backlog/memory budgets, client CPU/GPU frame-time percentiles and video-memory budgets, workload mix and failure/recovery objectives before declaring a pass.
  2. Scripted users move, fight, command the maximum legal summons, create overlapping effects, craft and trade; tests include crowded markets/world encounters, burst arrivals and instance activity. Client workloads include the production water/reflection, foliage, lighting/atmosphere and particle configurations rather than only placeholder scenes.
  3. Runs retain tick percentiles, queues, entity/subscription counts, bytes per client, database latency, pending settlements, memory and recovery measurements for exact release versions. Client results retain CPU/GPU frame percentiles, memory/resource counts and expensive-pass timings per supported quality tier.
  4. Latency/loss/jitter/reordering scenarios and an unavailable/saturated destination preserve authorization, meaningful rejection/recovery and economic conservation.
  5. The supported configuration meets approved budgets or explicitly reduces its admission envelope; identified performance changes have before/after evidence and preserve gameplay-critical hazards.

Completion evidence required: Required future proof: reproducible full-workload load/soak and client-clutter runs, raw percentile/bandwidth/database reports, approved capacity budgets and overload/recovery evidence for the release configuration.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Early probes guide architecture; final capacity waits for the workloads that dominate the intended game. Add partitioning or optimization only where measurements justify it.

Related open decisions: Capacity, security and recovery budgets; Incremental topology and comparable branch orders; Render configuration and supported quality envelope

Related documentation: Representative load requirements; Interest and critical hazards; Visual readiness; Selected 3D pixel-art direction; Rendering verification

BW-092 · Full-game integrated regression and balance signoff Not Started

Objective: Demonstrate the intended game as connected player journeys and resolve release-blocking interaction and balance findings.

Scope: Release-candidate integration across characters, level 1–60, enabled roster, groups/PvP, world travel, economy/professions, social systems and presentation. This is evidence of integration beyond individual epic completion.

Hard dependencies: BW-072, BW-073, BW-074, BW-085, BW-086, BW-089, BW-091

Recommended predecessors: None

Acceptance criteria (AC)

  1. The release candidate passes a versioned journey matrix spanning both factions, creation through cap, role access, starter departure, group content, professions/economy, social operations and enabled PvP modes.
  2. All 330 documented abilities, all 1,764 talent nodes and the approved full profession/world inventory have current binding and execution evidence; legal/invalid/reconstruction and positive/exclusion fixtures cover required behavior, and no required roster entry remains silently disabled.
  3. Equal-budget build/role/faction and profession-relevance reports meet documented evaluation standards, record measured deviations and resolve or explicitly withhold release on approved blocking findings.
  4. Cross-system failure cases cover concurrent rewards/trades, full-bag delivery, death/logout/reconnect, transition during economic activity, guild permissions and encounter reset without duplicated assets or cleared debt.
  5. Human usability/accessibility sessions cover keyboard talent editing, friendly-frame healing, expensive craft confirmation, small-window reflow and crowded combat, with blocking findings resolved. The release render/asset manifest and supported quality configurations match the approved 3D pixel-art comparisons, with camera/picking, privacy, water/transparency and atmosphere regressions included.

Completion evidence required: Required future proof: release-candidate journey matrix, executed integration/fixture reports, balance/profession studies, accessibility sessions and a reviewed issue disposition tied to exact artifacts.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Completed subsystem epics do not prove their interaction. Reserve a distinct integration gate, and do not substitute data counts or an unexplained subjective balance claim for measured evidence.

Related open decisions: Runtime bindings and complete release inventory; Measured balance, usability and content limits

Related documentation: Open runtime/content gates; Build diversity; Profession relevance; Usability readiness; Selected 3D pixel-art direction; Rendering verification

BW-093 · Production incident and support recovery rehearsal Not Started

Objective: Prove that operators can contain and recover realistic failures using the documented tools and authorized procedures.

Scope: Service outage, account compromise, economic corruption, failed update and support investigation rehearsals with visible player communications. Routine feature implementation is outside this gate.

Hard dependencies: BW-085, BW-086, BW-088, BW-090

Recommended predecessors: None

Acceptance criteria (AC)

  1. A staged outage/overload run uses measured alerts and documented ownership to identify the failure, restrict admission and communicate a user-visible service reason.
  2. An account-compromise scenario revokes access/epochs, preserves permitted evidence and completes authorized recovery/restriction/appeal handling without an undocumented data edit.
  3. An economic incident is contained with scoped freeze/suspension and repaired through audited reconciliation/reversal, preserving both sides of legitimate committed operations.
  4. A failed release/restore rehearsal meets approved recovery objectives or retains a blocking finding; operators verify artifact integrity and post-recovery ownership before reopening.
  5. Support can reconstruct an action history using permitted records; secrets and unnecessary personal data are absent, and retention/access policy is demonstrably enforced.

Completion evidence required: Required future proof: dated staged incident transcripts, alert/audit/reconciliation artifacts, measured detection/recovery results and reviewed runbooks corrected by the rehearsals.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Backup creation and healthy deployment do not demonstrate operational recovery. Rehearse against the final workload and permission model before the release decision.

Related open decisions: Capacity, security and recovery budgets

Related documentation: Support and recovery procedures; Observability; Economic incident response

BW-094 · Production release evidence gate Not Started

Objective: Make a reviewable release decision from verified full-game, capacity and recovery evidence.

Scope: Final artifact/configuration identification, mandatory evidence review, blocking-issue disposition and controlled release acceptance. This is a release gate, not an additional feature bundle or a claim of achieved production readiness.

Hard dependencies: BW-092, BW-093

Recommended predecessors: None

Acceptance criteria (AC)

  1. The candidate identifies immutable artifacts, content/rules/database versions, supported platforms, configured admission envelope and compatibility policy matching the tested reports.
  2. Required feature/integration, security, conservation, capacity, accessibility and recovery evidence is current for the candidate; missing or failed mandatory evidence prevents approval.
  3. Unresolved decisions have approved concrete configuration or an explicit scope exclusion consistent with the intended game; no required documented feature is silently deferred to obtain a pass.
  4. A controlled final deployment validates admission, first login/creation, core gameplay, durable transaction, reconnect and safe rollback checks before production acceptance is recorded.
  5. The release record identifies the responsible approver and retained evidence/findings; approval never changes incomplete epics to Complete without their own verified evidence.

Completion evidence required: Required future proof: signed/reviewed release checklist and evidence index, exact candidate manifest, blocking-issue disposition and controlled deployment/rollback smoke results.

Recorded evidence: None. Required evidence above describes future verification.

Blockers: None recorded; see hard prerequisites.

Ordering rationale: Release is conditional on demonstrated capabilities, rather than elapsed time, a speculative player count or completion of documentation. Root review must confirm this gate transitively covers every required epic.

Related open decisions: Capacity, security and recovery budgets; Rated entry eligibility and normalized build selection; Render configuration and supported quality envelope

Related documentation: Readiness limits; Retained evidence; Operational release controls
