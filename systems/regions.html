Player mechanic and scope

Regions persist three separate axes: settlement development, regional danger and discoveries. Permanent construction never decays simply because everyone logged out. Repeated threats are bounded authored events, not arbitrary destruction of historical progress.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Begin the small watchtower objective contract at Phase 15; evolve that same schema at Phase 22 rather than introducing an incompatible second project owner.
  2. For project.elderwood.north-road author Blocked → Supplied → Repaired visual states and a separate recurring danger event. Essential route access changes only on a committed stage.
  3. Bind the board, gate, merchant and map consumers to the shared region projection. Subscribe, pull a snapshot, then apply only newer contiguous deltas.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ARegionProjectionActor and ABriarwakeGameState publish public stage snapshots. Runtime tile overlays and props consume committed stage IDs; they cannot complete projects themselves.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Submit Contribution(ProjectId, StageId, ObjectiveId, MaterialInstances or validated achievement receipt, RequestId).
  2. Validate the currently active objective, permissible source, sufficient inventory, character lease and expected region revision.
  3. Commit material debit, contribution receipt, progress and any resulting stage transition once.
  4. Publish a compact revisioned snapshot/delta through an outbox. The visual bridge, road and merchant service now change together.
  5. On reload or missed revisions, fetch a fresh snapshot. A stage presentation replay does not replay the transaction.

Rejected commands, disconnect and restart

Stale stage → ProjectChanged; no debit. Repeated contribution → original receipt. An outbox delay shows PendingSave/Syncing instead of granting client-side completion.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_RegionBoard displays essential progress, optional enhancements, contribution choices and remaining personal effort. New arrivals receive an authoritative revision before applying deltas.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Every stage requires an authored tile/prop variant. No environment stages have been verified in the missing ZIP.

No universal ecological simulation, freeform terrain editing or offline punishment. Population scaling may never revoke credited progress or essential access.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
