Player mechanic and scope

Create one validated character with exactly one primary vocation. Appearance and vocation are separate choices; combat discipline is a third, independent progression choice. Character creation is an atomic durable operation, not the act of spawning a Pawn.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Create the three widgets under Content/Game/UI/Frontend. Put the appearance preview, vocation comparison and validation errors in separate panels. Set an explicit controller focus order: name, appearance, vocation, confirm, back.
  2. In DA_GameCatalog assign all available vocation definitions and the allowed appearance catalog. Before Phase 20/21, mark Woodwright and Apothecary unavailable rather than presenting nonfunctional choices.
  3. Configure the server default map separately from the client frontend. Phase 05 may use an explicitly disposable test account fixture; activate durable creation and duplicate-login prevention at Phase 06.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ABriarwakeGameMode admits a verified character-session lease. ABriarwakePlayerController routes owned commands. A newly spawned ABriarwakeCharacter is only the current body.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Submit CreateCharacter(RequestId, Name, AppearanceIds, VocationId) from the authenticated account context. The service derives AccountId; it is not trusted from the form.
  2. Normalize the name with a pinned Unicode policy, validate length and forbidden characters, then acquire account-slot and name constraints in one transaction.
  3. Create CharacterId, chosen vocation, zeroed independent XP ledgers, starting-zone position and starter-kit receipt. Reusing the request returns the same CharacterId.
  4. Reserve a session lease before admitting the body. Bind the local view to the admitted CharacterId and pull its snapshot.
  5. Reconnect from another client after logging out. Display the same vocation and appearance without granting another kit.

Rejected commands, disconnect and restart

No vocation → VocationRequired. Unsupported cosmetic ID → AppearanceUnavailable. Full slots → CharacterLimit. Duplicate normalized name → NameUnavailable. A provider failure must not leave a half-created character.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_Login → WBP_CharacterSelect → WBP_CharacterCreate → WBP_HUD. Public name, vocation and permitted appearance replicate; account identity, inventory and authentication tokens do not become public PlayerState fields.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

No archive was available. The character preview must use explicitly audited combinations before it can be accepted; do not infer skins from vocation names.

Authentication-provider selection, password recovery implementation and jurisdiction-specific retention policy remain unresolved. Do not build an ad hoc password store in Unreal.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
