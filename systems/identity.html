Player mechanic and scope

Every new character selects one permanent FactionId, one permanent CombatDisciplineId (combat class), and one changeable primary VocationId. These identities are independent; every available combat discipline supports every available vocation. Character creation is an atomic durable operation, not the act of spawning a Pawn.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Create the three widgets under Content/Game/UI/Frontend. Keep appearance, faction, combat discipline and vocation selections separate. Focus order: name, appearance, faction, combat discipline, vocation, confirm, back. Explain the permanent faction/class choices before confirmation; UI validation does not replace server validation.
  2. Assign available discipline/vocation definitions and the allowed appearance catalog in DA_GameCatalog; connect the approved faction selection catalog without class/vocation filters. Keep Woodwright and Apothecary unavailable before their existing Phase 20/21 activation. Required choices cannot be omitted because a definition is unavailable.
  3. Configure the server map separately from the client frontend. Phase 05 uses disposable identity fixtures; Phase 06 exercises durable transactions with isolated fixtures. Real character creation stays blocked until the approved faction catalog and Phase 12 discipline definitions are integrated. Do not silently choose a class or retain disposable fixtures as player characters.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ABriarwakeGameMode admits a verified character-session lease. ABriarwakePlayerController routes owned commands. A newly spawned ABriarwakeCharacter is only the current body.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Submit CreateCharacter(RequestId, Name, AppearanceIds, FactionId, CombatDisciplineId, VocationId) from the authenticated account context. The service derives AccountId; it is not trusted from the form. Include every semantic selection in the existing request digest.
  2. Normalize the name with a pinned Unicode policy, validate length and forbidden characters, then acquire account-slot and name constraints in one transaction.
  3. After independent catalog/availability checks, atomically create CharacterId, permanent FactionId/CombatDisciplineId, active VocationId, initial Progression.Combat and exactly one keyed Progression.Vocations entry. Initialize validated Level-1 XP, name reservation, safe starting position and the unique starter-kit outcome/receipt together. A matching request returns the original CharacterId, not another kit.
  4. Reserve a session lease before admitting the body. Bind the local view to the admitted CharacterId and pull its snapshot.
  5. Reconnect from another client after logging out. Display the same permanent faction/class, active vocation, saved vocation histories and appearance without granting another kit or replaying progression rewards.

Rejected commands, disconnect and restart

Missing combat discipline → CombatDisciplineRequired; unsupported/unavailable discipline → CombatDisciplineUnavailable. Missing vocation → VocationRequired; unsupported/unavailable vocation → VocationUnavailable. Missing/invalid faction → FactionRequired/FactionUnavailable; absent approved catalog → IdentityCatalogUnavailable. Unsupported cosmetic → AppearanceUnavailable; full slots → CharacterLimit; duplicate normalized name → NameUnavailable. Reject before any name/item/identity mutation.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_Login → WBP_CharacterSelect → WBP_CharacterCreate → WBP_HUD. Publish only the permitted public identity/appearance subset. UCharacterStateComponent exposes owner-only committed progression, including inactive vocation histories; raw records, account identity and authentication tokens are never public PlayerState fields.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Required selections and permanent identity guards

Committed requirement: faction, combat class (the existing combat discipline) and vocation are three independent identities. Appearance remains a separate cosmetic choice. Validate each selection against its own approved available definitions; do not create faction/class/vocation combination restrictions.

After successful creation, every durable mutation compares permanent FactionId and CombatDisciplineId with the stored values. A client-supplied replacement, generic record patch or unauthorized server-side mutation returns PermanentIdentityLocked before any write. No class-change operation, token, alternate active class or multiclass record is permitted. Controlled legacy completion below is not a gameplay class-change API.

Creation reserves the name and account slot, writes the complete identities and initial progression, grants the starter kit under the existing domain uniqueness guard, and commits the original-result receipt/outbox in one transaction. Reject malformed/missing/unavailable fields before reserving anything. A different payload under the same RequestId returns RequestIdentityConflict. No Pawn or UI can finalize partial creation.

Content readiness without roadmap reordering

The audited main contains generic faction reputation prose but no approved permanent-allegiance catalog/creation specification. Supply that existing faction work as a compatibility prerequisite; this change does not invent faction IDs, starting regions or lore. An absent catalog returns IdentityCatalogUnavailable; never default allegiance or drop the required field.

Phase 05 retains disposable selection fixtures and Phase 06 isolated persistence tests. UCombatDisciplineDefinition and its four data assets still activate at Phase 12 (ADR-004); re-open character creation then with approved faction content. Earlier fixture success is not production admission readiness. Real characters cannot be created until every required selected definition is integrated and available.

Faction catalog now specified

The former approved-faction-content gap is addressed by UFactionDefinition and sources/factions.json. Phase05 creator uses a clearly disposable content fixture; real end-to-end durable faction release requires Phase26 and all readiness gates. Production target selects only faction.hearthward-league; the other three records are registered but unavailable for new creation.

Mandatory selection remains independent of permanent combat discipline and active vocation. Existing characters retain their faction when new signups are disabled. Schema3 is additive to the recently authored schema2 class/vocation contract; migration never clears trained vocation histories.
