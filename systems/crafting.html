Player mechanic and scope

All five vocations use the same recipe validation and transaction machinery. Differences belong in ingredients, techniques, choices, station requirements and authored outputs, not five independent inventory systems.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Create recipes for WatchFitting, FieldLoaf, BridgeSupport and BlightRemedy. Assign item IDs and exact quantities through DA_GameCatalog.
  2. Place forge, oven, carpenter bench and alchemy bench service instances in the authored hub as their vocation phases activate.
  3. For the first recipe choose immediate atomic crafting. Add timed reservations only after cancellation/refund tests exist; do not invent partial-consumption rules in animation graphs.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ACraftingStation advertises service definitions; UActionExecutionComponent checks action eligibility. UDurableStateClient submits server-validated operations to the one persistence boundary.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Submit Craft(RecipeId, SelectedTechniqueId, Count, RequestId, ExpectedInventoryRevision). Validate station range, learned recipe, active vocation permissions and stack totals.
  2. Plan an all-or-nothing material/currency debit and output placement. Reject before mutation if output cannot fit.
  3. Commit input debit, server-created output instance, vocation advancement and receipt in one transaction.
  4. Return the committed revision and immutable outcome. Repeated requests with the same identity return that outcome; a new identity must still meet remaining inventory constraints.
  5. Refresh equipment/recipe views from the committed snapshot; presentation may now play forge/cook feedback.

Configured route fixture

recipe.watch-fitting uses 3 IronOre and 1 SalvagePlate to produce 1 WatchFitting. Start with 6 ore and 2 plates; two distinct valid crafts may legitimately succeed, but replaying one request cannot make a third.

Use L_ThornmereVillage and L_ElderwoodRoad as the repeated route. The isolated L_BriarwakePreview exists only to prove imported visuals. Field values below are fixtures, not production balance.

Rejected commands, disconnect and restart

Missing station → StationRequired. Locked advanced technique → VocationRequired. Stale revision → refresh. Reservation cancellation follows a published refund policy and cannot both refund inputs and retain output.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_Crafting shows ingredient availability, output preview, applicable specialization and pending state. Closing the panel neither consumes inputs nor cancels a committed result.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Forge/cook/alchemy-specific animation coverage is unverified. A shared interact pose may be a temporary visual, not evidence of vocation-exclusive art.

NPC commissions provide essential cross-vocation goods with fair bounded costs. Specialists offer variants and control, not a monopoly over mandatory progression.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.

Independent vocation and faction recipes

The four authored construction recipes are optional specialist routes through the existing craft transaction. Active vocation permissions, ingredients and capacity are still checked. The faction package adds no crafting owner and never activates skills of an inactive vocation.

The Hearthward public work order supplies equal essential project progress without materials, a recipe, another player or a particular vocation. Item/reward sources remain catalog-driven and replay-safe.
