Player mechanic and scope

A solo character can achieve the same critical narrative/world milestone as a party. Group encounters add coordination; they do not hold essential progression hostage. NPC allies fill specific authored mechanic roles, not autonomous farming jobs.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Author the Bellroot Vault beneath Elderwood with a safe entry room, two encounters, a checkpoint and return gate.
  2. For the solo bell mechanism let one NPC hold an exposed lever while the player fights; the helper retreats if the player stops active participation. Group variant uses voluntary role coordination.
  3. Define wipe/reconnect timeouts and checkpoint restoration before adding boss drops. Entry/exit must use the same transfer contract as biome travel.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

The dedicated instance server owns encounter progress and active participation. Companions follow constrained server AI with explicit assistance tasks and no separate player economy.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Validate entry eligibility and reserve instance capacity without requiring a minimum human group.
  2. Select an authored mechanic variant at an encounter boundary. Do not instantly change the rules during a boss cast when somebody joins.
  3. Track player actions, assistance and encounter eligibility. Helpers cannot independently earn loot while a player is idle.
  4. Commit the critical milestone once and optional variant rewards under separate explicit policies.
  5. On crash or disconnect, recover to a known safe checkpoint and reconcile pending receipts before reopening the encounter.

Rejected commands, disconnect and restart

Destination full → wait/cancel with no item debit. Instance loss → checkpoint recovery. Reused reward token → original receipt. A helper cannot authorize party-only item transfers.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_DungeonEntry shows variant, expected roles, available NPC aid and recovery policy. WBP_Party clearly distinguishes NPC helpers from human participants.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Dungeon tiles, guardian sprite, boss telegraphs and companion poses are design requirements; none is claimed acquired.

Maximum human party size is a tuning decision; use 5 as the initial fixture. No raid-only item essential to the main route.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
