Player mechanic and scope

Every screen is an observer and request surface. Removing the HUD must not remove the rules. Readable focus, remapping, text scaling, reduced motion and alternatives to timing/audio/color-only signals belong in the first functional slice, not a final cosmetic pass.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Create keyboard/controller focus order and return focus on each modal. Bind observers once, immediately pull state, and unbind on teardown.
  2. Add text-size and reduced-motion settings; duplicate sound-only bite/attack alerts with visible text/shape cues and distinguish statuses without relying on color.
  3. Use stable localization keys for dialogue, quests, item names and error messages. Test long translated strings and a narrow viewport instead of hard-coded pixel assumptions.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ABriarwakePlayerController owns local widget lifetime and input focus. Gameplay continues on the server while menus are open; private data is pulled from approved projections.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Open a screen through the controller and subscribe to its state projection.
  2. Render a snapshot, then apply newer revisions. Disable conflicting pending actions without freezing unrelated game controls.
  3. Submit only the chosen operation and required identifiers; never send a desired new balance or awarded item.
  4. Display the terminal result or unknown-outcome recovery message. Keep a clear retry path that preserves RequestId where required.
  5. Close/reopen or destroy the widget and verify the same state and commands still exist.

Configured route fixture

The First Supplies route is completed once with keyboard/mouse, once with controller, once with large text/reduced motion and once with fishing’s accessible timing mode.

Use L_ThornmereVillage and L_ElderwoodRoad as the repeated route. The isolated L_BriarwakePreview exists only to prove imported visuals. Field values below are fixtures, not production balance.

Rejected commands, disconnect and restart

Show ZoneFull, TransferFailed, StaleRevision, ServiceUnavailable, InventoryFull, NotAuthorized, PendingSave, TradeExpired and Disconnected with an action appropriate to each state.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

Frontend, HUD, map/minimap, equipment, inventory/bank, vendor, loot, journal, vocation/crafting, fishing/farm, region, dialogue, social/chat/trade and recovery screens share consistent pending/error states.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Fonts, SFX, music, VFX and UI icons need provenance. This documentation package includes no paid artwork, third-party audio or invented game screenshots.

Screen-reader integration and platform accessibility APIs require actual platform testing. Text alternatives in the design are not proof of native assistive-technology support.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
