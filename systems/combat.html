Player mechanic and scope

Combat combines server-resolved melee and projectiles with optional soft targeting for abilities and healing. Vanguard, Ranger, Arcanist and Warden are independent of the five vocations. Every discipline must have a viable solo path.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Enable GameplayAbilities and verify GameplayTags/GameplayTasks module dependencies in the future game. Add the AbilitySystemComponent on the selected replicated owner and document its owner/avatar initialization on possession and respawn.
  2. Author GA_BasicMelee, GA_BasicShot and GE_BasicDamage as planned native-derived assets. At Phase 09 assign the two fixture abilities through a server-owned basic-ability list. Full discipline definitions activate at Phase 12; no ability grant belongs in a widget.
  3. Place BP_TrainingDummy on the connected Elderwood route. Start with one trace shape and one projectile; disable visual damage notifies to prove rules remain server-driven.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

The PlayerState-associated AbilitySystemComponent and UCombatAttributeSet own runtime ability/attribute behavior. ABriarwakeCharacter is the current avatar. Server traces and target validation decide hits; PaperZD observes action state.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Ability input requests activation through the owning controller/ability component. Server checks lease, state, resource cost, cooldown, target and current committed grant permission. A stale or inactive vocation-exclusive grant is not permission to execute; permanent combat-class grants remain independent.
  2. Commit permitted runtime cost once and open the authored hit window. The server chooses collision results and line-of-sight eligibility.
  3. Apply damage/healing through the selected GAS effects. Track legitimate support and damage participation for rewards.
  4. On a durable reward, request the persistence transaction using encounter/reward identity; do not award XP in the damage widget.
  5. Rebuild talents/equipment-derived grants after respawn or transfer; remove old handles before reapplying the new avatar binding.

Rejected commands, disconnect and restart

No resource → InsufficientStamina/Mana. Blocked target → NoLineOfSight. Stale body after transfer → LeaseExpired. Interrupt channels through authoritative action cancellation, not widget closure.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_HUD displays health/stamina/mana, cooldowns and action errors; WBP_Talents requests purchases. Keyboard and controller can select the same valid targets.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Sword, shield, bow, spear, dual-blade and magic coverage must be audited separately. Unavailable spell/healing poses require named art tasks and readable temporary cues.

GAS is the recommended initial choice, subject to installed-version validation. It does not provide character persistence, quest state, trade escrow or realm allocation.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.

Political rivalry does not change combat class or enable PvP

Faction is independent of permanent CombatDisciplineId. Do not add class-specific political filters or faction damage against players. NPC hostility is bounded to authored PvE conflict contexts using the shared access decision; neutral/guest/shared-threat rules override guard aggression.

The future opt-in PvP integration boundary is the existing authoritative damage validator with an independently authorized match context. No arena, duel, battleground, required PvP reward or functional toggle is implemented.
