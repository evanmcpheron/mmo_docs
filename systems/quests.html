Player mechanic and scope

A quest is a versioned authored objective graph, not a widget containing counters. Conversations select options from validated state and may restrict local input, but the shared world continues running.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Author quest.thornmere.first-supplies with Talk → Gather/Fish alternative → Produce or Commission → Deliver. Its alternatives must be achievable by each initial vocation.
  2. Assign the same UNpcServiceDefinition to the mentor actor and its UI route; do not create competing NPC parent hierarchies for every service.
  3. Add localization keys and explicit completion IDs. Wire authoritative craft/catch/combat receipts into objective evaluation, not sprite notifies.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

ANpcServiceActor composes dialogue, merchant, trainer and project services. The zone validates interaction range and routes objective events from authoritative gameplay results.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Interact with an NPC; validate lease, distance and service availability at the current regional revision.
  2. Present a state-derived dialogue projection. On selection, validate the actual option against current conditions again.
  3. Advance eligible objectives from accepted gameplay receipts and preserve the personal/global distinction.
  4. Commit quest reward and completion flag together; a repeated delivery cannot create a second reward. Authored CombatXP and VocationXP awards are separate nonnegative integers; a vocation award names its validated VocationId. Validate both awards and commit their ledgers with the same unique quest outcome/receipt, never credit whichever vocation happens to be active when a delayed callback arrives.
  5. Refresh dialogue, journal and relevant region board. Party sharing checks each recipient’s eligibility and never copies completed rewards.

Rejected commands, disconnect and restart

Expired option → DialogueChanged with a refreshed list. Duplicate delivery → existing receipt. Broken prerequisite graph → content validation failure before release. Missing localization text → visible fallback key in development.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_Dialogue lists currently legal choices; WBP_QuestJournal shows objective state and alternatives. Old options are revalidated on selection, including after a region-stage change.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

NPC idle/walk appearance combinations are authored and audited; unrestricted NPC randomization is deferred until compatibility is proven.

Factions use bounded reputation and authored benefits, not unrestricted political simulation. Main progress always has a viable alternative route.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.

Trainer and progression award integration

Use the existing ANpcServiceActor/UNpcServiceDefinition trainer interaction and eligibility checks for ChangeVocation; no new NPC hierarchy or service is needed. The authoritative identity operation preserves quest/faction/region state while changing only the active vocation and its permitted initial record/debit.

For quests that grant experience, author CombatXP and VocationXP independently and name the target vocation for a vocation award. Existing unique quest-completion outcomes/receipts protect both ledgers together; reject invalid awards before either is written. Inactive vocation histories are preserved, but do not receive XP merely from switching or opening a journal.
