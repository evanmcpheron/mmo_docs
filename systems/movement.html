Player mechanic and scope

Movement is on a flat X/Y gameplay plane. Eight input sectors are supported, but only four sprite facings are promised initially. Sprint, dodge, a bounded low-obstacle hop and authored-water swimming are distinct server-validated action states; there is no climbing.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Use a Paper2D map transformed into the X/Y plane and a non-rendered collision floor compatible with CharacterMovement. Keep the capsule upright. Orient the sprite plane toward the fixed orthographic camera; do not rotate the camera at runtime.
  2. Create IMC_Gameplay with keyboard and controller bindings. Normalize diagonals before mapping to world axes. Disable orient-to-movement rotation for the visual root; select sprite facing instead.
  3. Mark one low fence as hop-eligible and one deep pool as swim-eligible in the Thornmere fixture. Give both explicit exit cells; a water texture alone cannot authorize swimming. Exact custom movement-mode integration is an engine verification gate.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

UBriarwakeMovementComponent controls collision and movement. The autonomous client may predict movement after the movement integration is verified; the server rejects impossible paths. UActionExecutionComponent arbitrates exclusive actions.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. IA_Move → owning controller → character movement input; UI focus may suppress local gameplay input but never pauses the server.
  2. The server checks action state, speed budget, collision and legal water transitions. Hop requests include a candidate direction, never an authoritative landing point.
  3. Sweep the proposed hop corridor and landing footprint; reject unmarked walls, occupied landings and wrong water states. Reserve or revalidate a landing to resolve simultaneous hops.
  4. Advance the authoritative action window and collision policy. Cosmetic sprite lift must not move the authoritative capsule or change hit range.
  5. Replicate action state and facing. Restore normal movement only after a valid landing or a server-selected recovery cell.

Configured route fixture

In L_ThornmereVillage place a 32-unit test tile grid, fence.low.01, wall.solid.01 and water.safe.01. Use 160 units/s walk and 240 sprint solely as tuning examples.

Rejected commands, disconnect and restart

Out-of-range hop → InvalidLanding. Swim outside eligible water → WaterRequired. Dodge during committed crafting → ActionBusy. Disconnection cancels uncommitted actions and retains the last safe recoverable position.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

Input Action IA_Move supplies a normalized Vector2D. UCharacterAppearanceComponent projects velocity or aim onto four available facings. WBP_HUD shows stamina and water/hop restrictions without calculating authority.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Sprint may temporarily reuse walk at an explicitly labeled rate. Hop/swim poses are unverified; temporary visuals do not prove those animations exist.

Click-to-move is deferred. Grid pathfinding for AI is custom planned work; no claim is made that Paper2D automatically creates a usable navigation mesh.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
