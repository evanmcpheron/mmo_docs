Player mechanic and scope

The first operational baseline is one controlled persistence service/store, a small realm directory and dedicated zone processes. It is not an unmeasured fleet of microservices. Security and recovery are tested at the boundaries that move durable value.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Record the source-engine build, compiler, operating system, plugin hashes and packaged build IDs before testing. Create future server/client targets in the game repository, not this documentation repository.
  2. Configure the server default map and cook the required zone maps and dependencies. Follow the official dedicated-server procedure, replacing sample names with Briarwake and validating exact target paths.
  3. Test one dedicated process plus two external clients before using the 30-client fixture. PIE-only success is insufficient for provider, packaging or process-isolation claims.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

Dedicated zones validate gameplay commands and use server-only credentials. The persistence boundary applies lease fencing, transactions, authorization and audit controls.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Deploy matched server/client/content/schema versions into a nonproduction environment.
  2. Admit an authenticated character through an active lease; rate-limit and validate every value-changing command.
  3. Inject zone crash, response loss, database timeout and duplicate request at named transaction boundaries.
  4. Restore a backup into an isolated environment, reconcile receipts/outbox and validate that the restored world has one canonical state.
  5. Publish measured results with environment and raw evidence. Mark unsupported platform/provider/version cases Not run rather than passing them by assumption.

Rejected commands, disconnect and restart

Fail closed on invalid identity or fencing token. A storage outage rejects new durable mutations or keeps a precisely recorded pending state; it does not silently fall back to local SaveGame truth.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

Operational dashboards show aggregate latency, errors, contention, replication, crashes and progression stalls. Player-facing UI shows maintenance and recovery states without leaking internal credentials.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

Packaging checks exclude paid source ZIPs, plugin source/binaries without rights, development accounts and unlicensed previews from documentation distribution.

No Unreal binary, service deployment, database instance, provider session or performance result was produced in this documentation task.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
