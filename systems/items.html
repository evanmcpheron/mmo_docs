Player mechanic and scope

Item definitions describe kinds of things; owned item instances describe a specific character’s possessions. Equipment references item instance IDs, not copied item objects. A full inventory must produce a lossless rejection or an explicitly designed pending-claim result.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Create DA_Item_IronOre, DA_Item_WatchFitting, DA_Item_FieldLoaf and DA_Item_StarterSword with bounded stacks and stable IDs. Assign them in DA_GameCatalog.
  2. Configure the logical slots Head, Chest, Legs, Hands, Feet, Waist, Shoulders, Cloak, MainHand, OffHand, Necklace, Ring1, Ring2, Trinket1 and Trinket2.
  3. Assign an appearance policy to equipment. Chest/Legs correspond to legacy Top/Pants logically; a combined outfit fallback is permitted where individual overlays do not exist.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

UCharacterStateComponent holds owner-only server-approved projections. Gameplay equip commands revalidate requirements and request the persistence boundary; derived GAS equipment effects are rebuilt from the committed loadout.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Request MoveStack, EquipItem or UseItem with exact instance ID, amount and expected inventory revision.
  2. Validate ownership, amount, slot, binding, class-independent requirements and one/two-hand conflict on the server/service.
  3. Commit the inventory/loadout mutation once. Reject the whole operation if capacity or currency would become invalid.
  4. Publish the new revision to the owning player, and only permitted cosmetic/loadout summaries to other players.
  5. Rebuild equipment effects from the committed loadout, clearing old effect handles. Reopen the widget to pull the same state.

Rejected commands, disconnect and restart

Wrong owner → ItemNotOwned. Zero/negative quantity → InvalidQuantity. Bag full → InventoryFull without debit. Unknown content version → ContentMismatch; do not silently destroy the item.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_Inventory and WBP_Equipment display one shared projection; neither stores an independent authoritative bag. WBP_Loot requests authorized claims and reports inventory-capacity errors.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

The fifteen logical slots do not imply fifteen sprite overlays. The visual compatibility matrix must explicitly identify combined outfits, optional layers and missing art.

Common through Legendary rarity is a committed vocabulary; actual affix pools and drop percentages are tuning examples. No arbitrary unlimited affix generation.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
