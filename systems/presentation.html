Player mechanic and scope

A logical equipment slot is not a guaranteed visible sprite overlay. Playback uses one authoritative pose clock for body, outfit, hair, headwear, cloak and tool layers. Visuals may fail or be replaced without granting an item, hit or completed action.

Committed requirement: one-human core progression remains available. Recommended initial choices below are design work, not compiled engine behavior.

Editor and configuration recipe

  1. Enable Paper2D through Edit → Plugins and restart. Import only a locally licensed source sheet into Content/Game/Art/Characters after recording archive and file hashes.
  2. Inspect sheet dimensions and author guides before choosing grid extraction dimensions. Apply pixel-art filtering, consistent pixels-per-unit and shared foot pivots. Do not hard-code a frame size from a screenshot or a pack name.
  3. In a verified installed PaperZD release, create the animation source and sequences and assign the project AnimBP to the chosen component/character arrangement. The exact native parent and multi-layer synchronization API must be checked against that release before compilation.

Native ownership and Blueprint boundary

All Briarwake class and command names are proposed custom project APIs. They are not installed Blueprint nodes. C++ validates durable/gameplay invariants; Blueprint configures reviewed content and presentation.

UCharacterAppearanceComponent resolves the current visual key and synchronizes layers. PaperZD is a third-party presentation integration, not the owner of combat costs or catches.

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Wire the actual player flow

  1. Receive server-approved appearance IDs, action type, facing and action start time.
  2. Resolve a complete compatible pose set from UAppearanceCatalog; check every required layer before replacing the visible outfit.
  3. Drive all layers from the same frame/time sample, including late-joining characters. Missing ornamental layers may be hidden only where the fallback policy explicitly permits it.
  4. Select idle facing from the last stable direction. Diagonal ties prefer the previous valid facing; initial ties use horizontal priority, with hysteresis to prevent rapid switching.
  5. Play cosmetic notifications only. Stopping playback, suppressing notifies or hiding the character cannot change authoritative rewards.

Rejected commands, disconnect and restart

Unknown appearance → safe catalog fallback plus actionable error. A missing mandatory outfit pose blocks that combination. Out-of-order appearance revisions must not restore an old weapon.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

UI, animation and accessibility

WBP_CharacterCreate and WBP_Equipment use the same catalog as remote avatars. Unsupported outfit/action combinations display a declared fallback rather than silently removing clothing.

Bind observers, pull the current snapshot, and unbind on teardown. Preserve controller focus, localized error text and an accessible alternative to timing-only or sound-only cues. A widget’s disappearance is not a gameplay commit.

Art, maturity and stop condition

The prompt reports p1/p2/p3/p4 and 0bas/1out/2clo/4har/5hat/6tla/7tlb naming. These are source-reported leads, not independently verified inventory.

True six- or eight-facing artwork is not generated by mirroring or interpolation. Future direction expansion requires a complete body/equipment/action compatibility pass.

Stop when the linked fixture cannot be run end-to-end, required source compatibility is unknown, or a command lacks an observable rejection/recovery path. This is an initial implementation contract; exhaustive properties, graphs and every content instance are not yet authored.
