Purpose and ownership

Canonical character identities, independent combat progression and retained per-vocation histories; active VocationId is not a second progression record.

Owner: Persistence boundary. Lifetime: Durable, versioned record.

Replication: No raw record replication; publish privacy-filtered projections. Persistence: Canonical service record.

Authored values describe rules; runtime projections and persistent instances remain separate. A view/definition cannot become an additional authoritative writer.

How to create and configure

This is a proposed backend record contract, not a Content Browser asset. Implement a versioned service schema with explicit field types, uniqueness/revision/lease constraints and migration tests. No database schema implementation is generated by this documentation package.

Create the three widgets under Content/Game/UI/Frontend. Keep appearance, faction, combat discipline and vocation selections separate. Focus order: name, appearance, faction, combat discipline, vocation, confirm, back. Explain the permanent faction/class choices before confirmation; UI validation does not replace server validation.

Lifecycle, failure and recovery

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

For a definition, do not attach a transaction/RPC to the Data Asset itself: its owning runtime service implements this lifecycle. For presentation, bind once, pull the snapshot and unbind on teardown; ignore stale callbacks.

Progression value ownership and defaults

Extend the existing Progression object, not a new manager, component, table owner or parallel save. VocationId remains the only authoritative active-vocation selector. Progression.Vocations is keyed by stable vocation ID; an entry’s identity is its key, never its position, display name or an additional mutable ID field. The active key must exist and every trained inactive entry survives.

Progression.Combat belongs to the permanent CombatDisciplineId. Each vocation value stores TotalXP, DefinitionVersion, MasteryXP, UnspentMasteryPoints, PurchasedSkillIds, PurchasedTalentIds, LearnedRecipeIds, UnlockedTechniqueIds and AccomplishmentIds. Integer values are nonnegative and bounded; ID collections are duplicate-free and validated against their versioned definitions. Mastery rank derives from MasteryXP and the authored mastery graph. Do not keep an independently writable saved Level or MasteryRank.

Combat and vocation levels derive independently from TotalXP and their pinned, validated LevelThresholds. No formula reads the other track’s level. ContentVersion on the definition is the stored DefinitionVersion; reject unavailable versions rather than silently using a changed curve. First training uses the vocation’s InitialXP (default 0), which must map to Level 1; initialize mastery XP/points to 0 and earned sets empty except explicitly authored initial recipes/unlocks. Entry creation and any permitted initial grants occur once under the existing transaction/domain-uniqueness rules.

Revision is the existing character aggregate revision and also the progression/build projection revision. Every committed XP award, purchase or active-vocation change advances it once; do not add a separately writable build/level counter. SchemaVersion versions serialization, not player progress. Preserve reputation, inventory records, quest outcomes and Living Regions contributions in their existing owners.

One-time award history remains governed by the existing durable domain outcomes and Record_CommandReceipt, not by cached ability handles. Threshold awards happen on validated XP deltas once; import, hydration, switching and permission reconstruction grant no XP, points, items or already-earned unlock rewards.

Compatible migration and unresolved legacy identities

Schema 2 below is the proposed next documentation contract; no deployed schema or actual save fixtures were found in mmo_docs. Before rollout inventory real supported versions and codecs. Keep the old representation readable, back up originals and validate conversion into temporary values before an atomic revision/schema update. Do not treat this prose as an executed database migration.

For a supported single-vocation legacy record, retain VocationId and move its existing vocation XP/mastery/purchases/recipes/techniques/accomplishments into Progression.Vocations[VocationId]. Preserve the combat ledger, talents and unspent combat points separately, plus all unrelated fields and unique reward outcomes. After conversion only the new keyed value is authoritative; deprecated fields remain read-only compatibility input, never dual-written. Reapplying the migration to schema 2 is a no-op.

Preserve every existing historical vocation record by its original stable ID. If an old format did not store a particular fact, use documented empty/zero defaults only where absence is proven to mean never earned. Unknown or conflicting history is not proof of an untrained vocation: retain the raw record, quarantine conflicting writes and recover from trusted records/receipts/backups or explicit migration review. Do not silently reset or discard earned progression.

Backfill CombatDisciplineId or FactionId only from an unambiguous trusted original selection. Otherwise return MigrationNeedsIdentitySelection and do not admit gameplay. Resolve through an authenticated, audited one-time legacy completion using approved available definitions while the record is fenced; preserve existing XP/talents and require a reviewed mapping when they constrain compatibility. Commit the decision and receipt atomically, then apply the permanent lock. Never assign a default class, infer allegiance from reputation or expose repeated class changes.

A missing inactive key in a validated current-schema record means never trained. A missing active key, duplicate serialized key, negative/overflowed XP, unknown/removed definition, inconsistent purchased IDs or unsupported schema/definition version is a load/migration failure, not permission to initialize over old data. Reject/quarantine while retaining the original; do not fall back to a fresh character. A content migration preserves XP, earned points/purchases and one-time outcomes; recompute views without replaying threshold rewards.

Faction integration and failure acceptance

Initialize immutable definitions before admitting the feature at its actual phase. Subscribe, pull the authenticated snapshot, then consume contiguous newer revisions; unbind on teardown or character/epoch change. Missing mandatory content rejects new creation/activation and routes existing characters to safe authenticated recovery without losing identity.

Test one human through both branches using the free public contract; test two opposed characters in neutral services and at a hostile boundary; repeat accepted request IDs, stale revisions and stale epochs; run 30 connected clients in the authorized game project. Offline source/model tests are not runtime/Blueprint evidence.

Do not log credentials, raw transfer tickets, account private data or complete dialogue payloads.
