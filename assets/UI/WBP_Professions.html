Purpose and ownership

Professions screen: request/observe only, explicit focus and teardown contract.

Owner: ABriarwakeGameMode admits a verified character-session lease. ABriarwakePlayerController routes owned commands. A newly spawned ABriarwakeCharacter is only the current body.. Lifetime: Current actor/component/widget instance; reconstruct on teardown.

Replication: Explicit per-field public/owner-only projection; see system contract. Persistence: No Actor/UObject pointer in durable storage.

Authored values describe rules; runtime projections and persistent instances remain separate. A view/definition cannot become an additional authoritative writer.

How to create and configure

Use the native asset editor or controlled fixture authoring path appropriate to the declared type. Confirm installed plugin support before creation; configure exact references through the owning phase rather than treating this planned record as an already-created engine asset.

Create the three widgets under Content/Game/UI/Frontend. Keep appearance, faction, combat discipline and vocation selections separate. Focus order: name, appearance, faction, combat discipline, vocation, confirm, back. Explain the permanent faction/class choices before confirmation; UI validation does not replace server validation.

Custom project functions and backend endpoints are proposed. Engine creation actions, plugin APIs and these custom commands are not interchangeable. Emit a completed-change notification only after the owning rule/transaction succeeds.

The graph tracks creation requirements; later observer assignments may reference an already-created owner without requiring cyclic construction. Follow the phase’s reopen-consumer instructions.

Lifecycle, failure and recovery

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

For a definition, do not attach a transaction/RPC to the Data Asset itself: its owning runtime service implements this lifecycle. For presentation, bind once, pull the snapshot and unbind on teardown; ignore stale callbacks.

Concrete wiring and fixture

Account fixture acct-bw-001 has two permitted slots; char-bw-hearth uses discipline.vanguard and vocation.hearthkeeper at zone.thornmere / spawn.square. Resolve FactionId from the approved faction fixture; the authored faction.hearthward-league fixture now resolves via sources/factions.json; runtime deployment remains gated. Slot counts and locations remain test values, not a replacement faction starting-region policy.

Submit CreateCharacter(RequestId, Name, AppearanceIds, FactionId, CombatDisciplineId, VocationId) from the authenticated account context. The service derives AccountId; it is not trusted from the form. Include every semantic selection in the existing request digest.

Reconnect from another client after logging out. Display the same permanent faction/class, active vocation, saved vocation histories and appearance without granting another kit or replaying progression rewards.

Acceptance and remaining depth

Create the Vanguard/Hearthkeeper with an approved faction, enter Thornmere, log out, restart and reconnect. Permanent identities, independent progression and all vocation records persist; one character, one starter kit and one active lease exist. See Fixture_identity for trainer-switch and migration acceptance.

Race two requests for the same normalized name, then race two logins for the same character. Exactly one name reservation and one current lease win; the losing session cannot spend inventory.

Active and retained vocation views

Observe owner-only Progression.Vocations histories and the one active VocationId at Record_Character.Revision. Display saved level/XP, mastery and learned recipes for inactive vocations as retained but inactive. A never-trained selection previews Level 1; it does not overwrite another history. No editable combat-class control belongs here.

Request retraining only through the existing trainer/controller route, with current revisions and the original PendingRequestId until resolved. Display server rejection or PendingSave/RecoveryPending without optimistic progression/grant mutation. After success pull current state; a replayed old receipt must not replace a newer projection.
