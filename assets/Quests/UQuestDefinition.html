Purpose and ownership

Versioned objective graph and once-only rewards.

Owner: Content author; immutable during play. Lifetime: Loaded content; no player state.

Replication: None for authored definitions/assets. Persistence: Save stable IDs only; not this object.

Authored values describe rules; runtime projections and persistent instances remain separate. A view/definition cannot become an additional authoritative writer.

How to create and configure

Prepare the future native type UQuestDefinition using the stated base and required module dependencies. Compile the real project before any Blueprint selects this type. Expose only current-phase properties and validated APIs. This page does not create a header, implementation or compiled class.

Author quest.thornmere.first-supplies with Talk → Gather/Fish alternative → Produce or Commission → Deliver. Its alternatives must be achievable by each initial vocation.

Lifecycle, failure and recovery

Reject an invalid or expired lease, an unknown content ID, a stale revision, insufficient capacity or permission before mutating state. Return a stable error code and refresh the current projection; do not ask the player to repeat an unknown-outcome transaction with a new request ID.

Persist the operation receipt in the same transaction as its effects. On a lost response, query or retry the same request identity. A successful receipt returns the original result; a changed payload under that identity is rejected. A UI timeout is not proof of a database rollback.

For a definition, do not attach a transaction/RPC to the Data Asset itself: its owning runtime service implements this lifecycle. For presentation, bind once, pull the snapshot and unbind on teardown; ignore stale callbacks.

Faction contract: ownership, initialization and authority

Extend existing evaluator definitions with faction eligibility and branch options; do not add faction quest subclasses or manager. Objectives consume trusted sources, not widgets.

Use the canonical faction transaction/lifetime contract and the exact authored campaign. This is a proposed extension to the existing owner, not an installed API or independently mutable manager.

Faction integration and failure acceptance

Initialize immutable definitions before admitting the feature at its actual phase. Subscribe, pull the authenticated snapshot, then consume contiguous newer revisions; unbind on teardown or character/epoch change. Missing mandatory content rejects new creation/activation and routes existing characters to safe authenticated recovery without losing identity.

Test one human through both branches using the free public contract; test two opposed characters in neutral services and at a hostile boundary; repeat accepted request IDs, stale revisions and stale epochs; run 30 connected clients in the authorized game project. Offline source/model tests are not runtime/Blueprint evidence.

Log structured OperationId, RequestId, character-scoped pseudonymous ID, content/character/region/policy revisions, rejection code and committed receipt reference. Do not log credentials, raw transfer tickets, account private data or complete dialogue payloads. Definition of done: exact faction behavior passes source/model checks AND later authorized native/Blueprint/dedicated-server acceptance with recorded evidence; runtime not_run here.

Planned game behavior is not runtime evidence. Read sources and limitations.
