What the boundary promises

Recommended initial choice: one small service with a transactional store owns character value, world contributions and durable receipts. Technology/provider selection remains open. Do not introduce distributed transactions across many services before the single-boundary route works.

Transport delivery may repeat or fail. The design aims for one durable effect per accepted operation, not a promise that messages are delivered exactly once. A receipt and uniqueness constraints make repeated delivery safe.

Commit sequence

  1. Authenticate and apply rate limits. Resolve the command’s character scope and content definition. Reject malformed requests before expensive work.
  2. Look up an existing receipt under (character/account scope, operation type, RequestId). Return it only to the authorized owner. If the semantic payload digest differs, reject RequestIdentityConflict.
  3. In the transaction, lock or compare affected records in a deterministic order. Recheck the current session epoch and expected revisions here—not only before making the service call.
  4. Plan all changes: material/currency debits, item capacity and instance creation, quest/mastery/project updates. Validate the complete plan before any commit.
  5. Commit the plan, domain uniqueness keys, receipt and outbox entry atomically. Store the returned instance IDs and exact committed revisions in the receipt.
  6. Publish privacy-filtered projections from the outbox. Consumers accept revisions idempotently; delivery may repeat. A crash between commit and publish is recovered by the pending outbox.
  7. A client/server that lost the response queries the receipt or retries the same semantic request. A fresh lease may query an older committed receipt for the same authenticated character; it may not authorize a new write using an old epoch.

Reservations and cancellation

The initial craft is an immediate atomic operation. Timed crafting needs a durable reservation only if ingredients are reserved across a delay. Reserved items cannot also be sold, equipped into a conflicting state, traded or consumed. The reservation has a state machine: Reserved → Completed or Cancelled, with one terminal transaction. A cancellation cannot refund inputs after completion.

A spinner timing out or an actor disappearing is not sufficient evidence to refund. Query the reservation/receipt first. If storage is unavailable, expose PendingSave/RecoveryPending and prevent competing value mutations until the outcome is known.

Uniqueness beyond requests

New client-generated request IDs must not bypass domain uniqueness. Use permanent or appropriately retained guards for (EncounterInstanceId, CharacterId, RewardVersion), (CastId, CharacterId), (SiteId, Generation, ClaimId), (CharacterId, QuestId, completion generation) and unique contribution identities. Receipt retention alone is insufficient if old domain events can be replayed after receipts are pruned.

Reject, retry and compensate are different

A validation rejection has no committed value changes. A transient service failure before a known commit can be retried with the same identity. An unknown outcome must be queried. A compensation is a new audited transaction after a known committed outcome; it must never blindly replay an old snapshot over newer character progress.

A definitive stale-revision rejection followed by a revised player choice is a new semantic request. Do not change fields under the old RequestId. Authentication failures must not create unauthenticated access to another character’s receipt.

Fault-injection table

Kill/drop pointRequired outcome
Before transactionNo value change; same request may execute later.
After validation, before commitEither transaction aborts or a commit is queryable; no partial debit.
After commit, before responseReceipt returns original result after reconnect.
After commit, before outbox publishPersistent outbox eventually republishes committed projection.
During repeated outbox deliveryViews converge by revision and do not grant rewards.
After lease was fencedOld source mutation fails its in-transaction epoch check.
During backup restoreRestore into isolation, verify revision/receipt consistency, and require an operational recovery plan before admitting live clients.

Implementation gap

This document specifies a proposed contract. Concrete schemas, transaction implementation, database choice, transport authentication, production retention and fault-injection results remain future work. No database was created by this package.
