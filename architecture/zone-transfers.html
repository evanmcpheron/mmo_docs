Choose the correct travel boundary

Epic documents that whole-server ServerTravel brings connected clients to the new world. Briarwake’s per-character biome crossing therefore requires a separate destination process and a validated client reconnection coordinated with durable ownership. Seamless travel within one server is not a cross-server database or identity protocol.

Recommended initial choice: Thornmere and Elderwood are separate dedicated processes on ports 7777 and 7778 in the development fixture, with one small directory/transfer responsibility alongside persistence.

Transfer state machine

SOURCE_ACTIVE(epoch e)
  → PREPARING (stop new actions; drain/reconcile pending durable work)
  → DESTINATION_RESERVED (short-lived capacity reservation)
  → IN_TRANSIT(epoch e+1; source writer fenced)
  → DESTINATION_ACTIVE(epoch e+1; ticket consumed)
  → SOURCE_RETIRED

Before fencing failure: cancel preparation and resume epoch e if still valid.
After fencing failure: service recovery claims a NEW epoch; never revive e.

Protocol and actor responsibilities

  1. The player reaches a validated gate. Source checks destination eligibility, route unlock, safe spawn, current lease and no incompatible action.
  2. Freeze new gameplay/value commands and reconcile in-flight durable operations by receipt. Do not capture a snapshot while a craft may still commit unnoticed.
  3. Reserve destination capacity. Record TransferId, CharacterId, source/destination zone IDs, content version and a short expiration.
  4. Commit the verified handoff snapshot and fence source ownership in the same authoritative transition. Increment the character epoch and enter InTransit; old source commands now fail their transactional epoch check.
  5. Issue a short-lived single-use opaque ticket bound to character, account, destination, transfer and new epoch. Keep bearer material out of logs, screenshots and public session advertisements.
  6. Instruct only that client to connect to the reserved destination. The loading screen displays progress but has no ownership authority.
  7. The destination authenticates the client and atomically consumes the ticket/reservation while acquiring the active lease for the new epoch. It validates the arrival cell, content and snapshot revision before possession.
  8. Initialize the new body and subscriptions, then activate commands. The source retires its body after terminal confirmation or fencing; visual destruction is not the fence itself.

Failure and recovery arbitration

FailureAuthoritative decision
Destination fails before source fencingCancel reservation/preparation, retain valid source lease and resume safely.
Client drops after fencing but before ticket consumptionKeep InTransit durable state; reconnect queries coordinator, not cached source address.
Destination consumes ticket then diesTicket stays consumed; recovery uses the canonical checkpoint/receipt state and a newer lease epoch.
Ticket expires as destination activatesConsumption and timeout recovery race through one compare/commit decision; only one wins.
Recovery returns to source zoneAdmit as a new authoritative session with a newer epoch, not by unfreezing the old body.
Source sends a late item commandPersistence rejects the old epoch even if that actor is still alive.
Client replays the ticketReturn transfer terminal state or reject; no second possession/lease.
Content/arrival mismatchDo not activate incompatible content; recover to a validated safe checkpoint through the coordinator.

Data contract

Record_Transfer includes TransferId, authenticated CharacterId, source/destination identities, snapshot revision, policy/content versions, token digest, reservation expiry and terminal result. Record_SessionLease includes CharacterId, owner server instance, epoch, expiry and status. No Actor pointer crosses processes or becomes a database key.

Every durable mutation checks the lease at commit time. Merely stopping input or deleting the source Pawn cannot prevent an already queued command from committing. Fencing must be a persisted check enforced by the same mutation boundary.

Two-client fixture

  1. Launch Thornmere and Elderwood dedicated processes only after actual game builds exist. Connect two separate clients to Thornmere.
  2. Client A crosses the north gate; client B remains in Thornmere. Assert B’s connection/map is unchanged.
  3. On A verify character/vocation/appearance/item instance IDs and region state. The active lease table contains one owner for A.
  4. Inject failure at each named protocol step, then repeat with stale tickets, repeated transfer requests and an old-source craft.
  5. Observe one durable terminal outcome and a safe reconnection path. Packet travel success alone does not pass the ownership test.

Evidence and scope

This is a proposed protocol requiring implementation, secure transport and failure testing. No transfer coordinator or dedicated server was executed. The engine travel distinction was checked against UE-TRAVEL; all Briarwake service APIs remain custom future work.

Faction-safe admission

Read durable FactionId/version at both source and destination, validate guest/root quest unlock and safe spawn under supported policy, fence source epoch before destination activation. Disabling new signups does not orphan an existing character.

Store only the travel ticket digest; lost begin responses use authenticated rotation or expiry recovery. Activation and expiry compete on the same transfer state/epoch; exactly one active writer survives. No faction value from the client menu can authorize a destination.
