Required evidence first

Epic’s dedicated-server tutorial uses a source engine build and a C++ project with server/client targets. Briarwake’s installed 5.8.3 source, actual targets and plugin builds are not available here. Follow the official mechanism, then verify the exact local build configuration and generated executable paths.

Future setup sequence

  1. In the future game, enable verified required modules/plugins. Create the native runtime classes and the actual server/client build targets; none is supplied by this documentation package.
  2. Set Maps & Modes → Server Default Map to the intended authored map; keep the client frontend separate. Assign the custom GameMode/Controller/PlayerState/default pawn classes.
  3. Build Development Server and Development Client using the verified toolchain; cook the required maps and dependencies for both configurations.
  4. Run the headless process with a log and explicit port, then connect two separate clients. Do not describe multiple PIE viewports as packaged process/provider proof.
  5. For Phase 07, run a second server on another port and use the custom verified transfer coordinator. Register actual process identities and capacity without publishing credentials.

Illustrative future commands

Run these only after the corresponding real executable and map have been built and cooked. The package path intentionally includes /Game/Game because the proposed physical content directory is Content/Game.

BriarwakeServer.exe /Game/Game/Maps/L_ThornmereVillage -log -port=7777
BriarwakeServer.exe /Game/Game/Maps/L_ElderwoodRoad -log -port=7778

Provider separation

LAN/Null session testing and a Steam option need separate validated configurations. Steam presence/listen-lobby settings are not automatically correct for a dedicated persistent realm. Account identity, persistence, realm directory and transfer are not supplied by session advertisement.

Pass criteria

Two external clients see server-owned avatars and cannot spoof durable state. A later zone crossing moves only one client. Record successful/failed provider callbacks, no-local-player behavior, packaged load/cook logs and actual network observations. Status in this delivery: Not run.
